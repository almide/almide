# E085 — 标准库之外使用 `@intrinsic` 或 `prim.*`

[English](../../../diagnostics/E085.md) | [日本語](../../ja/diagnostics/E085.md) | [简体中文](../../zh-CN/diagnostics/E085.md)

> 原文：[`docs/diagnostics/E085.md`](https://github.com/almide/almide/blob/9a95b28519b90ae535dc9918bfed04805dc4675c/docs/diagnostics/E085.md)，固定提交 `9a95b285`。这是面向读者的非规范性译文；CLI 诊断输出仍为英语。

`@intrinsic("almide_rt_…")` 和 `@wasm_intrinsic` 将 fn 名直接绑定到 runtime 符号；`prim` 模块是标准库建立其上的基本层（原始 load/store、分配器、`fd_write`、宿主文件调用）。两者都是 runtime 边界，仅在标准库自身源码中合法：编译器携带的捆绑标准库，或 `stdlib/` 下与某个嵌入源码同名的文件。在其他位置，checker 拒绝声明，以及任何 `prim.<fn>` 引用（调用、管道目标、fn 值）或 `import prim`。

```almide
@intrinsic("almide_rt_fs_write")
effect fn write(path: String, text: String) -> Result[Unit, String]   // E085
```

## 诊断形式

```
error[E085]: @intrinsic on fn 'write' outside the stdlib
  --> app.almd:1:1
hint: intrinsics live in the stdlib; wrap in an effect fn: call the stdlib
      module that owns the operation (fs, http, process, ...) from an
      `effect fn` of your own, so `--profile critical` sees the capability
```

```almide
effect fn main() -> Unit = {
  let text = prim.read_text_file("in.txt")!   // E085
  println(text)
}
```

```
error[E085]: `prim.read_text_file` outside the stdlib
  --> app.almd:2:14
hint: `prim` is the standard library's primitive floor, not user surface;
      call `fs.read_text` instead
```

提示指出包装基本层操作的公开函数。它从标准库源码推导（标准库自身调用图中最接近该操作的公开函数，优先专用的单操作转发器），因此随标准库变化而更新。没有专用转发器、被许多公开函数共享的基本层操作（`prim.handle`、`prim.load32`）属于内部基础设施，提示会说明它是标准库内部内容。

## 修复

导入拥有该操作的标准库模块并调用它；操作带 effect 时，从 `effect fn` 中调用：

```almide
import fs

effect fn write(path: String, text: String) -> Unit = fs.write_text(path, text)!
```

对 `prim.*`，调用提示指出的函数（`prim.read_text_file(p)` 对应 `fs.read_text(p)!`，`prim.band(a, b)` 对应 `int.band(a, b)`）。

## Fix-it 判定

**not-fixable** — 替代方案是调用拥有 runtime 符号或基本层操作的标准库模块，而符号名不能确定该调用：签名、effect 和错误形态属于标准库包装函数，而非 runtime，`prim.read_text_file` 与 `fs.read_text` 的错误形态不同。编译器指出规则和修复形态，不改写声明。

## 原因

权限说明（`almide check --profile critical --allow IO`、[cli.md](../../../specs/cli.md#--profile-critical)）以标准库模块为单位：程序要么被授予 `fs`，要么没有。直接指定 runtime 符号的用户文件从未导入 `fs`，因此单独的属性曾成为 profile 无法看见的磁盘写入方式。`scripts/check-intrinsic-boundary.sh` 证明 intrinsic 能链接，而非获准使用。`prim` 是下一层的同一漏洞：它一直可访问，因此用户文件中的 `prim.read_text_file(p)` 能通过类型检查，在没有 `import fs` 时到达宿主（#3025）。权限按源码来源决定，绝不按模块名称决定：名为 `list` 的用户模块仍是用户模块，`spec/stdlib/x_test.almd` 不是标准库。checker 无法知道来源的源码（没有路径的语言服务器内存分析）不作判定。
