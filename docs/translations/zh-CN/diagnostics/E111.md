# E111 — 类型过大

[English](../../../diagnostics/E111.md) | [日本語](../../ja/diagnostics/E111.md) | [简体中文](../../zh-CN/diagnostics/E111.md)

> 原文：[`docs/diagnostics/E111.md`](https://github.com/almide/almide/blob/9a95b28519b90ae535dc9918bfed04805dc4675c/docs/diagnostics/E111.md)，固定提交 `9a95b285`。这是供读者参考的非规范性译文，CLI 诊断输出仍为英文。

推断出的类型超出了 `type_size` 编译成本预算（ADR-0030）：其节点数超过编译器为一个类型构造的上限。类型内部每复制一次类型，整体就会增长，因此几行代码就能要求指数级大小的类型。

```almide
effect fn main() -> Unit = {
  let t0 = 1
  let t1 = (t0, t0)
  let t2 = (t1, t1)
  // ... each line doubles the type: t22's has 4 million leaves
  println("ok")
}
```

```
error[E111]: type too large (257+ nodes, max 256)
```

通过将实参返回两次的泛型也会发生同样情况（`fn dup[T](x: T) -> (T, T)`，然后 `dup(dup(dup(x)))`）。检查器在推断时共享结构，待共享结构要展开表示时，预算会阻止复制。

## 修复

为中间类型命名，或把数据保存在类型不会随每一步增长的记录或列表中。

```almide
effect fn main() -> Unit = {
  let t0 = 1
  let t1 = [t0, t0]
  let t2 = t1 + t1   // List[Int], however long it gets
  println("ok")
}
```

## 原因

编译器会运行于不可信源码之上：PR 的 CI、打开文件时的 LSP、评分器、playground。在预算加入前，这种形式的22行代码曾让 `almide check` 达到 3.7 GB（#4114）。预算统计节点，而不是秒数或内存，因此所有机器判定相同。源码不能提高它；不存在对应属性、manifest 键或环境变量。运行编译器的人可以用 `--budget type_size=N` 调整（`almide budgets` 列出所有预算），但 `--profile critical` 会拒绝这样做。

测试样例：`tests/diagnostics/e111-type-doubling-chain`、`e111-type-doubling-through-a-generic`；门禁是 `tests/compile_budget_test.rs`。
