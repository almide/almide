# Beyond-Rust Lab

**Question:** Almide becomes machine code through rustc and LLVM. Keeping that route, how can we change the generated Rust to make it faster than handwritten Rust built with the same rustc and flags?

The starting hypothesis is that, because both sides have the same machine-code engine (LLVM), there are only two ways to win.

- **A. Information:** convey facts known to Almide's type checking, effects and value semantics, but absent from the handwritten Rust, in a form LLVM can use.
- **B. Automation:** have the compiler automatically perform, every time, adjustments that are possible in Rust but too cumbersome for ordinary Rust users to make.

Phase 2 of the on-hold [performance-research.md](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/roadmap/on-hold/performance-research.md) proposes bypassing rustc and emitting LLVM IR directly. This lab instead measures how far we can go without removing rustc. Only if a gap remains beyond this approach's reach does it justify resuming Phase 2.

<a id="計測の単位-カーネル-レバー-の-4-列"></a>

## Measurement unit: four columns for a (kernel, lever) pair

One experiment applies one lever (a transformation of generated Rust) to one kernel (the program being measured). Measure these four columns in each experiment.

| Column | Contents |
|---|---|
| **R0** | Ordinarily written handwritten Rust (`research/benchmark/perf/rust-ref/`), without `unsafe` |
| **A0** | Rust currently generated by Almide (`almide_gen_main.rs` written by `almide build --release`) |
| **A1** | A0 with the lever applied, initially **by hand** (a probe) |
| **R\*** | Expert-written Rust for the same algorithm. May use `unsafe`, intrinsics and `assert_unchecked`. The attainable ceiling |

How to read it:
- **Beyond Rust** ⇔ A1 < R0 (same flags, on both architectures, beyond variation).
- **Value of the lever** = A0 ÷ A1.
- **Remaining headroom** = A1 ÷ R\*. Near 1 means that kernel has reached the ceiling through rustc.

<a id="手順-実装する前に手で当てて測る"></a>

## Procedure: apply by hand and measure before implementing

1. Emit the kernel's A0 (`/tmp/almide-run/almide_gen_main.rs`, one file including the runtime).
2. Apply the lever manually to make A1. Verify that its output matches A0 byte for byte.
3. Measure all four columns under the same conditions (controls below).
4. For rows that get faster or slower, write the **instruction-level explanation** using machine-code differences (`objdump` / `perf annotate`). Do not adopt a difference whose reason cannot be explained.
5. Turn only levers meeting the graduation criteria into compiler-implementation issues.

A lever that does not work when applied by hand will not work when implemented. Falsify it cheaply before paying the implementation cost.

<a id="統制条件"></a>

## Controls

- Use **the same rustc, flags and target CPU** for all four columns. Take the target CPU from the compiler's default, rather than copying it manually (#3883: only the Almide side used `x86-64-v3`, making the comparison unfair).
- All four columns must have byte-identical output. Do not reorder floating-point operations (fast-math), because that breaks the native/wasm output-equality promise.
- Measure on two architectures: GCE c4-standard-8 (x86, Xeon 8581C) and c4a-standard-8 (arm, Neoverse-V2).
- Alternate the columns and take the median of at least 7 runs. On VMs with a PMU (performance counters), also record instruction counts (`instructions:u`).
- Pass arguments at runtime. Literals let LLVM fold the entire loop into an expression.

<a id="卒業条件"></a>

## Graduation criteria

A lever becomes compiler work when all three conditions hold:

- A0 ÷ A1 ≥ 1.05 on at least two kernels.
- This holds on both architectures.
- No kernel slows down by more than 2%.

Land a graduating lever together with a row in the performance check (`scripts/check-perf-ratio.sh`).

<a id="レバー一覧"></a>

## Lever list

| ID | Kind | Lever | Hypothesis: what LLVM becomes able to do |
|---|---|---|---|
| L1 | A | Emit proven facts as `assert_unchecked`, unchecked indexing or unsigned arithmetic | Remove bounds-check branches. Turn `/2` into an unsigned shift. Improve vectorization decisions (#3604's enumerate index) |
| L2 | A | Express value-semantics non-aliasing through argument forms that receive `noalias` (separate `&mut [T]` and `&[T]`) | Enable load elimination and vectorization |
| L3 | A | Emit effect-free functions in forms LLVM can infer to be read-only (inlining boundaries, placement of `#[inline]`) | Enable common-subexpression elimination and loop-invariant code motion |
| L4 | B | Build multiple versions of hot functions with per-function CPU settings and choose the fast version (`#[target_feature]` and runtime dispatch) | Get both benefits, such as portable for nbody and v3 for spectralnorm (#3883) |
| L5 | B | Automate PGO (reoptimization with statistics collected by running the program) as an extension of `--release` | Match branch placement and inlining decisions to actual execution |
| L6 | A | Turn callbacks from `Rc<dyn Fn>` into direct calls to concrete functions | Remove per-call target lookup and permit inlining (get onto R0's footing) |

L6 is a lever for catching up, not surpassing, but it is listed because leaving it in place obscures the benefits of other levers. Allocation semantics (region windows, Perceus reuse) are already a winning line of work, tracked separately by VICTORY rows in [BENCHMARKS.md](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/project/BENCHMARKS.md).

## Kernels

Alongside the existing rows in `research/benchmark/perf/` (nbody, spectralnorm and its two idiomatic forms, fasta, fft, fannkuchredux, mandelbrot), add small kernels isolating each lever's effect.

- Indexed loops (bounds checks).
- Enumerate indices.
- Map/fold with callbacks.
- Numerical loops heavy in `sqrt`.

Checking A0: rebuilt A0 differs from the binary written by `almide build --release` by no more than 1%, except indexed on x86 (A0 2.3% faster) and nbody on arm (A0 2.5% slower). The only differences are `panic=abort` and the runtime crate's flags (Almide uses `codegen-units=4`).

**Machine-code explanations** (all rows differing by at least 2%)

- **A0 already has the facts.** LLVM derives the same facts itself in A0 for range counters and enumerate indices. F1–F3 in the three spectralnorm forms had the same hot-loop instructions as A0 on both x86 and arm (`perf annotate`). A0 also hoists `v[j]` bounds checks out of the loop: the loop exits at `min(n, len)`, then tests whether to abort. idxloop's A0 also has no remaining bounds checks. On arm, `i / 2` is `lsr` and `r as f64` is `ucvtf`; on x86 it is vectorized four-wide. The information L1 could add was already present.
- **F2 causes spectralnorm_indexed's slowdown (x86 −21%, arm −2% / `native` −12%).** Adding `assert_unchecked(0 <= j && j < n)` inside the fold closure leaves the `v[j]` bounds check in the loop (x86 `cmpq %rbp,%rdx` + `je`, arm `cmp x10,x14` + branch, every iteration). A0 could fold it into the exit. On x86, A0's twofold unrolling and paired divides (`vdivpd %xmm`) also disappear, becoming one-at-a-time `vdivsd`. Instructions rise from 17.55G to 22.39G on x86 (+28%) and 15.13G to 18.15G on arm (+20%). The exploratory column with F2 removed and only F1 retained has the same instruction sequence as A0 (−2.3% remains in x86's primary set, but the hot-loop instructions match A0 and the reason has not been identified).
- **idxloop's slowdown on arm (primary set −20%).** In A1, loads become unconditional `get_unchecked`. LLVM therefore rewrites them to carry `xs[i-1]` and `xs[i]` in registers into the next iteration (loads per iteration 3 → 2, adding two `fmov`; instruction count 7.50G → 8.00G, +6.7%). That is the entire instruction difference. Why it amounts to 20% on Neoverse-V2, however, has not been explained from the machine code.
- **idxloop's gain on arm `native` (+4.5%) is unexplained.** Instruction counts match (5.50G), and both are unrolled twofold. Only instruction ordering and register allocation differ.
- For idxloop on x86 (primary set), A1's instruction count falls from 3.50G to 3.13G, but the timing difference is under 1%.

**R\* headroom** (A1 ÷ R\*)
- spectralnorm, x86: 1.57–1.97. R\* divides four rows together in SIMD lanes while retaining the same operation order. It computes the denominator in f64, exact if `n <= 2^20`. Instructions fall from 17.5G to 4.7G. This is not L1 but a candidate for a different lever: parallelizing rows.
- spectralnorm, arm: ≈ 1.0. R\* uses `fdiv v.2d`; instructions are halved (15.1G → 7.3G), yet time is unchanged. f64 division throughput is the bottleneck on Neoverse-V2, so two lanes confer no gain. With `native`, R\* is slower (0.86–0.92).
- nbody: x86 1.04–1.14, arm 1.08–1.18. R\* computes the 10 `sqrt`/divides while positions are unchanged in three groups of four lanes.
- idxloop: ≈ 1.0 (the 1.25 in arm's primary set is A1's own slowdown. A0 ÷ R\* = 1.00).

**Incidental observations**
- For idxloop on x86 `x86-64-v3`, A0 is 1.66 times faster than R0 (0.273 versus 0.454). R0 retains two bounds checks per iteration, including `xs[i / 2]`, and stays scalar. A0 has no checks and is vectorized four-wide. Independently of L1, this row is already “beyond Rust.”
- For nbody on x86, `x86-64-v3` makes A0 11% slower than leaving the CPU unspecified (2.01 versus 1.81). R0 does not change. The same phenomenon as #3883. On arm, A0 is 18% faster than R0 (2.86 versus 3.48).
- The one-crate form (`ALMIDE_NO_RTLIB=1`, runtime included in `src/main.rs`) gives enumerate 1.31 seconds and indexed 1.34 seconds on arm. It was not used for A0 because it is slower than the Almide binary (1.12 seconds, 1.22 seconds). The reason has not been investigated.

**Conclusion:** implementing L1 as mechanically emitting proven facts everywhere possible brings no benefit and causes losses. On this kernel set, LLVM already derives the local facts L1 can emit. Redundant `assert_unchecked` disrupts transformations LLVM was making (folding bounds checks into the exit, unrolling and vectorizing, load placement). If L1 continues, restrict it to facts LLVM cannot derive itself: for example, lengths across calls (`len(v) == n`) or range-bounded integers (an upper bound on `n` establishes that the product cannot become negative). Before emitting a fact, verify that A0's machine code actually still contains the instructions it would eliminate.
