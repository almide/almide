> **当前范围**：将回执 **C-PRESERVED**（差分保持）做成 harness，并确定 **C-ASSERTED**（批准性质）的可判定片段。
> **退出条件**：针对 agent 修改的 `.almd` module，所提议 harness 以第三方可复现的形式输出“保持了观察契约”。原先的 `make verify` 是构想中的名称，并非当前回执保证保持全部语义。
> **关联文档**：[v1-proof-architecture](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/roadmap/active/v1-proof-architecture.md)（最终形态）、[receipt-logic](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/roadmap/active/receipt-logic.md)（回执格式）、[trust-layer](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/roadmap/active/trust-layer.md)（L0–L4 信任轴）。

<a id="1-なぜ別の層が要るか--c-faithful-はプログラムの正しさではない"></a>

## 1. 为什么需要另一层——C-FAITHFUL 不是“程序正确性”

既有证据的范围随 claim 而异。`proofs/receipt.sh` 的 C-FAITHFUL 是明确指定的 RC routine / model 对应关系，并不声称已证明任意完整程序 refine ALS。C-SAFE/C-REPRO 也伴有目标 fixture、decline、trusted boundary。符合功能规格又是另一个问题。

> “sort 实现保持源码语义”与“该 sort 满足排序规格”是两个义务。但这不意味着前者已对任意 sort 证明。

比较表中标为 `負け` 的轴——Dafny/F*/SPARK/Lean 所证明的 `機能仕様`（例如“输出是已排序的排列”）——属于后者，即**程序自身的行为**。它是信任轴之上的另一个问题，既有层无法填补。因此增加新层。

保留的比较标签分别意为“落败”和“功能规格”。

---

<a id="2-この提案で重視するもの"></a>

## 2. 本提案重视什么

与既有形式验证系统竞争表达力或市场排名不是本提案目标。研究的是，在机器生成/修改的运作中，能否以较小负担明确规格来源、验证性质及未验证范围。其他语言或证明系统也可能构建类似运作，因此不以“只有专家能用”“采用率不增长”“这种方式原则上不可用”等对他者的断言作为前提。

---

<a id="3-再定義--機能正しさは証明問題でなく信頼できる仕様の出所問題"></a>

## 3. 重新定义——功能正确性不是“证明问题”，而是“可信规格来源问题”

即使证明 `code ⊨ spec`，信任也只是转移到**“该 spec 是否正确？”**。

- **人类编写规格的世界**：该人类就是信任 oracle，因此成立。
- **机器编写的世界**（= Almide 的世界）：机器所写规格与机器所写代码**仅有同等可信度**。这是同作者问题（§v1-arch 1）。

这里在证明义务之外，明确**从哪里获得规格，以及依据什么采纳它**。这不是 Almide 独有问题，也不是其他验证系统无法处理的问题。本提案考虑两个规格候选来源：

1. **紧邻之前的可信版本**——修改前代码具有“曾作为正确代码运行”的记录，将其作为差分 oracle。
2. **共同生成 + 批准的不对称**——机器提出大量简短性质，人类审查其意义、覆盖和用途适配性并批准。仅仅文字简短，不保证有效性或完整性。

---

<a id="4-着地形--c-faithful-の上に二つの受領書を積む"></a>

## 4. 最终形态——在 C-FAITHFUL 上增加两种回执

考虑复用将 witness 与小型检查器分离的设计。既有 RC 定理不会直接变成功能规格证明；各性质的语义、检查器健全性及与制品的对应关系需要新的依据。证明系统的选择与整个系统的 TB 不同，后者仍有模型、执行、抽取等前提。维持不创造新逻辑的设计方针，但不声称仅靠 Coq 就闭合所有信任。

<a id="c-preserved--差分保存近未来の本丸"></a>

### C-PRESERVED——差分保持（近期主攻目标）

> **主张**：此次修改保持紧邻之前可信版本的**观察契约**（声明的输入输出及 effect 表面）。**规格来源 = 前一版本。**

这是处理相对修改前版本保持观察契约的提案，不是 MSR 测量值本身。前版的运行记录可作为选择比较来源的材料，但不会消除前版 bug、未观察输入或环境差异。对既有代码修改的适用性，应固定 harness 和使用条件后验证。

- 不同于 C-REPRO：C-REPRO 是“同一源码 → 同一字节”（确定性）。C-PRESERVED 是“**不同源码**（修改后）→ 契约上等价”。
- 也不同于编译器回归 oracle（新编译器 ≈ 旧编译器）：那是工具链稳定性，这是**用户程序的修改保持**。层次不同。

<a id="c-asserted--批准性質グリーンフィールド用"></a>

### C-ASSERTED——批准性质（用于新建代码）

> **主张**：程序满足已批准性质集合 Π。Π 属于**可判定片段**，机器发现满足关系，检查器重新核算，**人类仅批准 Π 的文字**。

新代码没有前版，因此提议将批准的性质集作为另一种证据来源。审查负担未必总能限制在三行内，未指定需求不获保证。

| 提议回执 | 规格来源 | 主要用途 | 剩余前提 |
|---|---|---|---|
| **C-PRESERVED** | 紧邻之前的可信版本 | 修改/重构既有代码 | 前版质量、观察契约覆盖、环境识别 |
| **C-ASSERTED** | 共同生成 + 人类批准的简短性质 | 新代码正确性（部分） | 批准性质的有效性、检查器与制品的对应关系 |

<a id="5-設計上の絶対制約自分を縛る"></a>

## 5. 设计上的绝对约束（约束自己）

- **将性质语言限制在可判定/可自动化片段。** 一旦贪求表达力，就必须处理无法自动化的性质。将未证明者标为未主张，并测量该限制的有效性与负担。
- **C-PRESERVED 是“保持”，不是“正确性”。** 前版错误则无价值，对新建代码不起作用。**是必要条件，不是充分条件。**
- **C-ASSERTED 永远无法达到完整性。** 即使证明 `順列 ∧ 整列`，也捕获不了“需要稳定排序”。终点是**“针对批准的 Π 经机器验证”**这一层级。
- **不把三层混为一个“正确性”数字**（严格遵守 done 的 3 层级）。回执必须明确**来自哪个来源的哪个主张**。
- **不让检查器膨胀。** 这些检查器也必须始终比生成容易——过度膨胀的检查器会成为下一个信任问题（与 §v1-arch 9 相同的纪律）。

保留的性质表达式意为“排列 ∧ 已排序”。

---

<a id="6-完全性用途相対で数える"></a>

## 6. 完整性（相对于用途计数）

将 [v1-proof-architecture §7](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/roadmap/active/v1-proof-architecture.md) 的 U 相对完整性再延伸一层：

> **U₃ = 无监督的*修改*运作**：C(U₂) + **C-PRESERVED 覆盖**。在 agent 持续改写生产代码的运作中，每次修改保持观察契约。

**不说**“Almide 证明程序正确性”。仅输出可计数形式：**“对 U₃，n/n 次修改获得了保持回执”**、“此函数**已针对批准的 Π 验证**”。

---

<a id="7-何をしないか"></a>

## 7. 不做什么

- **针对人类规格的功能验证**（Dafny/SPARK 的方法）。改为将规格来源移至机器生成模式（§3）。
- **在 benchmark 上击败 Lean**。那是虚荣。胜利条件不是“表达力最高的证明系统”，而是**“针对机器所写代码，成本最低的可信行为保证”**。
- **高表达力性质逻辑**。限定在可判定片段（§5）。
- **混合 C-PRESERVED 与 C-ASSERTED**。来源不同，信任品质就不同。

<a id="リスク-正直に"></a>

## 风险（坦诚地说）

| 风险 | 性质 | 对策 |
|---|---|---|
| SMT 不完备性侵蚀易写性 | 本层最大的工程风险 | 将性质语言限制为可判定片段。Π 由 LLM 提议，人类只批准。自动满足失败时，诚实地把缺口标为“未主张” |
| C-PRESERVED 的 cold-start | 初版没有前置 oracle | 新建代码仅有 C-ASSERTED + C-FAITHFUL。诚实标出**新代码较弱**的层级，接受修改运作才是强项 |
| 批准疲劳（人类对 Π 只盖章） | 信任依赖批准纪律 | 在 dojo 测量已批准 Π 的覆盖和质量。将“最小声明的纪律”明确写入 §5 约束 |
| “在某轴获胜”变成虚荣 | 战略风险 | 目的是中和弱点（低成本多提供一层功能正确性）。主要胜利仍放在护城河（LLM × 经机器验证的契约） |

---

<a id="一文で"></a>

## 一句话

在机器生成代码验证中，将**相对前版保持观察契约**与**符合人类批准性质**作为不同证据呈现的设计提案。两者都明确规格来源及验证范围，不主张未指定需求、所有程序正确性或相对其他方式的独占优势。
