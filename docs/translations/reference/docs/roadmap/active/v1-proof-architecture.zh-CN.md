<a id="1-なぜこの設計が要るのか"></a>

## 1. 为什么需要此设计

AI 大量快速编写程序的时代，软件瓶颈已**从“能否写出”转为“能否相信”**。代码几乎免费涌现，人类已不可能逐一阅读并确认安全。

此前软件信任靠**“谁写的”**（作者信誉＋人工审查）。但作者变成机器后，信誉无法积累，阅读赶不上编写，出问题也没有可追责对象。**绑定人格的信任无法扩展到机器作者。**

唯一剩下的道路是**验证成果物本身，而非作者**。不是“请相信我”，而是“请自行核查”。Almide v1 把这变成语言与工具链自身的架构。

---

<a id="2-設計の背骨これ一つ"></a>

## 2. 设计的唯一骨架

> **不证明编译器正确；只证明小型检查器健全，让编译器每次构建吐出“证书”，检查器每次对照检查。**

根据是简单的不对称：**构造很难，核查却容易几个数量级**（解数独费力，复核已解数独瞬间可做）。

结果：

- 编译器不论规模，10万行也行，**可以有 bug**。即使输出异常，附带证书不成立，检查器会拒绝。
- 必须证明的只有**检查器健全性**：“**检查器接受，则成果物具有该性质。**”该定理完全不涉及编译器内部，因此10万行可成为**无需信任（untrusted）**。

这从结构上消除了“为证明而把编译器做得完美”的必要。

<a id="3-用語初出で定義"></a>

## 3. 术语（首次出现时定义）

| 词语 | 含义 |
|---|---|
| **ALS**（Almide Language Specification） | 语言的**规范语义**，形式定义“各程序意味着什么”的唯一正典。编译器与参考执行器都须遵循/实现它，而不自行决定语义。 |
| **证书 / witness** | 编译器附于成果物的**机器可复核依据**。以检查器能对照的形式记录“内存全部清理了”“未写入错误位置”等。 |
| **证书格式** | 用于书写 witness 的**刻意极简化语言**。越简单，语义越少歧义，任何人都能写独立读取实现。 |
| **检查器（checker）** | 读取证书、与成果物对照确认成立的小程序（数百至千行）。除检查器外，形式化、执行、提取、硬件等信任边界仍存在。 |
| **refine（精化）** | “忠实实现”的形式版本。“实物 a 精化模型 M”意味着 a 的可观察行为只包括 M 允许的行为。 |
| **可信基（TB, Trusted Base）** | 接受该主张时**决定不加怀疑而信任的事物集合**，越小越好。 |
| **Coq / Rocq** | 编写证明并由**极小核心（kernel）严格复查有无漏洞**的工具。自动化再大，最终也只信任 kernel（收窄信任的机制）。 |
| **CompCert** | **正确性经数学证明的 C 编译器**；本构想考虑的一条验证编译路径示例。 |
| **CertiCoq** | 从 Gallina 出发的验证编译路径候选。本构想中的连接含未实现部分，须明确相关证明前提、提取/执行环境、机器模型与实际硬件边界再评估。 |
| **DO-178C / DO-330** | 航空软件认证规则（178C），以及其中**正式认可工具**的规定（330）。 |
| **Thompson 漏洞** | “若编译器自身被植入背叛，读源码也看不见”的经典问题。验证编译是对策之一，但不自动闭合运行二进制来源、构建环境和下层边界。 |

<a id="4-着地形--完成したアーキテクチャ"></a>

## 4. 最终形态 — 完成的架构

目标是把形式证明检查核心集中为 **Coq kernel**，并不意味着整个系统的可信基只剩它一个。ALS 是否表达意图、模型与成果物对应、提取/执行路径、硬件/OS 等遵循 §5/§8 及当前 `TRUSTED_BASE.md` / `proofs/receipt.sh` 的范围。下图包含未达成项目，是完成形态构想，不是当前已获接受的工具鉴定配置。

```
        ┌────────────── 規範意味論 ALS(Coq 内の形式意味論)──────────────┐
        │   すべてのプログラムの意味は、ここだけが定める                   │
        └───────────────────────────┬───────────────────────────────────┘
                       refine        │        refine
        ┌──────────────┘             │             └──────────────┐
   非信頼コンパイラ          性質 P {メモリ安全・stack 均衡・        参照実行器
   (規模不問・バグ可)        name 全域・capability 上界・型        (ALS の実行像)
        │                    concretize・終端挙動} = ALS に対して定義
        ▼
  ( wasm バイト列 a , 証明書束 c ) ── 継ぎ目は「証明書形式」ただ一つ
        │                            (極限まで単純・意味論を完全文書化)
        ├──► 性質検査器 K   K(c, a) = 受理 ⟹ a は P を全部満たす
        └──► 翻訳検査器 V   V(a, ALS(s)) = 受理 ⟹ a の挙動は ALS(s) を refine
                  │
   K・V は Gallina 関数として書かれ、Coq で健全性を証明され、
   CertiCoq + CompCert で機械語化され、独立 2 実装(うち 1 つは機械語まで検証)が
   一致して初めて通り、DO-330 で資格化される唯一の対象。
```

保留的日文图完整说明：Coq 内形式化的规范 ALS 语义独自决定所有程序含义。无需信任的编译器（任意规模、可含 bug）与参考执行器（ALS 的可执行映像）都精化 ALS。性质 P 包括内存安全、stack 均衡、name 全域、capability 上界、类型 concretize、终端行为，均相对于 ALS 定义。编译器输出 wasm 字节 a 与证书束 c；唯一接缝是极简、语义完全文档化的证书格式。性质检查器 K 的 K(c, a) 接受意味着 a 满足全部 P；翻译检查器 V 的 V(a, ALS(s)) 接受意味着 a 的行为精化 ALS(s)。构想中的 K/V 以 Gallina 函数编写、由 Coq 证明健全性，再由 CertiCoq＋CompCert 编译到机器码；两个独立实现（其中一个验证到机器码）一致才通过，是唯一拟定的 DO-330 工具鉴定对象。这是目标架构，不是这些连接或鉴定已完成的证据。

**编译和签发证书是同一个动作。** 每个分析 pass 的输出就是 witness。编译器只说证书格式，检查器只听证书格式，彼此不知道内部；这就是架构的唯一接缝。

**规范只有 ALS 一点。** 只有 ALS 决定含义。编译器、参考执行器、两个 backend 都是 ALS 的 refinement。因此双 target 字节一致不是事后检查，而是**同一体系自然产生的结果**。

**从一开始承认有两个检查器。**
- 性质检查器 K：通过证书确认成果物 a 满足性质 P。
- 翻译检查器 V：**每次构建**确认输出字节 a 精化 ALS(s)，回答审查者的关键问题：“**证明的是模型，那实际飞行的实物呢？**”

两者都小、都经 Coq 证明、都验证到机器码、都是工具鉴定对象；共享“成果物语义库”，减少重复鉴定。

**WASM 是正典可信成果物。** rustc 只参与一次“构建编译器”，不进入成果物路径（可信基础最小）。可读 Rust → Ferrocene 作为第二鉴定路径，同样是 ALS 的 refinement。

**多样性与审计。** 不同团队、不同语言的两个独立检查器实现必须一致才通过。每次由 gate 确认全部定理所用公理包含在固定标准集合内（Coq `Print Assumptions` ⊆ 标准），不允许任何私自扩大信任的技巧，例如在证明里信任编译器执行。

<a id="5-信頼境界--何を信じ何を信じないか"></a>

## 5. 信任边界 — 信什么，不信什么

| 分类 | 内容 | 正确性 |
|---|---|---|
| **无需信任（untrusted）** | parser、checker、全部 codegen pass、optimizer、wasm emitter（几乎全部代码量） | 不要求，可以有 bug，检查器每次验证输出 |
| **可信（trusted，即鉴定对象）** | 性质检查器 K、翻译检查器 V、证书格式语义 | Coq 健全性证明＋验证到机器码＋两个独立实现一致 |
| **可信基（TB，不质疑）** | Coq kernel / CompCert、CertiCoq 的 TB / 硬件 / **ALS 是否符合意图** | 证明不能消除的底层（§8） |

**设计意图**：以检查器为中心的证据整理评估对象。但 DO-330 工具鉴定范围或整个编译器免于审查，并非此技术设计就能决定；也不声称小检查器已获鉴定。适用范围与接受仍需另行评估。

<a id="6-受領書receipt"></a>

## 6. 收据（Receipt）

原构想用收据整理 C-SAFE / C-REPRO / C-FAITHFUL / C-PROVEN。当前各主张的 fixture、模型、decline、trusted boundary 见 [receipt generator](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/proofs/receipt.sh) 与 [proven versus trusted](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/contracts/proven-vs-trusted.md)。不声称已达成任意 host 字节一致或全部 ALS 语义的 refinement。

当前 `make verify-trust` / `make receipt` 在声明范围内重新导出列出的检查/证据，不是验证外部测量或未实现构想的万能 `make verify`。本地复查减少只依靠 CI，但不消除模型、执行、工具链等信任边界。

<a id="7-完全性の定義使用目的に相対化して閉じる"></a>

## 7. 完整性的定义（相对于使用目的闭合）

“完整覆盖绝对语义”会膨胀到 CompCert 规模，因此不追求。改为：

> **完整性(U)** = 已列举使用目的 U 所需主张集合 C(U)，每个主张有检查器，全部 TB 落在公理集合内的状态。

- **U₁＝sandbox 内 agent 执行**：C(U₁)＝{ capability 上界、错误时终端行为、确定性、可复现性 }，主要由 C-SAFE/C-REPRO 构成。
- **U₂＝无人监督的生产运行**：C(U₁)＋C-FAITHFUL 覆盖。

收据明确**证明了哪个用途**。不说“Almide 完整”，而用可计数形式：“**对 U₁ 完整，对 U₂ 为 n/n**”。

<a id="8-消えない底ラベルに刻む"></a>

## 8. 无法消除的底层（刻入标签）

任何验证体系都留下、证明不能消除的可信基：

- **Coq kernel**（小，受全球审视，信任它是标准做法）。
- **CompCert / CertiCoq 自身的 TB**。
- **硬件 / OS**。
- **ALS 是否符合我们的意图**——唯独这无法证明，只能通过参考执行器、每日 MSR 测量、实际使用，**经验性地确认**。

**在已知限制文档明确写出这四项，才有资格把其余全部称作“已证明”**。比“全部完美”更有力的审查表达是划线：“这里之前已证明，这里之后请信任”。

---

<a id="9-何をしないか"></a>

## 9. 不做什么

- **证明整个编译器**（CompCert 级完整证明），而是收敛为检查器健全性＋每次构建证书。
- **完全覆盖绝对语义**，完整性相对于使用目的（§7）。
- **自创新逻辑**。逻辑要求累积审视，因此借用 Coq。可以自定义的是证书格式、检查器、检查器的独立实现，而非逻辑。
- **日常并用两套逻辑**。原构想把常用证明系统集中到 Coq；只有一套证明系统不等于全系统 TB 只剩 kernel。
- **隐藏公理**。TB 不隐藏，记入台账（§8）。
- **检查器膨胀**。检查须持续比生成容易，过大的检查器本身会成为下一个信任问题；以简单性与多样性防护。

---

<a id="10-v0-から-v1-へ運ぶもの--捨てるもの"></a>

## 10. 从 v0 带到 v1 的东西与舍弃的东西

- **舍弃**：编译器实现代码，即向 phase 结构事后附加证明的 v0 主体。
- **带走**：**知识**。spec corpus、oracle registry、12次 release 发现的已知 edge case（#484 级）从第一天就复用为 v1 编译器的**差分测试/fuzz oracle**。**编译器可以重建，知识不重建。**

---

<a id="一文で"></a>

## 一句话

本构想旨在扩展可独立检查成果物与证据的范围，缩小必须信任的编译器本体面积。连接 K/V/ALS 的未实现部分、模型有效性、提取/执行环境、硬件等信任仍存在。不是已达成的“一个检查器成为全部可信基”或“全部代码自动无需信任”主张。
