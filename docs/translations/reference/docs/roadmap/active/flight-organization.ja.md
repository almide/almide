<a id="b--organization"></a>

## B — 組織

<a id="b1-a-legal-entity-able-to-sign-dossiers-and-carry-liability--"></a>

### B1. dossier に署名し責任を負える法人 ❌
*（旧 #577）*

認証当局や主契約企業は、リポジトリでなく法人と契約する。監査への回答、責任、dossier の署名には法人が必要だ。エージェント支援の作業は証拠を作れるが、署名できるのは法人だけである。Ferrocene と AdaCore が企業として存在するのは、まさにこのためだ。

**内容**：法人形態と法域を決める。法人が保証するもの（dossier ごとのツールチェーン挙動）と、オープンソースのままとするものを定める。

**完了条件**：リリース dossier に署名し、サポート契約を結べる法人が存在する。

<a id="b2-a-multi-decade-lts-policy-and-versioning-commitment--"></a>

### B2. 数十年単位の LTS 方針とバージョニングの約束 ❌
*（旧 #578）*

航空機プログラムはツールチェーンより長く続く。採用者には、固定したツールチェーン版への修正をどれだけ続けるか、Known Problems をどう通知するか、アップグレードをどう適格性確認するかについて、文書による約束が必要だ。

**内容**：LTS 方針書 — 適格性確認済みリリースごとのサポート期間、バックポート規則、安定性契約と整合した廃止規則、Known Problems 通知経路。

**完了条件**：公開された LTS 方針が dossier から参照されている。

<a id="b3-certification-authority-relationships-der--notified-body-engagement--"></a>

### B3. 認証当局との関係（DER／通知機関との折衝）❌
*（旧 #579）*

適格性確認は提出するだけでなく、協議するものだ。指定技術代表者／通知機関と早期に関わることで、大量に証拠を作る*前に*何が証拠として認められるかが決まる。

**内容**：最初の対象制度を特定する（おそらく最初の顧客の制度：民間航空電子機器より前に宇宙機関のソフトウェア規格か UAS 当局）。経験あるコンサルタント／DER に dossier に対するギャップ評価を依頼する。

**完了条件**：ツールの適格性確認を経験した人による、書面のギャップ評価。

<a id="b4-qualification-engineering-beyond-the-solo-plus-agents-model--"></a>

### B4. 一人＋エージェント体制を超えた適格性確認エンジニアリング ❌
*（旧 #580）*

適格性確認には人間を省けない部分がある。監査面談、署名付きレビュー、責任を負う判断である。現在の体制（人間一人＋エージェント群）は異例の速度で証拠を作るが、それだけでは検証独立性への期待を満たせない。

**内容**：最小チームを定める — 少なくともツール適格性確認の経験者一人と、独立検証の役割。誰が何を検証し、エージェントの出力を何と位置づけるか、独立性の説明を文書化する。

**完了条件**：最初の適格性確認の試みに向けて、検証独立性の体制が文書化され、人員が配置されている。

<a id="b5-funding-the-climb-from-trust-market-revenue--"></a>

### B5. 信頼市場の収益で段階を上がる資金を賄う ◑
*（旧 #581 — trust-layer ロードマップに戦略がある）*

適格性確認は複数年に及ぶコストセンターである。エージェント／wasm サンドボックスの信頼市場は、その費用を賄う収益・証拠のエンジンだ。同じ証拠の仕組みで、より早い段階の買い手を得る。規制対象の目標への回り道ではなく、その資金調達経路である。

**内容**：trust-layer の収益化（receipts、capability containment、MCP を入口とする戦略）を順序立て、製品の副産物として dossier 級の証拠が蓄積するようにする。適格性確認の予算を明示的に確保する。

**完了条件**：適格性確認のマイルストーン（B1–B4 と #574 のデータパッケージ）に収益源がある、資金の裏付けられた計画。

**参照**：[trust-layer.md](../../../../../roadmap/active/trust-layer.md)

## C — 実績

<a id="c1-the-first-regulated-adjacent-deployment-to-start-the-service-history-clock--"></a>

### C1. 最初の規制分野に近い導入で、稼働履歴の時計を動かす ❌
*（旧 #582）*

製品の稼働履歴そのものが認証で価値を持ち、実際の導入でしか蓄積されない。小型衛星の飛行ソフトウェアや UAS（特定カテゴリー）は、民間航空電子機器より参入障壁が大幅に低く、必要とする種類の運用記録を生む。

**内容**：宇宙または UAS の場で Almide 生成コードを飛行運用する設計パートナーを一社見つけて獲得する（Critical profile が利用可能になったら使う）。初日から問題報告の仕組みを組み込む。

**完了条件**：配備済みの宇宙／UAS システムで Almide コードが動き、稼働履歴が記録されている。

<a id="c2-the-deployment-ladder--"></a>

### C2. 導入の段階 ❌
*（旧 #583）*

飛行制御から始める人はいない。段階は、地上／検証ツール（その市場も規制対象だが、より近い）→ 宇宙／UAS 項目 → 低保証水準の航空搭載品（DAL-D/C クラス）→ より高い水準。各段階が、次のための顧客・証拠・履歴を生む。

**内容**：段階を継続更新する文書として書く。段階ごとの対象制度、各段階が必要とする証拠と生む証拠、段階を上がる基準を記す。

**完了条件**：現在の段階を明記した文書が `docs/roadmap/` にある。

<a id="c3-service-history-and-problem-reporting-record-keeping--"></a>

### C3. 稼働履歴と問題報告の記録管理 ❌
*（旧 #584 — C1 に依存）*

稼働履歴が認められるには、監査に対応できる方法で記録しなければならない。稼働中の版、曝露時間、発見した問題、処置、Known Problems へのフィードバックである。

**内容**：リリース dossier と flagged-contracts 台帳に紐づく、軽量な運用中記録形式。C1 以降のすべての導入がこの形式で報告する。

**完了条件**：記録管理形式を定義し、最初の導入で使用している。

<a id="c4-a-published-position-on-certifying-machine-written-code--"></a>

### C4. 機械が書いたコードの認証に関する見解の公開 ❌
*（旧 #585）*

保証の枠組みは人間の著者を前提とする。規制当局（EASA の AI ロードマップ、FAA の対応する取り組み）は、AI 支援開発の意味を積極的に検討している。機械が書くことを最初から前提とし、機械的証拠を備えるツールチェーンは、相手側がまだ持っていない答えである。早くから議論に参加することが、新参者を単に許容される立場ではなく選ばれる立場にする。

**内容**：見解文書 — 著者がモデルである場合に、仕様キー付き契約、ビルドごとの証明書、証拠の段階が、開発保証の期待をどう満たすか。関連ワーキンググループとも関わる。

**完了条件**：文書を公開し、少なくとも一回、規制当局／業界ワーキンググループとのやり取りを記録する。
