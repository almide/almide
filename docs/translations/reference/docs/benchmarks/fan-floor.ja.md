## プローブ

各プログラムは `work(s, i, iters)` を計算する。`acc = (acc * 31 + j) % 1000003` を `iters` ステップ実行する。10 要素の offer 単位で動作し、各 offer の結果が次の初期値になるため、offer 同士は重ならない。これらのマシンでは、1 要素の 1 反復は約 4–5 ns（iters 1000 ≈ 4–5 µs）。

| プローブ | 1 回の offer | 測定方法 |
|---|---|---|
| `sweep` | 10 要素の並列 map 1 回 | t(1010 offers) − t(10 offers)、offer あたり |
| `nest` | 要素自体が 10 要素の並列 map である、4 要素の並列 map | t(210) − t(10)、外側の offer あたり |
| `busy` | 独立した 2 つのレーンを同時に動かし、それぞれが 10 要素 map の列を実行（Almide: 2 つの `fan { }` 分岐） | t(510) − t(10)、offer のペアあたり |

2 回の実行の差分により、プロセス起動と、wasm ではコンパイルも相殺する。各値は 7 回の実行の最小値であり、各反復ではすべての実装を順番に実行して、同じマシン状態を経験させる。すべての行で、すべての実装が同じ結果を出力した。

実装:

| 列 | 内容 |
|---|---|
| Almide native | `almide build --release`、デフォルト（コストモデルが offer ごとに逐次／並列を選択） |
| native seq | 同じバイナリに `ALMIDE_FAN_SEQUENTIAL=1` を設定。2 つの `fan { }` 分岐は依然として同時実行されるため、`busy` の seq は 1 レーンの時間 |
| Almide wasm | `almide run --target wasm`、デフォルト。参考値のみ: wasm プログラムであり、比較実装はネイティブコードなので、それらとの順位付けはしない |
| Rayon | Rust 1.x + `rayon` 1.10.0: `into_par_iter().map().collect()`、ネストした par_iter、レーンには `rayon::join` |

## 読み解き

- **`busy` の差が最大: 1000 反復で 4.0x（Intel）、5.1x（AMD）**。そこで Almide は自身の逐次モード（39.6 / 50.6 µs）より遅い。各レーンの offer は `fan { }` 分岐のスレッドから来る。常駐ワーカー群を確保できるのは一度に 1 つの offer のみだった（list.rs の `almide_fan_run_tasks`）ため、もう一方のレーンは offer ごとにワーカーごとのスレッドを生成していた。これを次に修正した。下の**変更後**を参照。
- 次は `nest` の 4.2x / 3.3x。外側の map は effect コールバックを持ち（`fan { }` を呼ぶ）、effect の `fan.map` は要素を順に実行する（#2594）。そのため並列なのは内側の map だけで、4 × 10 要素は 10 要素 offer 4 回として動く。これはランタイムではなく言語表面の変更である。
- `sweep` は 10000 反復以上で最速の 1.3x 以内。1000 では 1.7–2.2x の差があり、この領域では Rayon のワークスティーリング join の方が、Almide の配分とコストモデルによる 5 ワーカーの選択より低コストである。
- Zig 0.13 の `std.Thread.Pool` はここで offer あたり 110–350 µs かかり、最速になることはない。
- 反復数が多いと Go の逐次ループが他より約 10% 速い。これは並列ランタイムではなくコード生成であり、10000 以上で Go が最速となる理由である。

## 変更後: 1 つの共有プール、呼び出し元もブロックを取得（2026-10-16）

## 逐次ループ: リテラルによる剰余（2026-10-17）

10000 反復以上では最速列は Go だった。Go の逐次ループが Rust と Almide より約 10% 速いためである（並列ランタイムはどれも 10 要素を 8 スレッドへ同じように分割するので、ループがその行を決める）。ループは `acc = (acc * 31 + j) % 1000003`。反復ごとに 1 本の依存連鎖があり、レイテンシに律速される。Almide の連鎖を長くしていた要因は 2 つ:

- rustc は定数による `checked_rem` をマジックナンバーの乗算へ低水準化するが、その符号補正が連鎖上に置かれる（商の推定値をシフトし、符号ビットを加え、掛け戻す）。さらにループを展開すると、帰納変数のオフセット（`j + 1`、`j + 2`）も連鎖上に置く。
- ネイティブビルドのデフォルト `x86-64-v3` では、Rust で書いた i128 乗算が、符号付き 1 オペランド `imul` ではなく、符号なし `mulx` と符号補正になる。

`Int` の `x % <literal>`（除数が 3 以上で 2 の累乗でない）は、現在 `almide_rem_const::<D>(x)` として出力される（crates/almide-codegen/src/prelude_rem.rs）。同じ切り捨て剰余で、符号付き `imul` 上のマジック乗算から商を求め、被除数の符号による符号補正を乗算の脇で剰余に適用する。3 以上のリテラル除数は 0 でも -1 でもないため、この呼び出しは中断し得ない。そうしたリテラルによる `%` も元々中断しなかった。90M ステップの連鎖（`x86-64-v3`、各 2 回）は Intel VM で 290-292 ms（rustc は 364-372 ms、Go は 310 ms）、AMD VM で 370-371 ms（454-457 ms、400-420 ms）だった。剰余は、17 個の除数について 60,000 個の被除数、および 2000 未満の各除数の倍数で `%` と照合している（`prelude_rem.rs` テスト）。

## プール: ポーリングスレッドへの offer 公開、スティーリング、コストモデルの再較正（2026-10-17）

ループが Go と同等以上に速くなったため、各差の残りは並列ランタイムだった。offer は各アイドルプールスレッドの専用チャネルを通じて呼び出しを渡し、スレッドは offer の間にスリープしていた。そのため offer ごとにカーネルの起床経路（これらの VM で 5-20 µs）のコストを払った。各ワーカーはスレッド CPU クロックも 3 回読んだ（システムコール。AMD VM では約 1.1 µs）。ブロックは mutex から取り、サイト履歴も mutex で保護された map だった。さらに別の offer の要素内で作られた offer は、スレッドがすでに確保済みなので呼び出し元だけで動いた。現在は（runtime/rs/src/list.rs）:

- **投稿ではなく公開。** offer は 64 スロット（`ALMIDE_FAN_SLOTS`）の 1 つで公開される。プールスレッドは offer の後、park する前に `ALMIDE_FAN_SPIN`（50 µs）の間ポーリングし、ブロックが残る任意の公開 offer からブロックを取る。offer が park 済みスレッドを起こすのは、ポーリング中の数が希望数より少ないときだけ。ポーリングスレッドは、ブロックが残る公開 offer の数という 1 つのカウンター（`ALMIDE_FAN_OPEN_BLOCKS`）を読み、それが非ゼロになるまで他には触れない。最後のブロックの配分後に入ったスレッドは要素の後処理をせずに退出し、呼び出し元ハンドルは呼び出し元がスリープし得る段階になって初めて clone する。ゲートは呼び出し元のフレーム内にあり、ブロックはアトミックカウンターで、引き続きリスト順に配分する（ADR-0024 D6 のトラップ待機はこれに依存する）。
- **コアごとに 1 スレッド。** プールスレッドが offer に入るのは、offer を処理中のスレッド数がコア数より少ない間だけ（`ALMIDE_FAN_RUNNING`）で、そうでなければコアを譲る。2 つの `fan { }` 分岐がそれぞれ 7 スレッドへ配分すると、8 コアに 9 スレッドを載せていた（busy、10000 反復: Intel VM で Go の 1.33x）。
- **待機中の呼び出し元は自身の木の中でスティーリングする。** 自身のブロックが取得された後、呼び出し元は同じ最外 offer（`AlmideFanGate::root`）のブロック内で作られた offer からブロックを取り、別の分岐からは取らない。別の分岐の要素を取ると、この分岐の次の offer が最大 1 要素分遅れた（busy 10000: ペアあたり 95 に対して 108 µs）。何も取らないと、各外側 offer の末尾で 1 コアが遊んだ（nest 10000: 187 に対して 220）。
- **コストモデルを再較正。** 10 個の空要素の強制並列 offer は、W=8 で現在 2.4 µs（Intel）、3.1 µs（AMD）。以前は 8.2、24.1 µs（上の表）、Go は 3.0、7.3 µs。`native_offer_ns` / `native_worker_ns` は現在 1.5 + 0.7W µs で、新しい較正行の包絡となる（fan-cost-model.txt）。並列 offer は 8 回に 1 回計時する（`ALMIDE_FAN_RESAMPLE_PAR`）。計時区間ごとにクロック読み取り分を差し引き、切り替え点の 2x 以内にある並列 offer 由来の推定値は 1 回の逐次 offer で確認する。逐次サイトが並列になるのは 2 回連続の測定後だけ。サイト履歴はロックフリーテーブルになった。

## nest: fan-out のみを行う effect コールバック（2026-10-17、#2594）

`nest` の外側の `fan.map(list.range(0, 4), (q) => inner(s0 + q, iters))` は 4 要素を順に実行していた。`inner` は `effect fn` であり、effect コールバックでは効果をリスト順に保つため、逐次の `fan.map` を維持していた。しかし `inner` の唯一の効果は、純粋な `work` に対する自身の `fan { list.map(…) }` である。fan の観測はその逐次評価と同じであり（ADR-0024 D1）、出力は要素ごとのタイムラインを通る（D5）。そのため、証明済みの作業上で fan-out するだけの要素は、他の要素に自身の順序を観測させることができない。

純粋性解析の fan 用ビュー（crates/almide-codegen/src/pass_stream_fusion.rs の `Purity::for_fan`）は現在、本体が証明済み関数、ネストした `fan { }` ブロック、証明済みコールバックを伴う `fan.*` 呼び出し、および `!` にしか到達しない `effect fn` を受け入れる。fan のルーティング（pass_rust_lowering_fan.rs）は、そのような関数を effect ではないものとして扱う。直接または別の関数経由の効果モジュール呼び出し（tests/fan_nested_effect_parallel_test.rs の `env.sleep_ms`）があれば、依然としてコールバックを逐次に保つため、I/O の順序は変わらない。テストは生成 Rust の両ルーティングを固定し、並列出力が逐次実行および wasm とバイト単位で同一であることを検査する。

### 読み解き

- 最速が 1 µs 以上である**すべての行で Almide native は最速以下**: Intel VM で 0.48-0.92x、AMD で 0.47-0.85x（sweep 0.48-0.91x / 0.47-0.85x、nest 0.54-0.90x / 0.66-0.85x、busy 0.53-0.92x / 0.50-0.78x）。2026-10-16 の表では該当する 24 行中 22 行が 1.06-5.05x だった。
- 1.00 に最も近いのは比較ランタイムが最も得意な行: 10000 反復の `busy` における Go の goroutine（Intel で 0.92x）、`sweep` 100 における Go の逐次ループ（Intel で 0.91x、offer は逐次のまま）、そして作業量が大きい行。そこではすべてのランタイムが 10 要素を 8 スレッドに同様に分け、ループが決定要因となる（Intel の sweep 30000 は 0.90x）。
- 空の強制並列 sweep offer は Almide で 2.55 / 2.47 µs（Intel / AMD）、Go で 3.14 / 6.23、Rayon で 8.95 / 18.75。300–3000 反復では、このコストが offer の大部分を占め、Almide は最速の 0.47-0.65x。
- wasm 列は参考値（比較実装はネイティブコード）。今回の実行では AMD VM 上でノイズが多かった（nest 100 で 205.8 µs）。develop の wasm とこのツリーの wasm を交互実行すると、nest 1000 で 371 と 455 µs、nest 0 と 100 ではゼロ未満だった。これらの変更が触れるのはネイティブ側だけ。

残るもの: `fan { }` 分岐と並列 offer が順に動く wasm 側（ADR-0024 D8）、および今回の変更で認めない effect コールバック。I/O に到達するコールバックは引き続きリスト順に実行する。ADR-0024 D3 では、順序付き操作に到達しない限り並行実行するとしており、これには `@ordered` 集合が必要。

## 幅広い形状とチューニング済み比較実装（2026-10-17、Almide develop、0746eb689 時点）

Goal-5 の拡張: 以前のプローブは、同じ大きさの要素を最大 10 個 offer する。これらの行は、n を 10 から 10⁶ として **n 要素に対して 1 回の `fan.map`** を実行し、さらに 4 つの作業形状を用いる:

| 形状 | 要素の作業 |
|---|---|
| size | 下限測定の `work(s, i, iters)` ループ |
| skew | 10 要素ごとに 1 要素が 20× の作業を行う |
| heap | 各要素が 20 部分からなる `String` を構築し、その長さを返す。ループなし |
| fail | 97 要素に 1 要素が `err("bad i")` を返す |

各実装はすべての要素を実行し、最小インデックスのエラーを保持する。Almide の `fan.map` の規則である。すべて同じ作業と全 8 スレッドを共有し、すべての行で各実装が同じチェックサムを出力した。

比較実装はそれぞれチューニング済み:

| 言語 | 派生版 |
|---|---|
| Rust（Rayon 1.10.0） | `rayon`: `into_par_iter().map().collect()` · `tuned`: 同じものに `with_min_len(n / (4·threads))` を設定 · `scope`: 静的チャンクに対してスレッドごとに 1 つの `rayon::scope` タスク |
| Go 1.22 | `par`: 要素ごとに goroutine · `pool`: map ごとに起こされる常駐ワーカーが、アトミックカウンターから n/(4W) のチャンクを取得 · `errgroup`: `golang.org/x/sync` v0.8.0 と `SetLimit(W)`、インデックスごとのエラースロット、コンテキストキャンセルなし |
| Zig 0.13.0 | `std`: `std.Thread.Pool`、n/(4W) のチャンクごとに 1 回の `spawnWg`、呼び出し元も手伝う · `hand`: W−1 個の常駐スレッドと呼び出し元、futex 世代とアトミックチャンクカウンター |

**再現:**

```bash
cd research/benchmark/fan-floor/wide && ./build.sh && ALMIDE=almide python3 wide.py
```

これにより、map あたりの µs（7 回の最小値、実装を交互実行）、最大 RSS（GNU time）、起動時間が得られる。ソースは `wide/`。`al-n` はコンパイルされたままのネイティブ Almide、`al-seq` は同じバイナリに `ALMIDE_FAN_SEQUENTIAL=1` を設定したもの、`al-w` は `almide run --target wasm` であり逐次。「best」は各言語の最速並列派生版で、括弧内に名前を示す。**al-n / best** はそれらすべての最速に対する比で、1.00 未満なら Almide の勝ち。

### Almide が負ける箇所とその理由

| # | 行 | 比（Intel / AMD） | 原因 | 優先度 |
|---|---|---|---|---|
| W1 | size iters 100、n ≥ 100。heap | 5.7–11.4 / 2.1–5.5。Intel では `al-n` が **`al-seq` より遅い**（n = 10⁶ で 522 ms 対 312 ms） | `almide_rt_fan_map_par` は**要素ごと**に出力タイムラインを開く。`almide_fan_enter` は `Arc` を clone してスレッドローカルを交換し、その drop はグループ mutex を取り、stdout をフラッシュし、`notify_all` を呼ぶ（`runtime/rs/src/fan.rs:101`、`crates/almide-codegen/src/prelude_fan.rs:64-90`）。≤ 1 µs の要素は、ロック競合と futex 起床でこのコストを払う。ローカルでは、同じプログラムが逐次の 1.0 s に対し、sys 時間を 18 s 費やす。`almide_fan_group` は要素ごとにバッファも 1 つ確保する（`prelude_fan.rs:61`）。これが n = 10⁶ で RSS 17 MB に対し 65 MB となる理由。 | **P-high**（#3784）: 最も一般的な `fan.map` の形であり、高速化を逆転させる |

| W4 | 全行、`al-w` | 1.2–1.3× `al-n-seq` | wasm は `fan.map` を逐次実行する（ADR-0024 D8）。リグレッションではない | #1628 / #3331 で追跡 |

要素の作業が支配的な箇所（iters 10000、skew、AMD の fail）では Almide は勝つか同等で、最良のチューニング済み比較実装に対して 0.69–1.07。Rayon の `with_min_len` と静的な `scope` が単純な `rayon` に勝つのは小さな offer だけ。n = 10⁴ を超えると、Go の常駐プールが最強の比較実装となる。`SetLimit` 付きの `errgroup` はどこでも最も遅い並列派生版であり、要素ごとにセマフォを通して goroutine を作る。W1 は別の目標で、この目標の内容はそれを変更しない。
