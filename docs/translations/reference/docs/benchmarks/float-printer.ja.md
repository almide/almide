これがその測定である。日付：2026-09-08、develop の `8517914d8`（almide 0.62.0）、構造化側、`almide build --target wasm`（出荷される WASI 形式、wasm-opt なし）。

<a id="why-the-table-free-schubfach-is-the-smallest-exact-printer"></a>

## 表なし Schubfach が最小の正確なプリンターである理由

最短ラウンドトリップアルゴリズムはすべて、コードと 10 の累乗表とのトレードオフである。

- **Dragon4**：表なし、大きいコード（多倍長整数の桁ループが大半）。
- **Ryū / Schubfach**：小さいコード、617 要素 × 128-bit の表（生データで 9.9 KB）。この側ではリテラル `List[Int]` は要素あたり約 17 B、文字列リテラルは 1 byte あたり 1 B を要するので、全表はどう符号化しても 12–21 KB、全体の測定値は 24,372 B になる。issue の予測（「10 KB の表は 6.4 KB のコードより悪い」）は正しい。
- **コンパクト表**：8 個ごとの要素に十分なガードビット（189）を持たせ、10^0..10^7 による再スケーリングで 617 個の正確な要素すべてを再現する（オフライン検証済み）。データは生で 1.9 KB、リテラルで 4 KB に減るが、なお Dragon4 を 760 B *上回る*。
- **実行時に導出する表**：g(k) = ⌊10^k · 2^-r⌋ + 1 自体が小さい正確な計算である。k ≥ 0 では u32 limb 上で ×10^9 をまとめて行い P = 10^k とし、g − 1 は P の上位 126 bits となる。k < 0 では P = 2^N を 10^-k で、÷10^9 に分割して割る。整数では `⌊⌊x/a⌋/b⌋ = ⌊x/(ab)⌋` なので分割除算は正確で、g − 1 の 126 bits がちょうど残る。必要なのは小整数乗算ループ 1 個、小整数除算ループ 1 個、2 の累乗の設定とビット抽出である。10 KB のデータの代わりに約 1 KB のコードとなり、桁ループがなくなるため Dragon4 より 13× 高速になる（値ごとに 64×64 積 3 回と比較数回）。
- **Grisu3** は正確性を確定できない約 0.5 % の入力にフォールバックを要する。フォールバックは Dragon4 またはこの Schubfach のような完全な正確なプリンターでなければならず、Grisu3 はバイト数を厳密に追加するだけで、速度狙いにしかならない。構築しなかった。サイズについての問いは上の行ですでに決着しており、wasm 上で 1 µs/変換なら速度の問いも未解決ではないためである。

`format!` とのバイト一致には Giulietti の Java から 2 点の変更が必要だった。どちらも読解ではなく境界集合で見つかった。

1. **同距離なら偶数ではなく絶対値を切り上げる。** 最も近い 2 候補が等距離のとき（1669760939663944.25 — ...4.2 と ...4.3 の両方がラウンドトリップする）、Rust の Dragon4（`2R >= S`）は ...4.3 を選び、Java は偶数の ...4.2 を選ぶ。
2. **より短い 10 の倍数の候補は s ≥ 100 ではなく s ≥ 10 から試す。** Java は少なくとも 2 桁を印字するため、1 桁の結果は不要である。`format!` は 20 · 2^-1074 に `1e-322` を印字する（s = 98、100 は丸め区間に入る）。同様に Java の `C_TINY` 分岐（MIN_VALUE を `4.9E-324` と印字）はない。`format!` は `5e-324` と印字する。

<a id="recommendation"></a>

## 推奨

表なし Schubfach を出荷し（この PR で実施済み）、float 1 個を印字するプログラムの新しい下限を 5.5 KB、そのうち約 4.2 KB をプリンターとみなす。残る手段はアルゴリズムではなく到達可能性である。float の `${x}` は最短ラウンドトリップ経路全体を引き込む。整数値の float だけ、または固定精度だけを印字するプログラムなら、はるかに小さいフォーマッターに到達できるかもしれない。#1712/#1962 の必要に応じて分割する規律を stdlib の一群に適用することで、issue #1985 の選択肢 3 に相当し、未解決として残す。

## 追記 (#2099, 2026-09-24)：正確なスケーリング上の to_fixed、両形式に 1 つのプリンター

develop の `c653598ee`（#2368 による重複文字列定数の除去後）で再測定した。`println("${1.25}")` は 5,405 B、Int の対照は 1,970 B で、最短プリンターの分は 3,435 B だった。`println(float.to_fixed(1.25, 2))` は 6,650 B。保持した Dragon4 固定桁経路は 4,680 B と最短プリンターより大きく、実際に `spectralnorm`（サイズ階梯の T2 段）が呼ぶのはこちらである。変更したが出力は不変：

- `__sf_scale(x, q, k)` は多倍長整数上で floor(x · 2^q · 10^-k) を正確に計算する。x をシフトまたは 10^-k 倍し、10^9 の塊で 10^k により除算するか右シフトして、剰余から sticky bit を読み取る。約 250 B である。
- `float.to_fixed(x, nd)` は M = floor(2 · v · 10^nd) のためにこれを 1 回呼ぶ。N = M >> 1、落としたビットが半分を表し、sticky bit または N の最下位ビットがセットなら切り上げる（同距離は偶数へ）。そして 10^9 による除算を繰り返して N の各桁を得る。Dragon4 固定モードの桁ループ、すなわち桁ごとの多倍長整数比較減算、多倍長整数 5 個、`math.log10` の推定と補正はなくなった。
- `float.to_string_compound`（`${x}` 形式）は `dot0` フラグ付きの同じプリンターであり、`to_string` の結果を再レンダリングして `.0` を落とす別モジュールではない。ゼロは 4 つの文字列リテラルではなく同じ writer を通してレンダリングするため、プリンターに含まれるリテラルは `NaN` / `inf` / `-inf` だけになる（リテラルは静的プールをずらし、それに伴い float を印字する全プログラムの確保台帳の全行もずれる）。
- `__sf_wd` は数字、ゼロ、小数点を逆向きの 1 パスで結果文字列へ直接書く。桁バッファ、コピー、3 通りのレンダラーはない。桁の供給元を使い切ると、除算なしでゼロを書く（巨大・微小な値は大半がゼロ）。
- `float.to_string` は上記の実行時 g(k) の Schubfach コアを保持する。その 3 つの数も `__sf_scale` で計算する方式（各々 1 つの正確な多倍長整数パイプライン）を試した。さらに約 400 B 減るが、wasm の `float.to_string` が 3× 遅くなる（値あたり 0.95 → 2.9 µs）。このために最短印字を 3× 遅くする主流のプリンターはない。最短プリンターのサイズはコンパクト表の後続作業の担当である。

変更の正確性の証拠：`tests/float_to_string_cross_target_test.rs` は全バイアス付き指数 × 仮数 7 種 × 両符号（28,672 値）の各値の全 3 形式、履歴にある十進特殊事例、1074 / 1100 / 1200 / 4096 桁の `to_fixed`、100,000 個の xorshift64 ビットパターン（ローカルでは 1,000,000）を wasm 側で印字し、Rust `format!` とバイト単位で比較する。意図的に壊したガード（Java の規則 `s >= 100`：最初の不一致は 100,521 行目）では失敗し、このプリンターでは通る。正確なスケーリングへの書換えにあった 2 つのバグ（整数値の末尾ゼロが左側に出る、固定桁値の 9 桁の塊を誤った順序に書く）を見つけたのは、ランダムストリームではなく指数の全走査である。

## 追記 (#2099, 2026-09-24)：`float.to_string` がコンパクト表から g(j) を読む

実行時の g(j) 導出（値ごとに多倍長整数で 10 の累乗を計算）が `float.to_string` の時間の大半を占めていた。現在はコンパクト表から読む。この形は wasm を意識した正しいプリンターが皆使うもので、Swift の `FloatingPointToString.swift`、Wado の `fpfmt.wado`、Ryu / Zig の小さい表に見られる。

- **表。** 127-bit の C(b) = floor(5^b · 2^-s) を 27 乗ごとに格納する（b = −297 … 324、24 要素）。g(j) = floor(C(b) · 5^(j−b) / 2^u) + d(j) + 1：
  - 既存の 64×64 上位積ヘルパーによる 127×63-bit 積 1 回。
  - 正確な 5^f を最大 26 回の乗算で計算。
  - j ごとに補正ビット d(j) ∈ {0, 1} を 1 個格納する。C の切捨てを補う。C は保持する 126 bits より 1 bit 多いため、1 bit で足りる。
- **出力が変わり得ない理由。** 結果はプリンターが要求し得る全 617 個の j について論文の正確な g(j) なので、候補選択に渡る値はビット単位で同一である。
- **表の配置。** 表の各 byte は 7 bits を持つので、552-byte の表は通常の文字列リテラルである。コード中の i64 定数ではなくデータセグメントに置かれる。本書の初回で試したコンパクト表は `Int` リテラル 234 個で、+760 B を要した。
- **なくなったもの。** `to_string` は作業ブロックを確保しなくなった。`to_string` / `${x}` だけで float を印字するプログラムは、多倍長整数ヘルパーをリンクしなくなった。

develop `547b0fdaf` と比較測定（`almide build --target wasm`）：

| プログラム | develop | この変更 | Δ |
|---|---:|---:|---:|
| `println(float.to_string(1.25))` | 4,886 | 4,596 | −290 |
| `println("${1.25}")` | 5,405 | 4,800 | −605 (−11.2 %) |
| `println(float.to_fixed(1.25, 2))` | 6,650 | 4,529 | −2,121 |
| `spec/wasm_cross/edge_float_formatting.almd`（両プリンター） | 16,700 | 14,448 | −2,252 |
| `spec/wasm_cross/float_shortest_roundtrip.almd` | 5,096 | 4,806 | −290 |

両プリンターを呼ぶプログラムは、表と `to_fixed` が必要とする多倍長整数ヘルパーを持つ。この直前の段階に比べて、そうしたプログラムは約 540 B 増える（2 fixtures）。それ以外の float 印字 fixture はすべて縮小する。

確保量の最大到達点の台帳は静的プールも数えるので、float を印字するプログラムごとに表の分、約 0.5 KB 行の値が増える。確保自体は減少する。回数台帳では変わった行はすべて減り、`to_string` 呼出しごとに `alloc_list` が 1 回減る。

wasm 実行時間、`almide bench --target wasm`、シード付き xorshift64 ストリームの 200,000 変換、負荷のあるマシン（load ≈ 18）で develop build と交互実行：

| build | 中央値 | 最小 |
|---|---:|---:|
| develop | 246–349 ms | 218–220 ms |
| この変更 | 72–102 ms | 66–83 ms |

同じマシンの同じ時点で約 3× である。静かなマシンでの develop は 145 ms（値あたり 0.73 µs）なので、この変更は値あたり約 0.25 µs となる。残りの大半は巨大・微小な値が印字する約 300 文字の文字列の書出しである。1 store ごとにゼロ 8 個を書くと測定上約 10–15 % 高速だったが、float 印字プログラムすべてで 88 B を要するため採用しなかった。

正確性の証拠：

- `tests/float_gtable_exact_test.rs` は stdlib ソースから表をデコードし、各 j についてプリンター自体の 64-bit ワード演算を再現する。各 g(j) を多倍長整数による定義と照合する。
  - 表の 1 byte（要素 12、byte 3）を変更すると j = 27 … 53 で失敗する。
  - float の走査ではこの変更を検出しない。壊したビットは g の最上位ビットから約 2^-100 下にあり、サンプル中の丸め判断はそこまで達しなかった。そのため表に専用のテストがある。
- float の走査（全バイアス付き指数、特殊事例、100,000 パターン；ローカルでは 1,000,000）は通る。補正ビットを落とすと 100,479 行目で失敗する。
