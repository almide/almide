## 探针

每个程序计算 `work(s, i, iters)`：执行 `iters` 步 `acc = (acc * 31 + j) % 1000003`。程序以 10 个元素的 offer 为单位运行，每个 offer 的结果作为下一个的种子，因此 offer 之间不能重叠。在这些机器上，每个元素每次迭代约耗时 4–5 ns（iters 1000 ≈ 4–5 µs）。

| 探针 | 一个 offer | 测量方式 |
|---|---|---|
| `sweep` | 一个 10 元素的并行 map | t(1010 offers) − t(10 offers)，折算每个 offer |
| `nest` | 一个 4 元素的并行 map，其中每个元素本身是一个 10 元素的并行 map | t(210) − t(10)，折算每个外层 offer |
| `busy` | 同时运行两个独立通道，各自运行一串 10 元素 map（Almide：两个 `fan { }` 分支） | t(510) − t(10)，折算每对 offer |

两次运行之差抵消进程启动，在 wasm 上还抵消编译。每个数值都是 7 次运行的最小值；每轮重复中依次运行每种实现，使它们经历相同的机器状态。每一行中，所有实现都打印了相同结果。

实现：

| 列 | 内容 |
|---|---|
| Almide native | `almide build --release`，默认模式（成本模型为每个 offer 选择顺序或并行） |

## 解读

- **`busy` 差距最大：1000 次迭代时为 4.0x（Intel）和 5.1x（AMD）**，而且此处 Almide 比自身顺序模式（39.6 / 50.6 µs）更慢。每个通道的 offer 来自一个 `fan { }` 分支的线程。同一时刻只有一个 offer 能占有常驻工作线程组（list.rs 的 `almide_fan_run_tasks`），所以另一个通道每个 offer 都为每个 worker 创建线程。这就是接下来修复的项目：见下文**改动后**。
- `nest` 次之，差距为 4.2x / 3.3x。其外层 map 带有效果回调（调用 `fan { }`），而带效果的 `fan.map` 会逐个执行元素（#2594）。所以只有内层 map 并行，4 × 10 个元素作为四个 10 元素 offer 运行。这是语言表层变更，而非运行时变更。
- `sweep` 从 10000 次迭代起位于最速的 1.3x 以内。在 1000 次时差距为 1.7–2.2x，此时 Rayon 的工作窃取 join 比 Almide 的分发及成本模型选择 5 个 worker 的成本更低。
- Zig 0.13 的 `std.Thread.Pool` 在此每 offer 成本为 110–350 µs，从未最快。
- 高迭代次数下，Go 的顺序循环比其他实现约快 10%。这是代码生成，而非并行运行时，也是 Go 在 10000+ 时最快的原因。

## 改动后：一个共享池，调用者也领取块（2026-10-16）

现在，每个并行 offer 都将辅助调用投递到同一个常驻池（list.rs 的 `almide_fan_deal` / `almide_fan_pool`），无论它来自哪个线程，包括 `fan { }` 分支线程。调用线程也领取自身 offer 的块。在块耗尽后才启动的 helper 不领取任何块。调用者只等待已经进入该 offer 门控区的 helper，因此没有 offer 会等待正在别处忙碌的 helper。辅助调用发送给编号最小的空闲池线程，所以连续的单 offer 运行会保持使用相同的已预热线程；轮流分发在 AMD 机器上每 offer 多花 4–15%。

## 顺序循环：对字面量取余（2026-10-17）

从 10000 次迭代起，最速列属于 Go，因为 Go 的顺序循环比 Rust 和 Almide 约快 10%（并行运行时以相同方式将 10 个元素分到 8 个线程，因此循环决定这一行的结果）。循环为 `acc = (acc * 31 + j) % 1000003`：每次迭代一条依赖链，受延迟限制。有两件事拉长了 Almide 的链：

- rustc 将常量 `checked_rem` lowering 为魔数乘法，其符号修正位于链上（移位商的估计值、加上其符号位、再乘回去）；循环展开也将归纳变量偏移（`j + 1`、`j + 2`）放到链上；
- 在原生构建默认的 `x86-64-v3` 下，用 Rust 写的 i128 乘法变成无符号 `mulx` 加符号修正，而不是有符号单操作数 `imul`。

`Int` 上的 `x % <literal>`（除数为 3 或更大且不是二的幂）现在输出为 `almide_rem_const::<D>(x)`（crates/almide-codegen/src/prelude_rem.rs）：保持相同的截断余数，通过有符号 `imul` 的魔数乘法求商，并在乘法旁路根据被除数符号对余数作符号修正。3 或更大的字面量除数绝不会是 0 或 -1，因此调用不会中止，正如此前对这种字面量的 `%` 从不中止。90M 步的依赖链（`x86-64-v3`，各运行两次）在 Intel VM 上测得 290-292 ms，而 rustc 为 364-372 ms，Go 为 310 ms；AMD VM 上为 370-371 ms，对照为 454-457 ms 和 400-420 ms。余数已针对 17 个除数的 60,000 个被除数，以及小于 2000 的每个除数的倍数，与 `%` 进行核对（`prelude_rem.rs` 测试）。

## 线程池：向轮询线程发布 offer、窃取、重新校准成本模型（2026-10-17）

循环达到或超过 Go 的速度后，每项差距的其余部分都来自并行运行时。offer 通过每个空闲池线程自己的通道向其交付调用，而线程在 offer 之间睡眠，因此每个 offer 都支付内核唤醒路径的成本（这些 VM 上为 5-20 µs）。每个 worker 还读取线程 CPU 时钟三次（系统调用，AMD VM 上约 1.1 µs），块通过 mutex 获取，站点历史是 mutex 保护的 map。并且，在另一个 offer 的元素内产生的 offer 会发现线程已被占用，于是只在调用者自身上运行。现在（runtime/rs/src/list.rs）：

- **发布，而非投递。** offer 发布到 64 个槽位（`ALMIDE_FAN_SLOTS`）之一。池线程在每个 offer 后、park 前，轮询 `ALMIDE_FAN_SPIN`（50 µs），并从任何仍有剩余块的已发布 offer 领取块。只有当轮询线程数少于所需数量时，offer 才唤醒已 park 的线程。轮询线程只读取一个计数器，即仍有剩余块的已发布 offer 数（`ALMIDE_FAN_OPEN_BLOCKS`），在其非零之前不触碰其他内容。在最后一块分发后才进入的线程，不做元素清理便退出；调用者句柄只有在调用者可能睡眠时才克隆。门控位于调用者栈帧中，块由原子计数器分发，仍按列表顺序（ADR-0024 D6 的陷阱等待依赖这一点）。
- **每核一个线程。** 池线程仅在正在处理 offer 的线程数少于核心数时进入 offer（`ALMIDE_FAN_RUNNING`），否则让出核心。两个 `fan { }` 分支各向七个线程分发，会在八个核心上放置九个线程（busy，10000 次迭代：Intel VM 上为 Go 的 1.33x）。
- **等待的调用者在自身树内窃取。** 自己的块被领走后，调用者从同一最外层 offer（`AlmideFanGate::root`）的块内创建的 offer 领取块，而不取其他分支的块。领取另一分支的元素，会使本分支下一个 offer 最多延迟一个元素的时间（busy 10000：每对 108 µs，而对照为 95）；完全不取则在每个外层 offer 尾部让一个核心空闲（nest 10000：220，而对照为 187）。
- **重新校准成本模型。** W=8 时，十个空元素的强制并行 offer 现在成本为 2.4 µs（Intel）和 3.1 µs（AMD），此前为 8.2 和 24.1 µs（上表），Go 为 3.0 和 7.3 µs。`native_offer_ns` / `native_worker_ns` 现在为 1.5 + 0.7W µs，是新校准行的包络（fan-cost-model.txt）。并行 offer 每 8 次计时一次（`ALMIDE_FAN_RESAMPLE_PAR`），每个计时间隔都减去读时钟的成本；来自切换点 2x 以内并行 offer 的估计，会用一次顺序 offer 检验。顺序站点只有连续两次测量后才转为并行。站点历史是无锁表。

## nest：只做 fan-out 的效果回调（2026-10-17，#2594）

`nest` 的外层 `fan.map(list.range(0, 4), (q) => inner(s0 + q, iters))` 原本依次运行四个元素：`inner` 是 `effect fn`，效果回调会保留顺序 `fan.map`，使其效果保持列表顺序。但 `inner` 唯一的效果是自身对纯 `work` 执行 `fan { list.map(…) }`。fan 的可观察行为与其顺序求值相同（ADR-0024 D1），输出通过逐元素时间线（D5）。因此，一个只对已证明的工作进行 fan-out 的元素，无法让其他元素观察到它的顺序。

纯度分析的 fan 视图（crates/almide-codegen/src/pass_stream_fusion.rs 的 `Purity::for_fan`）现在允许一种 `effect fn`：其函数体仅能到达已证明的函数、嵌套 `fan { }` 块、带有已证明回调的 `fan.*` 调用，以及 `!`。fan 路由（pass_rust_lowering_fan.rs）将这种函数视为无效果。任何直接或经另一函数到达的效果模块调用（tests/fan_nested_effect_parallel_test.rs 中的 `env.sleep_ms`），仍会让回调保持顺序，因此不会改变 I/O 顺序。测试固定生成 Rust 中的两种路由，并检查并行输出与顺序运行及 wasm 字节完全一致。

- 空的强制并行 sweep offer 成本，Almide 为 2.55 / 2.47 µs（Intel / AMD），Go 为 3.14 / 6.23，Rayon 为 8.95 / 18.75。在 300 到 3000 次迭代之间，该成本占 offer 较大比例，Almide 是最速者的 0.47-0.65x。
- wasm 列仅供参考（参考实现为原生代码）。本次运行在 AMD VM 上噪声较大（nest 100 为 205.8 µs）；交错运行 develop 的 wasm 和本代码树的 wasm，在 nest 1000 处测得 371 和 455 µs，在 nest 0 和 100 处低于零。这些改动仅涉及原生路径。

剩余内容：wasm 路径中，`fan { }` 分支和并行 offer 依次运行（ADR-0024 D8）；以及本改动未允许的效果回调：会到达 I/O 的回调仍按列表顺序运行。ADR-0024 D3 要求除非到达有序操作，否则并发运行，这需要 `@ordered` 集合。

## 宽规模形状对比调优后的同类实现（2026-10-17，Almide develop，0746eb689）

Goal-5 扩展：先前的探针最多 offer 10 个相同大小的元素。以下行运行**一个覆盖 n 元素的 `fan.map`**，n 从 10 到 10⁶，并加入四种工作形状：

| 形状 | 元素工作 |
|---|---|
| size | 下限测试的 `work(s, i, iters)` 循环 |
| skew | 每第 10 个元素执行 20× 工作 |
| heap | 每个元素构建一个由 20 部分组成的 `String` 并返回长度；无循环 |
| fail | 每 97 个元素中有 1 个返回 `err("bad i")` |

每种实现都运行每个元素，并保留最低索引的错误，这就是 Almide 的 `fan.map` 规则。所有实现执行相同工作，使用全部 8 个线程；每行在每个实现上都打印相同校验和。

同类实现分别经过调优：

| 语言 | 变体 |
|---|---|
| Rust（Rayon 1.10.0） | `rayon`：`into_par_iter().map().collect()` · `tuned`：相同实现加 `with_min_len(n / (4·threads))` · `scope`：每线程一个处理静态块的 `rayon::scope` 任务 |
| Go 1.22 | `par`：每元素一个 goroutine · `pool`：每次 map 唤醒常驻 worker，从原子计数器领取 n/(4W) 大小的块 · `errgroup`：`golang.org/x/sync` v0.8.0，使用 `SetLimit(W)`、逐索引错误槽位、不取消上下文 |
| Zig 0.13.0 | `std`：`std.Thread.Pool`，每个 n/(4W) 大小的块一个 `spawnWg`，调用者也帮忙 · `hand`：W−1 个常驻线程加调用者，一个 futex 世代和一个原子块计数器 |

**复现：**

```bash
cd research/benchmark/fan-floor/wide && ./build.sh && ALMIDE=almide python3 wide.py
```

这会得到每 map 的 µs（7 次最小值，实现交错运行）、最大 RSS（GNU time）和启动时间。源码位于 `wide/`。`al-n` 是编译后的原生 Almide，`al-seq` 是相同二进制设置 `ALMIDE_FAN_SEQUENTIAL=1`，`al-w` 是 `almide run --target wasm`，以顺序方式运行。“best”是每种语言最快的并行变体，名称列在括号内。**al-n / best** 是相对于其中最快者的比值，低于 1.00 表示 Almide 胜出。

<a id="where-almide-loses-and-why"></a>

### Almide 落后的地方及原因

| # | 行 | 比值（Intel / AMD） | 原因 | 优先级 |
|---|---|---|---|---|
| W1 | size iters 100，n ≥ 100；heap | 5.7–11.4 / 2.1–5.5。Intel 上 `al-n` **比 `al-seq` 更慢**（n = 10⁶ 时 522 ms 对 312 ms） | `almide_rt_fan_map_par` 为**每个元素**开启输出时间线：`almide_fan_enter` 克隆一个 `Arc` 并交换线程局部值，其 drop 获取组 mutex、刷新 stdout 并调用 `notify_all`（`runtime/rs/src/fan.rs:101`、`crates/almide-codegen/src/prelude_fan.rs:64-90`）。≤ 1 µs 的元素通过锁争用和 futex 唤醒支付这一成本：本地同一程序消耗 18 s 的 sys 时间，对比顺序运行的 1.0 s。`almide_fan_group` 还为每个元素分配一个缓冲区（`prelude_fan.rs:61`），这就是 n = 10⁶ 时 RSS 为 65 MB 对 17 MB 的原因。 | **P-high**（#3784）：最常见的 `fan.map` 形状，却使加速效果反转 |
| W2 | size iters 100，n = 10（Intel） | 1.39 / 0.92 | 微小 offer 上同样的逐元素成本；成本模型将其保留为并行（`al-n` 3.5 µs 对 `al-seq` 3.1 µs） | P-low，归入 W1 |
| W3 | fail，n = 10³ / 10⁵ | 1.10–1.15 / 0.99–1.15 | 1000 次迭代下 W1 的逐元素成本，加上每个失败元素一个 `String`；Go 的线程池两者都不支付 | P-low，归入 W1 |
| W4 | 每一行，`al-w` | 1.2–1.3× `al-n-seq` | wasm 顺序运行 `fan.map`（ADR-0024 D8）；不是回归 | 由 #1628 / #3331 跟踪 |

凡是元素工作占主导的地方（iters 10000、skew、AMD 上的 fail），Almide 都胜出或持平：相对最佳调优实现为 0.69–1.07。Rayon 的 `with_min_len` 和静态 `scope` 只在小 offer 上胜过普通 `rayon`。n = 10⁴ 以上，Go 的常驻池是最强对手。带 `SetLimit` 的 `errgroup` 在各处都是最慢的并行变体：每个元素通过信号量运行一个 goroutine。W1 是独立目标；本目标中没有任何内容改变它。
