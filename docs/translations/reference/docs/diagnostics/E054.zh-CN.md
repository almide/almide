# E054 — fmt 验证失败

[![English](https://img.shields.io/badge/English-d0d7de?style=flat-square)](E054.md) [![日本語](https://img.shields.io/badge/%E6%97%A5%E6%9C%AC%E8%AA%9E-d0d7de?style=flat-square)](E054.ja.md) [![简体中文](https://img.shields.io/badge/%E7%AE%80%E4%BD%93%E4%B8%AD%E6%96%87-24292f?style=flat-square)](E054.zh-CN.md)



> 原文：[E054.md @ 9a95b285](https://github.com/almide/almide/blob/9a95b28519b90ae535dc9918bfed04805dc4675c/docs/diagnostics/E054.md)。这是供读者参考的非规范性翻译。CLI 内嵌的诊断说明仍使用英文原文。

`almide fmt` 拒绝写入文件，因为格式化无法保持程序不变。这是格式化器的 `--safe` 验证器（Black 模型，#1309）：任何写入之前，格式化输出必须 (1) 仍能解析，(2) 具有完全相同的 AST，(3) 保留所有注释。任一项失败，文件就保持原样，此诊断会报告原因：

```
error[E054]: fmt verification failed — AST changed by formatting at $.decls[3].body
  hint: Formatting this file would not conserve the program (parse, AST, or
        comments), so it was left untouched. This is a FORMATTER bug, not a
        source problem — please report it ...
```

<a id="what-it-means"></a>

## 含义

与 [E083](../../../../diagnostics/E083.md) 一样，**缺陷在编译器，而不在你的源码**。验证器正是为了让格式化器错误表现为明确拒绝，而不是悄然破坏；消息会包含第一个发生分歧的 AST 路径（或解析错误、注释数量），让编译器开发方能够据此处理。

<a id="what-to-do"></a>

## 应该怎么做

- 让所指文件保持未格式化状态（fmt 已经这样做了——拒绝说明安全机制正在发挥作用）。
- 在 <https://github.com/almide/almide/issues> 报告该文件；每个 E054 都是可以用回归夹具固定的格式化器缺陷。
- 正常格式化周围的文件；拒绝是逐文件进行的。

一类已知的无害情况是表达式中间的行内注释（`f(1 /* x */, 2)`）：解析合法，但 fmt 尚无法附着它，`#1326` 跟踪此支持。这类文件会保持未格式化，而不会丢掉注释。

<a id="where-it-fires"></a>

## 触发位置

`tests/diagnostics/` 中故意不设置 E054 源码夹具：触发因素是格式化器内部缺陷，没有任何已提交源码文件能够（或应该）刻意重现。验证器逻辑本身由 `crates/almide-tools/tests/fmt_corpus_test.rs` 固定，它直接将被破坏的“格式化后”输出输入 `verify_format`，并断言拒绝。

<a id="fix-it-verdict"></a>

## Fix-it 判定

**not-fixable** — 此错误报告的是自动重写无法决定的语义／设计问题。（`mechanical` = 无人值守的修复器可以应用重写；`conditional` = 建议的修复需要审查；`not-fixable` = 不存在自动重写。遵循 #1486 的适用性原则。）
