<a id="authoring-guide"></a>

## 執筆ガイド

各文書には次を含めます。

1. コードの意味を説明する**1 行の要約**。
2. **よくあるケース** — 発生させる最小コード片。
3. **診断の形** — 実際の `error[EXXX]: ...` 出力がどう見えるか。特に `hint:` と、存在する場合の `try:` セクション。Dojo や他のハーネスはこの形に依存します。
4. **修正方法** — 頻度／確率の順に並べます。
5. **理由** — 自明でない設計上の根拠。大きなコンテキストウィンドウを持つ LLM が、自分のケースに規則が適用されるかを推論できるようにします。
6. **関連項目** — 近接するコードやチートシートの節への相互参照。

<a id="fix-its-and-applicability-1312"></a>

## Fix-it と適用可能性（#1312）

ソース範囲と置換内容が分かる診断は、それ自体が修正です。`almide fix` は、そのための独自の書換表を持ちません。コンパイラの出したすべての fix-it を集め、機械適用可能なものを適用し、再検査し、繰り返します。修正を正確に表現できる新しい診断は、導入した日から自動修正を得られます。

修正を付ける際は二択であり、ビルダーがその選択を要求します。適用可能性を指定せずに置換範囲を付けることはできません。

| ビルダー | 適用可能性 | 適用するもの |
|---|---|---|
| `.with_machine_fix(line, col, end_col, text)` | `machine-applicable` | `almide fix` が無人で適用 |
| `.with_suggested_fix(line, col, end_col, text)` | `maybe-incorrect` | 人またはモデルが選択した後に適用 |
| `.with_alternative(line, col, end_col, text)` | `maybe-incorrect` | 人またはモデル。別の解釈であり、優先候補ではない |
| `.with_try(text)`（範囲なし） | `unspecified` | 誰も適用しない。表示のみ |

すべてのビルダーは診断の `repair` フィールドへ書き込みます（#2149）。内容は `primary`（範囲が正確な編集）、`alternatives`、`example`（表示専用のコード片）です。`almide fix`、LSP の quickfix、`check --json`（`"repair"`）はすべて、この一つのフィールドを読みます。

**`with_machine_fix` は綴りだけの変更に使います**。値、型、評価が同じで、作者の意図の読み方が厳密に一つである場合です。言語にないキーワードの削除（E049）は該当します。編集距離で選んだ改名は該当しません。コンパイルできても、誤った関数を呼ぶかもしれません。`T` を `Option[T]` に変えるものも該当しません。適用するとエラーを解消せず、移動させるからです。

**範囲は正確でなければなりません。** 実際のトークンまたは `Span` から導き、そこにあるはずの文字列をテキスト検索して推定してはいけません。推測した範囲に結び付いた fix-it は誤ったバイト列を黙って書き換え、fix-it がない場合より確実に悪くなります。正確な範囲が得られなければ `with_try` に戻し、人がコード片を読むようにします。`with_machine_fix` は実際のソースを指定できない範囲（行／列が 0、逆転した範囲）を拒否し、信頼するのではなく表示専用へ格下げします。

両面にゲートがあります。`tests/diagnostic_harness_test.rs` は、フィクスチャ群の範囲付き fix-it がすべて適用可能性を宣言し、問題なく適用でき、コンパイルでき、`fixed.almd` を再現することを検査します。

各文書の `## Fix-it verdict` は、バイナリと双方向に照合されます（#2149）。**mechanical** の各コードは、少なくとも一つのフィクスチャで機械適用可能な `repair.primary` を出力しなければならず、`almide fix` がそのフィクスチャを検査に通るプログラムへ変えなければなりません（`tests/diagnostic_coverage_test.rs`）。それ以外のコードはこれを出力できません（`tests/diagnostic_harness_test.rs`）。

<a id="the-two-way-repair-ratchet-2149"></a>

## 双方向の修正ラチェット（#2149）

- **診断を出す側** — `tests/diagnostics/<case>/repair.grep`：1 行に一つの検索文字列を書き、それぞれが、そのケースの診断が書き手に指示する内容（メッセージ、ヒント、`try:`、任意の `repair` 置換）の中に現れなければなりません。修正そのものを固定するので、ヒントが「引数の型を修正してください」（#2097）へ後退するとビルドが失敗します。
- **診断を出さない側** — `tests/diagnostics/silent/*.almd`：以前に誤った診断や誤解を招く診断を生じた形の、正しいプログラムです（#2345、#2097、#2254、#2096、#2607、#2093/#2095、およびすべての機械的 fix-it の適用対象に近いが対象外のケース）。それぞれ警告も含めて一切診断なしで検査を通る必要があります（`tests/diagnostic_silent_test.rs`）。追加するには、何の形を守るかを冒頭コメントで示したプログラムを書き、`SILENT_FLOOR` を増やします。

<a id="source-caveats"></a>

## 原文の確認が必要な点

この翻訳は、原文内の不整合を実装の挙動だと推測して統合・訂正しません。次の箇所では、実際の挙動や自動修正の適用条件を別途確認する必要があります。

- E002 / E003 / E013: 本文の修正案と末尾の Fix-it 判定では、無人適用できる範囲の説明に差があります。
- E009: pure loop の再帰推奨は、現在の `CLAUDE.md` の回数既知ループに関する方針との照合が必要です。
- E015: 本文は警告として説明し、定型 verdict は error と表現しています。
- E027: #3788 は原文で将来条件として扱われています。現在の実装完了を示す記述ではありません。
- E043: 上部の書換例には末尾の `!` があり、自動 fix の説明にはありません。
- E048: 「三つの形」と述べる一方、表には五行あります。
- E049: 本文は `in` の削除、末尾の verdict はブロックへの書換えを説明しています。
- E052: 表は演算子の書換えも自動適用対象とし、その後の説明は「最初の行だけ」としています。
- E116 / E117: 関連項目の E118 説明は「標準ライブラリの型のみ」としていますが、E118 本文は依存パッケージ・アプリの owner/grant も認めています。

- E100: 原文には全ターゲットのメモリ安全性や唯一の破損経路について強い表現があります。この訳は実装の無欠陥や成果物全体の安全性を独立に証明したものではありません。保証範囲は[証明と信頼の境界](../../../../contracts/proven-vs-trusted.md)と照合してください。
- E103: 原文の「定時間」を、入力長に無関係、またはコンテナー全体の全処理から時間情報が漏れないという保証へ拡張しないでください。
