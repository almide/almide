# E109 — pure fn runs an effect fn through a function value

A plain `fn` ran an `effect fn` that it reached as a VALUE: a callback it
was handed, a record field, a list element, an option payload, or a closure
another function built. E006 refuses the shapes it can see at a call — a
direct call, a name that holds an effect fn (#3274), an effect fn named as an
argument — but a function value travels further than a call site, and the
pure fn that finally calls it ran the effect with nobody refusing it (#4151).

```almide
import fs

type Reader = { read: (String) -> Result[String, String] }

fn pure_looking(r: Reader) -> Result[String, String] = (r.read)("s.txt")   // ← E109

effect fn main() -> Unit = {
  let r = Reader { read: fs.read_text }
  println(pure_looking(r) ?? "none")
}
```

```
error[E109]: pure function `pure_looking` runs an effect function it does not call by name
  --> main.almd:5:56
  = path: pure_looking → field `read` → closure (line 8:26 in main) → fs.read_text (line 8:26)
  hint: A plain `fn` cannot run an `effect fn`, even one it receives as a value — a callback, a record field, a list element (ADR-0009 D2). Mark `pure_looking` as `effect fn` if it is meant to do I/O, or pass it a function that does none
```

## How it is decided

The effect bit rides function values the way effect categories do
(ADR-0026 D1, `crates/almide-codegen/src/effect_flow`): an `effect fn`
carries it, a closure that calls one carries it, and a value stored in a
field, a list or an option keeps it. A bare fn-typed PARAMETER is transparent
(ADR-0009 D2): a plain fn may call it, and the call site that hands it an
effect fn is charged instead — so `fn apply(f: (A) -> B, x: A) = f(x)` is
fine, and `apply(fs.read_text, p)` is an effect call (E006 from a pure fn).
E109 is the remaining case: a pure fn whose own body runs the bit, not
through a parameter of its own.

The analysis is whole-program and conservative: a value that leaves the
tracked positions (a list, a variant payload, a value passed into an unknown
callee) is pooled with every other untracked value of the same signature, and
a call of a value read back from such a position is charged with the pool. A
pure fn that calls a function it read from a list is therefore refused when
any function of that signature that does I/O was put in a list anywhere in
the program.

`process.exit` (an `effect fn` whose result is `Never`) does not carry the
bit: ending the program is ADR-0022's abort, which a plain fn may do.

## Fix

1. If the function is meant to do I/O, say so: mark it `effect fn` (its
   callers then see a `Result` and propagate with `!`).
2. If it is meant to be pure, pass it a function that does no I/O — do the
   I/O in the effect fn that builds the value and hand the pure fn the data.

## Fix-it verdict

**not-fixable**: whether the function should become an `effect fn` or be
given a different value is a design decision; the diagnostic names the path
(`= path:`) from the pure fn to the effect fn it reached.
