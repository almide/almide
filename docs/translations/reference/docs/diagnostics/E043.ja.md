# E043 — 公開および内部の try_* 記法

[![English](https://img.shields.io/badge/English-d0d7de?style=flat-square)](E043.md) [![日本語](https://img.shields.io/badge/%E6%97%A5%E6%9C%AC%E8%AA%9E-24292f?style=flat-square)](E043.ja.md) [![简体中文](https://img.shields.io/badge/%E7%AE%80%E4%BD%93%E4%B8%AD%E6%96%87-d0d7de?style=flat-square)](E043.zh-CN.md)



> 原文：[`docs/diagnostics/E043.md`](https://github.com/almide/almide/blob/9a95b28519b90ae535dc9918bfed04805dc4675c/docs/diagnostics/E043.md)、固定コミット `9a95b285`。読者向けの非規範的な翻訳であり、CLI の診断出力は英語のまま。

`list.try_*` ファミリー（`try_map` / `try_filter` / `try_flat_map` / `try_filter_map` / `try_fold` / `try_find` / `try_each`）は、失敗可能性の多相性がなかったことへの単相の回避策だった。ADR-0006 がこれを解消する。コアのコンビネーターは失敗可能性に対して多相となり、本体末尾が `!` のコールバック（または `-> T!` を宣言した名前付き fn）が、最初のエラーでの短絡を含む失敗可能形式を具体化する。このファミリーは一回の非推奨期間（v0.55.0）を経て、v0.56.0 以降削除されている。このエラーは書き換えを示す。

<a id="the-mechanical-rewrite"></a>

## 機械的な書き換え

```almide
list.try_map(xs, f)      →  list.map(xs, (x) => f(x)!)!
list.try_filter(xs, p)   →  list.filter(xs, (x) => p(x)!)!
list.try_fold(xs, z, f)  →  list.fold(xs, z, (a, x) => f(a, x)!)!
// find / each / flat_map / filter_map are the same shape
```

<a id="the-internal-carriers-are-not-the-escape-hatch"></a>

## 内部 carrier は抜け道ではない

公開名の削除後も、その本体は `list.__fallible_map` … として残った。これはコールバックが伝搬するときにチェッカーが代わりに具体化する形式である。一つのリリースではソースから到達可能で、`list.__fallible_map(xs, f)` はコンパイル・実行でき、警告も出なかった。これは第二の記法を削除したのではなく改名しただけで、書き手にとっては非推奨名より悪い。二つの動く記法のうち片方だけ文書化され、どちらが正規か示されないためである。それ以降、ソース内で carrier を名指しすることも同じ E043 となる。

carrier は今も存在し、実行される。ただしソースで書いてよいものではなくなった。

同じ規則は、後から失敗可能形式を得た fs のストリーミング walker（#1144、契約 C-274）にも適用される。`fs.__fallible_fold_lines` と `fs.__fallible_for_each_line` は脱糖先であり、記法ではない。これらに公開 `try_` 名があったことはなく、最初から閉じられた入口しか持たなかった。

```almide
fs.fold_lines(path, z, (a, l) => f(a, l)!)!   // ✓ the blessed spelling
fs.for_each_line(path, (l) => f(l)!)!         // ✓
fs.__fallible_fold_lines(path, z, f)          // ✗ E043
```

二つの分割処理（`fs.fold_lines_range` / `fs.fold_lines_chunked`）には失敗可能形式自体がない。分割 walker では最初のエラーが定義されないため、隠すべき carrier もない。

<a id="diagnostic"></a>

## 診断

```
error[E043]: list.try_map was removed — the core HOF is fallibility-polymorphic (ADR-0006)
  try: list.map(xs, (x) => f(x)!)!

error[E043]: list.__fallible_map is an internal carrier, not a spelling — source may not name it (ADR-0006)
  try: list.map(xs, (x) => f(x)!)!

error[E043]: fs.__fallible_fold_lines is an internal carrier, not a spelling — source may not name it (ADR-0006)
  try: fs.fold_lines(path, z, (a, l) => f(a, l)!)!
```

<a id="why"></a>

## 理由

`try` は借用語だが、借用元同士で意味が異なる（Rust の `try_fold` は短絡、Swift/Zig の `try` は伝搬、つまり Almide の `!`）。戦略ごとの対になる関数は、公開仕様を戦略 × コンビネーターの数に増やす。各コンビネーターを一つの名前にし、コールバックの `!` に戦略を担わせるのが Swift SE-0413 のモデルである。

carrier を閉じる理由も同じである。`try_*` のコストは単語そのものではなく、書き手が選ばなければならないことだった。`__` 接頭辞は選択をなくさず、選択肢の片方を隠すだけである。`stdlib/list.almd` を読んだモデルは、その隠れた方を出力する。

<a id="fix-it-verdict"></a>

## Fix-it 判定

**mechanical** — try_* の書き換え表は正確である。単独の fn 参照コールバック形式（`list.try_map(xs, f)`）は機械的に適用される（#1486）。コールバックを `(x) => f(x)!` で包み、Result carrier 型を保持する（末尾の `!` は付けず、アンラップは呼び出し側の判断に残す）。lambda コールバックは本体内の編集を要するためヒントのみとなる。（`mechanical` = 無人の修正ツールが書き換えを適用できる。`conditional` = 提案された修正はレビューが必要。`not-fixable` = 自動書き換えが存在しない。#1486 の適用可能性の原則。）
