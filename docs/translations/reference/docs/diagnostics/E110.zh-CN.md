# E110 — 不可信输入只能解码到输入类型

[![English](https://img.shields.io/badge/English-d0d7de?style=flat-square)](E110.md) [![日本語](https://img.shields.io/badge/%E6%97%A5%E6%9C%AC%E8%AA%9E-d0d7de?style=flat-square)](E110.ja.md) [![简体中文](https://img.shields.io/badge/%E7%AE%80%E4%BD%93%E4%B8%AD%E6%96%87-24292f?style=flat-square)](E110.zh-CN.md)



> 原文：[`docs/diagnostics/E110.md`](https://github.com/almide/almide/blob/9a95b28519b90ae535dc9918bfed04805dc4675c/docs/diagnostics/E110.md)，固定提交 `9a95b285`。这是供读者参考的非规范性译文，CLI 诊断输出仍为英文。

标记为 `@input_sink` 的 fn（`http.decode_json`）将不可信输入解码到其受 `Decode` 约束的类型参数。该参数必须绑定为**输入类型**：声明为 `: Decode` 且不同时为 `Encode` 的记录或变体（row 22，C-436）。输入类型的每个字段都是输入，因此该类型就是客户端可设置内容的允许清单。

```almide
type User: Codec = { name: String, email: String, is_admin: Bool = false }

match http.decode_json[User](req) {   // ← E110
```

```
error[E110]: `http.decode_json` decodes untrusted input only into an input type, and `User` is also sent out (it is `Codec`)
  hint: Declare what the client may set as its own type, then build `User` in code:
          type UserInput: Decode = { name: String, email: String }
          match http.decode_json[UserInput](req) {
            ok(i) => … User { name: i.name, email: i.email, … } …
            err(bad) => bad,     // unknown key → 400
          }
        Every field of a `: Decode` type is input. A field the client must not set stays out of it.
```

同一代码还覆盖两种形式：

- **嵌套**在输入类型中、同时也用于输出的记录，作为字段（`Address: Codec` 时的 `type SignupInput: Decode = { address: Address }`）或变体内部值（`Role: Codec` 时的 `| Grant(Role)`）。给共享的 `Address` 添加 `verified: Bool = false` 会使该字段可从请求设置。
- 自身不是 `@input_sink` 的 fn 的**类型参数**（`fn body_as[T: Decode](req) = http.decode_json[T](req)`）：将转发 fn 标记为 `@input_sink`，让其调用者的类型接受检查。

嵌套在输入类型中、由标准库模块声明的类型（`Url`、`Uuid`）是叶值，不接受此项判定。

<a id="decoding-the-request-by-hand-4232"></a>

### 手动解码请求 (#4232)

绕开 sink 不会绕开规则。请求数据——由 `HttpRequest`（`@input_sink` 声明的参数类型）计算出的任何值——会通过绑定、容器、回调和用户辅助函数被追踪到解码位置。若到达同时用于输出的类型、含有这种类型的输入类型，或非 `@input_sink` fn 的类型参数的 `T.decode` / `T.decode_strict`，会在解码处（或把数据交给解码辅助函数的调用处）产生相同的 E110。

```almide
let u = User.decode(json.parse(http.body(req))!)!   // ← E110
```

```
error[E110]: `User.decode` decodes request data into `User`, and `User` is also sent out (it is `Codec`)
  note: path: HttpRequest → User.decode
```

改为解码到输入类型（`UserInput.decode_strict(..)` 或 `http.decode_json[UserInput](req)`），再用代码构造 `User`。从非请求来源数据解码的 `Codec` 类型不接受此项判定。`@input_sink` fn 的函数体也不判定；其类型参数在每个调用者处判定。

<a id="fix"></a>

## 修复

```almide
type User: Codec = { name: String, email: String, is_admin: Bool = false }

type UserInput: Decode = { name: String, email: String }

match http.decode_json[UserInput](req) {
  ok(i) => http.response(201, "${User { name: i.name, email: i.email, is_admin: false }.name}"),
  err(bad) => bad,
}
```

<a id="why"></a>

## 原因

mass assignment 需要不可信来源，**以及**字段集合比该来源允许设置范围更宽的目标类型。在测量过的所有基于派生的 codec 中（Go、serde、pydantic、zod、Swift、kotlinx、Jackson、aeson），`is_admin` 这类已知字段若不作特殊标记，就会从输入设置。严格处理未知键也无济于事，因为 `is_admin` 是已知键。堵住这一漏洞的生态使用与领域类型分离的允许清单类型（FastAPI 的 `UserCreate`、zod 的 `pick`、Elm 的 decoder 值、Rails 的 strong parameters）。领域类型上的 `@skip_decode` 是拒绝清单：下一个添加到 `User` 的字段不会自带标记。

仅 `: Decode` 的类型就是这个只需声明一次的允许清单，修改 `User` 不会扩大它。sink 同时使用 `T.decode_strict` 解码，因此任何深度上输入类型之外的键（`is_admin`、拼写错误、探测键、嵌套输入记录或变体内部值中的键）都会产生带路径的 `400 Bad Request: unknown key '<k>'`。其他位置的 `T.decode` 仍保持宽松。

测试样例：`tests/diagnostics/e110-codec-at-request-sink`、`e110-codec-nested-in-input-type`、`e110-codec-in-variant-payload`、`e110-forwarded-input-type-parameter`；手动解码请求体的样例为 `e110-hand-decoded-request-body`、`e110-hand-decode-through-helper`、`e110-hand-decode-generic-helper`。
