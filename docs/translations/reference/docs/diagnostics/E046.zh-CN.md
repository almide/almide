# E046 — 调用参数中的占位符 `_`

[![English](https://img.shields.io/badge/English-d0d7de?style=flat-square)](E046.md) [![日本語](https://img.shields.io/badge/%E6%97%A5%E6%9C%AC%E8%AA%9E-d0d7de?style=flat-square)](E046.ja.md) [![简体中文](https://img.shields.io/badge/%E7%AE%80%E4%BD%93%E4%B8%AD%E6%96%87-24292f?style=flat-square)](E046.zh-CN.md)



> 原文：[`docs/diagnostics/E046.md`](https://github.com/almide/almide/blob/9a95b28519b90ae535dc9918bfed04805dc4675c/docs/diagnostics/E046.md)，固定提交 `9a95b285`。这是面向读者的非规范性译文；CLI 诊断输出仍为英语。

调用参数位置的 `_` 不是值，也永远不会成为值。它能解析（`ExprKind::Placeholder`），但 lowering 无法在该位置放入内容，于是将其变为 `Unit`。因此 `add(_, 10)` 过去能干净通过检查（“No errors found”），随后在构建时失败：

```
codegen produced invalid Rust — this is an Almide bug.
error[E0308]: mismatched types
    let v: i64 = add((), 10i64);
                     ^^ expected `i64`, found `()`
```

这是编译器把用户错误归咎自身，与 E045 针对元组索引解决的失败模式相同（#1266）。现在它是检查期错误。

```almide
fn add(a: Int, b: Int) -> Int = a + b

let v = add(_, 10)        // ← E046: argument 1 of add()
let w = 5 |> add3(_, 10)  // ← E046 on the pipe path too
```

## 这不是部分应用

Almide 没有 `_` section 语法，该占位符也从未如此工作。对修复前编译器的测量：

- `let v = add(_, 10)` 将 `v` 的类型设为 add 的**返回**类型（`i64`），而非函数；生成的 Rust 为 `let v: i64 = add((), 10i64)`。
- 在管道位置，`_` 计为**额外的位置参数**：`5 |> add(_, 10)` 产生 E004，“add() expects 2 argument(s) but got 3”。多一个参数的被调用方（`5 |> add3(_, 10)`）吸收了这个额外参数并进入 codegen，这种形式使其成为检查时静默放行、构建时崩溃的问题，而不只是令人困惑的问题。

## 修复

用 lambda 为缺失值命名；它才是真正表示“稍后提供这一项”的结构：

```almide
let f = (x) => add(x, 10)
let v = f(5)

xs |> list.map((x) => add(x, 10))
```

## 不要与 typed hole 混淆

表达式位置的 `_` 是另一种获准的结构：**typed hole**，它接受上下文要求的任何类型，让程序其余部分通过类型检查，并在执行到达时 panic。

```almide
fn compute(x: Int) -> Int = _                  // typed hole — checks, panics
fn compute(x: Int) -> Int = todo("no impl")    // same, with your own message
```

这些不是 E046。参见 [docs/CHEATSHEET.md](../../../../CHEATSHEET.md)。

## Fix-it 判定

**conditional** — lambda 参数名及参数数量取决于意图。（`mechanical` = 无人值守的修复器可以应用改写；`conditional` = 建议的修复需要审查；`not-fixable` = 不存在自动改写。#1486 的适用性原则。）
