# E101 — 源码看起来与编译内容不同

[![English](https://img.shields.io/badge/English-d0d7de?style=flat-square)](E101.md) [![日本語](https://img.shields.io/badge/%E6%97%A5%E6%9C%AC%E8%AA%9E-d0d7de?style=flat-square)](E101.ja.md) [![简体中文](https://img.shields.io/badge/%E7%AE%80%E4%BD%93%E4%B8%AD%E6%96%87-24292f?style=flat-square)](E101.zh-CN.md)



> 原文：[E101.md @ 9a95b285](https://github.com/almide/almide/blob/9a95b28519b90ae535dc9918bfed04805dc4675c/docs/diagnostics/E101.md)。这是供读者参考的非规范性翻译。CLI 内嵌的诊断说明仍使用英文原文。

E101 拒绝读者所见与编译器读取内容不同的源码文本：`.almd` 文件中任何位置的原始隐藏字符（#4092、#4266），以及读者无法与其他名称区分的标识符（#4266）。

<a id="hidden-characters"></a>

## 隐藏字符

集合为 C-418 的转义表（`crates/almide-base/src/err_text.rs` 中的 `ALMIDE_RT_ERRTEXT_ESCAPED`）减去 TAB、LF 和 CR：运行时错误文本必须转义的字符，正是源文件不得原样包含的字符。

- 双向控制字符（下表），会重新排列显示行；
- U+2028 LINE SEPARATOR 和 U+2029 PARAGRAPH SEPARATOR，编辑器或网页会把它们显示为换行，但词法分析器不将其视为换行；
- 其他所有 General Category Cf 字符——U+200B..U+200D、U+2060..U+2064、文件中间的 U+FEFF、U+00AD 等——在屏幕上不可见；
- Tags 区块 U+E0000..U+E007F：不可见的 ASCII，阅读源码的模型却会把它读作文本（ASCII smuggling）；
- TAB、LF 和 CR 之外的原始 C0 和 C1 控制字符。

开头的字节顺序标记在扫描前移除。九个双向控制字符：

| 码点 | 名称 |
|---|---|
| U+202A | LEFT-TO-RIGHT EMBEDDING |
| U+202B | RIGHT-TO-LEFT EMBEDDING |
| U+202C | POP DIRECTIONAL FORMATTING |
| U+202D | LEFT-TO-RIGHT OVERRIDE |
| U+202E | RIGHT-TO-LEFT OVERRIDE |
| U+2066 | LEFT-TO-RIGHT ISOLATE |
| U+2067 | RIGHT-TO-LEFT ISOLATE |
| U+2068 | FIRST STRONG ISOLATE |
| U+2069 | POP DIRECTIONAL ISOLATE |

注释、字符串字面量、heredoc、原始字符串和所有目标都遵循同一规则：这是前端错误。

包含 `U+202E } U+2066 if admin then U+2069 {`（实际字符，而非名称）的行注释，在编辑器或代码审查页面中显示为顺序颠倒的代码，而编译器读到的是注释。本页不能显示原始字符——这正是关键。

```
error[E101]: raw hidden character U+202E RIGHT-TO-LEFT OVERRIDE at line 5, column 6
  hint: this character makes the source display differently from how it compiles (Trojan Source), or hides text from a reader that a model still reads. Remove it from a comment; inside a string literal, write the escape `\u{202E}` if the character is intended
```

<a id="fix"></a>

## 修复

- 在注释中：删除该字符。
- 在确实需要它的字符串字面量或 heredoc 中：写转义。转义在源码中是 ASCII，因此审查者与编译器读取同样的文本，同时仍会解码为该字符：

```almide
let s = "user\u{202E} txt.exe"   // the escape, not the raw character
```

原始字符串（`r"…"`）没有转义层；请改用普通字面量构造值。emoji ZWJ 序列将连接符写为转义：`"👨\u{200D}👩\u{200D}👧"`。

<a id="homoglyph-identifiers"></a>

## 同形字标识符

UTS #39 的两条规则，仅检查包含非 ASCII 字符的标识符（rustc 的 `mixed_script_confusables` 和 `confusable_idents` 采用相同边界，但作为警告）：

- **混合文字体系。** 非 ASCII 标识符最多允许 UTS #39 的 *Moderately Restrictive* 范围：一种文字体系；Latin 与 Han、Hiragana、Katakana、Hangul 或 Bopomofo 组合；或 Latin 与除 Cyrillic、Greek 以外的另一种文字体系组合。每个字符还必须属于 General Security Profile 的 `Allowed`。含 Cyrillic `а`（U+0430）的 `аdmin` 属于 Latin + Cyrillic，会被拒绝。
- **易混淆项。** 同一文件中两个不同写法若具有相同的 UTS #39 skeleton，且至少一个含非 ASCII 字符，会在较后出现者处拒绝：例如 `ace` 旁边全为 Cyrillic 的 `асе`。插值孔中的标识符也计入。

```
error[E101]: identifier `аdmin` mixes scripts a reader cannot tell apart at line 4, column 4
  hint: its non-ASCII characters are `а` U+0430 (Cyrillic). An identifier must be written in one script, …
```

修复：使用该名称自身文字体系中的字母，或重命名其中一个。`привет`、`名前`、`user名` 和 `π` 都可以。

<a id="why"></a>

## 原因

Trojan Source（CVE-2021-42574）：源码含其中某个字符时，审查者读到的代码并非编译器读到的代码。rustc 默认禁止注释和字面量中的双向控制字符（`text_direction_codepoint_in_comment`、`text_direction_codepoint_in_literal`）。同形字标识符对应 CVE-2021-42694：第二个函数看起来与第一个一样，使变更能够调用不同于差分所展示的代码。

<a id="fix-it-verdict"></a>

## Fix-it 判定

**not-fixable**：注释中的字符应删除，字面量中则可能有意使用，应改为转义；诊断不会替你选择。

夹具：`tests/diagnostics/e101-*`（注释、字面量、heredoc、行内块注释和原始字符串中的双向控制符；标签字符；注释中的 U+2028；字面量中的 U+200B；混合文字体系和易混淆标识符；插值孔中的同形字）。相近但不触发的例子：`tests/diagnostics/silent/bidi-control-written-as-escape.almd` 和 `tests/diagnostics/silent/non-ascii-identifiers-a-reader-can-tell-apart.almd`。
