# E001 — 类型不匹配

[![English](https://img.shields.io/badge/English-d0d7de?style=flat-square)](E001.md) [![日本語](https://img.shields.io/badge/%E6%97%A5%E6%9C%AC%E8%AA%9E-d0d7de?style=flat-square)](E001.ja.md) [![简体中文](https://img.shields.io/badge/%E7%AE%80%E4%BD%93%E4%B8%AD%E6%96%87-24292f?style=flat-square)](E001.zh-CN.md)



> 原文：[`docs/diagnostics/E001.md`](https://github.com/almide/almide/blob/9a95b28519b90ae535dc9918bfed04805dc4675c/docs/diagnostics/E001.md)，固定提交 `9a95b285`。这是面向读者的非规范性译文；CLI 诊断输出仍为英语。

表达式的类型不符合周围上下文的预期。

<a id="common-cases"></a>

## 常见情况

```almide
let x: Int = "hello"             // expected Int, got String
fn f() -> Int = "abc"            // body type doesn't match return type
list.map(xs, (x) => x + "!")     // closure return type conflicts with list element
```

<a id="specialized-sub-patterns-with-try-snippets"></a>

## 特定子模式（附 `try:` 片段）

<a id="unit-leak-fn-body-ends-with-a-let-binding"></a>

### Unit 泄漏：fn 体以 `let` 绑定结束

```almide
fn sum_digits(n: Int) -> Int = {
    let abs_n = int.abs(n)           // ← `let` returns Unit, not Int
}
```

诊断：

```
error[E001]: type mismatch in fn 'sum_digits': expected Int but got Unit
  try:
      // fn body ends with `let abs_n = ...` (a statement, returns Unit).
      // Add `abs_n` as the trailing expression so the fn returns Int:
      //
      //   let abs_n = <computation>
      //   abs_n                         // <-- add this line
```

编译器从 AST 提取真实的绑定名，并在片段中引用它。修复：将该名称添加为末尾表达式。

<a id="unit-leak-if-arm-is-an-assignment"></a>

### Unit 泄漏：if 分支是赋值

```almide
fn clamp(x: Int, lo: Int) -> Int = {
    var val = x
    if val < lo then { val = lo } else val    // ← then-arm is Unit
}
```

诊断：

```
error[E001]: type mismatch in if branches: expected Int but got Unit — Int is the declared return type, and the branch at line 3 produces it
  try:
      // the then-arm is `val = ...` (assignment, returns Unit).
      // Rewrite as a rebinding of `val`:
      //
      //   let new_val = if cond then <new-value-for-val> else val
```

会引用真实变量名（`val`）。修复：使用 `let new_x = if cond ... else ...`。

<a id="effect-call-bound-to-an-annotated-let-without-"></a>

### 未加 `!` 的 effect 调用绑定到带注解的 `let`

```almide
effect fn count() -> Int = 3

effect fn main() -> Unit = {
  let n: Int = count()             // ← the call is Result[Int, String]
  println(int.to_string(n))
}
```

诊断：

```
error[E001]: type mismatch in let n: expected Int but got Result[Int, String]
  hint: the value is a Result[Int, String] — unwrap it first: `!` propagates the error (effect fn body), `?? fallback` supplies a default, or `match` handles ok/err
  try: (machine-applicable — `almide fix` applies it)
      !
```

用户定义的 `effect fn f() -> T` 在调用处是 `T!`（ADR-0002 §D6），因此注解指定的是成功类型，缺少的是 `!`。这与 E005 对 `g(count())`、E041 对 `let m = count()` 提供的指引相同。在 effect fn 体内（任何 lambda 之外），当被调用方是声明非 Result `-> T` 的 `effect fn` 时，`count()` → `count()!` 的修复属于 **machine-applicable**：`!` 是两端声明类型对应的唯一写法。声明 `-> Result[T, E]` 的被调用方有意返回 Result，因此同样的 `!` 只是建议（作者可能想用 `??` 或 `match`）。在 pure fn、lambda 中，或调用跨越多行时，只给出提示而不提供编辑。

<a id="a-wrong-first-arm-2927"></a>

### 第一个 arm 错误（#2927）

```almide
effect fn level() -> Level? = some({ label: "v", n: 1 })

effect fn apply(c: Cmd) -> Result[Level?, String] = match c {
  A => ok(level()),        // ← the mistake: level() without `!`
  B(_) => ok(none),
}
```

诊断：

```
error[E001]: type mismatch in match arm: expected Result[Option[Level], String] but got Result[Result[Option[Level], String], String] — Result[Option[Level], String] is the declared return type, and the arm at line 5 produces it
  --> app.almd:4:8
  hint: add `!` to `level()`: without it the call's own Result is wrapped a second time. …
  try: (machine-applicable — `almide fix` applies it)
      !
```

位于尾位置的 match / if 会依据 fn 声明的返回类型检查，因此报告的是与之不一致的 arm（或分支），而非后面正确的 arm。若没有声明类型作为依据，第一个 arm 会确定类型，消息也会说明这一点（`the first arm at line N fixed
the type to T`）。如果 `ok(f())` / `some(f())` arm 中的调用返回 Result，而声明类型并未将它嵌套，就会指出缺少 `!`。

<a id="-on-an-effect-fn-that-returns-an-option-without--3522"></a>

### 对返回 Option 的 effect fn 使用 `??`，却未加 `!`（#3522）

```almide
import args

effect fn main() -> Unit = {
  let ledger = args.option("ledger") ?? "ledger.toml"   // ← missing `!`
  println(ledger)
}
```

诊断：

```
error[E001]: type mismatch in ?? fallback: expected Option[String] but got String
  --> app.almd:4:37
  hint: `args.option` is an effect fn (its call is `Result[Option[String], String]`): propagate its error with `!` before `??` — `args.option("ledger")! ?? "ledger.toml"`
  try: (machine-applicable — `almide fix` applies it)
      !
```

声明 `-> Option[T]` 的 effect fn（`args.option` 或自定义函数）以 `Result[Option[T], String]` 调用，因此单独的 `??` 为 `Err` 提供默认值，需要 `Option[T]` 类型的后备值。当后备值是 `T` 时，修复是先 `!` 再 `??`：`!` 传播错误，`??` 为 none 提供默认值。绑定类型为 `T`，所以后续使用处不会重复报告。后备值既不是 `Option[T]` 也不是 `T`，以及对纯 `Option[T]` 调用使用 `??` 的情况，仍保持普通类型不匹配诊断。

<a id="fix-general"></a>

## 修复（通用）

- 调整字面量／值以匹配预期类型。
- 修改显式类型注解以匹配实际表达式。
- 使用标准库辅助函数转换：`int.to_string`、`int.parse(s)!`（在兼容的失败通道中）或 `int.parse(s) ?? 0`、`float.from(n)`、`int.from_saturating(x)`（截断）等。
- **如果不匹配中的“got Unit”令人疑惑**，检查末尾的 `let x = ...` 或 `x = y` 赋值是否位于预期产生值的位置。

<a id="fix-it-verdict"></a>

## Fix-it 判定

仅限定形态属于 **mechanical**（#2653）：`let x: T = f()` 中，`f` 是声明 `-> T` 的 `effect fn`，且绑定位于 effect fn 体内时，在调用后添加 `!` 是精确修复（见上文）；在相同被调用方规则下，`ok(f())` / `some(f())` 的 match arm 或 if 分支将声明的 `Result` 多嵌套一层时，也适用同样的 `!`（#2927）；以及左侧是声明 `-> Option[T]` 的 `effect fn` 的单行调用、后备值是其 `T`、且 `??` 位于 effect fn 体内的任何 lambda 之外时，在 `??` 前添加 `!`（#3522）。所有其他 E001 都是 **not-fixable**：错误报告的是自动改写无法判断的语义／设计问题。（`mechanical` = 无人值守的修复器可以应用改写；`conditional` = 建议的修复需要审查；`not-fixable` = 不存在自动改写。#1486 的适用性原则。）
