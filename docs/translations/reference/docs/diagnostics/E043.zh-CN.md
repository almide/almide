# E043 — 公开与内部的 try_* 写法

[![English](https://img.shields.io/badge/English-d0d7de?style=flat-square)](E043.md) [![日本語](https://img.shields.io/badge/%E6%97%A5%E6%9C%AC%E8%AA%9E-d0d7de?style=flat-square)](E043.ja.md) [![简体中文](https://img.shields.io/badge/%E7%AE%80%E4%BD%93%E4%B8%AD%E6%96%87-24292f?style=flat-square)](E043.zh-CN.md)



> 原文：[`docs/diagnostics/E043.md`](https://github.com/almide/almide/blob/9a95b28519b90ae535dc9918bfed04805dc4675c/docs/diagnostics/E043.md)，固定提交 `9a95b285`。这是面向读者的非规范性译文；CLI 诊断输出仍为英语。

`list.try_*` 系列（`try_map` / `try_filter` / `try_flat_map` / `try_filter_map` / `try_fold` / `try_find` / `try_each`）是缺少可失败性多态时的单态变通方案。ADR-0006 消除了它：核心组合器具备可失败性多态，函数体以 `!` 结束的回调（或声明 `-> T!` 的具名 fn）会实例化可失败形式，包括遇到首个错误时短路。该系列经历了一个弃用窗口（v0.55.0），自 v0.56.0 起已移除；此错误提供改写方式。

<a id="the-mechanical-rewrite"></a>

## 机械改写

```almide
list.try_map(xs, f)      →  list.map(xs, (x) => f(x)!)!
list.try_filter(xs, p)   →  list.filter(xs, (x) => p(x)!)!
list.try_fold(xs, z, f)  →  list.fold(xs, z, (a, x) => f(a, x)!)!
// find / each / flat_map / filter_map are the same shape
```

<a id="the-internal-carriers-are-not-the-escape-hatch"></a>

## 内部 carrier 不是绕过方式

公开名称移除后，函数体保留为 `list.__fallible_map` …，这是回调传播时 checker 为你实例化的形式。有一个版本允许从源码访问它们：`list.__fallible_map(xs, f)` 能编译运行，且没有警告。这并未移除第二种写法，只是将其重命名；对编写者而言，比弃用名称更糟，因为有两种可用写法，却只记录一种，也不说明哪个是正式形式。此后，在源码中指名 carrier 也会产生同样的 E043。

carrier 仍然存在并运行，只是不再允许在源码中写出。

同样规则也涵盖后来加入可失败形式的 fs 流式 walker（#1144，契约 C-274）：`fs.__fallible_fold_lines` 与 `fs.__fallible_for_each_line` 是脱糖目标，不是源码写法。它们从未有过公开 `try_` 名称——入口从一开始就不对外开放。

```almide
fs.fold_lines(path, z, (a, l) => f(a, l)!)!   // ✓ the blessed spelling
fs.for_each_line(path, (l) => f(l)!)!         // ✓
fs.__fallible_fold_lines(path, z, f)          // ✗ E043
```

两个分区处理项（`fs.fold_lines_range` / `fs.fold_lines_chunked`）完全没有可失败形式：分区遍历没有定义首个错误，因此也没有需要隐藏的 carrier。

<a id="diagnostic"></a>

## 诊断

```
error[E043]: list.try_map was removed — the core HOF is fallibility-polymorphic (ADR-0006)
  try: list.map(xs, (x) => f(x)!)!

error[E043]: list.__fallible_map is an internal carrier, not a spelling — source may not name it (ADR-0006)
  try: list.map(xs, (x) => f(x)!)!

error[E043]: fs.__fallible_fold_lines is an internal carrier, not a spelling — source may not name it (ADR-0006)
  try: fs.fold_lines(path, z, (a, l) => f(a, l)!)!
```

<a id="why"></a>

## 原因

`try` 是借用词，但来源语言的含义不一致（Rust 的 `try_fold` 是短路；Swift/Zig 的 `try` 是传播，即 Almide 的 `!`）。每种策略一套对应函数，会使公开接口按策略 × 组合器扩增。每个组合器一个名称，由回调中的 `!` 携带策略，这是 Swift SE-0413 的模型。

关闭 carrier 的理由也一样：`try_*` 的成本从来不是这个词，而是编写者必须选择。`__` 前缀不会消除选择，只会隐藏其中一项；读过 `stdlib/list.almd` 的模型会生成隐藏的形式。

<a id="fix-it-verdict"></a>

## Fix-it 判定

**mechanical** — try_* 改写表是精确的。单独 fn 引用作为回调的形式（`list.try_map(xs, f)`）会被机器应用（#1486）：回调包装为 `(x) => f(x)!`，并保留 Result carrier 类型（没有末尾 `!`，解包仍由调用者决定）。lambda 回调需要修改其函数体，因此仅提供提示。（`mechanical` = 无人值守的修复器可以应用改写；`conditional` = 建议的修复需要审查；`not-fixable` = 不存在自动改写。#1486 的适用性原则。）
