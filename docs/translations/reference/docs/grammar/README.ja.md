# 公開 Almide 文法

[![English](https://img.shields.io/badge/English-d0d7de?style=flat-square)](README.md) [![日本語](https://img.shields.io/badge/%E6%97%A5%E6%9C%AC%E8%AA%9E-24292f?style=flat-square)](README.ja.md) [![简体中文](https://img.shields.io/badge/%E7%AE%80%E4%BD%93%E4%B8%AD%E6%96%87-d0d7de?style=flat-square)](README.zh-CN.md)

`almide.lark` は機械可読な Almide 文法である。その目的は一つ、**デコード時の制約エンジン**のためだ。[llguidance](https://github.com/guidance-ai/llguidance)、[XGrammar](https://github.com/mlc-ai/xgrammar)、OpenAI custom tools（Lark CFG 入力）は、利用可能な CFG があって初めてトークンサンプリング時に構文の妥当性を強制できる。この成果物は生成前に一部の不正なトークン列を排除できるが、意図的にコンパイラ構文の上位集合となっている。不正な Almide プログラムをすべて表現不可能にするものではない。制限と検証済みの否定例は以下に記す。

この方式の根拠：CangjieBench（arXiv 2603.14501）では、低リソース言語において構文制約付き生成が精度とコストの最善のトレードオフである。CRANE（arXiv 2502.09061）では、制約するのは*出力*であり、推論ではない。

## ファイル

| ファイル | 内容 |
|---|---|
| `almide.lark` | 文法成果物（Lark 構文、Earley + basic lexer） |
| `negative-fixtures.txt` | 文法が拒否しなければならない不正なプログラム |
| `../../scripts/check-lark-grammar.sh` | 陳腐化防止ゲート |
| `../../scripts/lib/lark-gate.py` | ゲートの実装 |

<a id="using-it"></a>

## 使用方法

```python
from lark import Lark
parser = Lark(open("docs/grammar/almide.lark").read(),
              start="start", parser="earley", lexer="basic")
parser.parse(open("app.almd").read())
```

llguidance / XGrammar には、同じファイルをエンジンの Lark フロントエンドへ渡す。

<a id="the-anti-rot-gate--exactly-what-it-checks"></a>

## 陳腐化防止ゲートが正確に検査すること

手書きの文法はパーサが変わった瞬間に古くなり、古くなった文法は*ないより悪い*。デコーダを、コンパイラがもう受理しない言語へ制約してしまうからだ。これを防ぐのが `scripts/check-lark-grammar.sh` で、独立した三つの事項を検査する。

**1. 字句の一致。** `almide.lark` の `BEGIN-KEYWORDS` / `BEGIN-OPERATORS` マーカーブロックを、`crates/almide-syntax/src/lexer.rs` の `KEYWORDS` と `OPERATORS` の表とトークンごとに差分比較する。lexer にキーワードを追加してここへ追加しなければゲートが失敗し、その逆も同じである。`EXCLUDED` リストも双方向に検査する。除外演算子は依然として実在する lexer トークンでなければならず（そうでなければ除外が古い）、同時に文法へ宣言されていてもならない。

**2. コーパスの上位集合。** `spec/`、`examples/`、`stdlib/` 配下のすべての `.almd` を公開文法で解析する。文法が*拒否*する各ファイルについて、`almide <file> --emit-ast` 経由でコンパイラに問い合わせる。これは lexer と parser だけを実行する（型エラーでも終了コードは 0）。コンパイラが解析するのに文法が解析しないファイルがあれば、明確な失敗とする。

要求するのはこの方向だけである。文法は意図的に**上位集合**となっている。過剰受理はデコーダに損失を与えない（悪いトークンを阻止し損ねるだけ）が、受理不足は合法なプログラムをサンプリングできなくする。

**3. 識別能力。** `negative-fixtures.txt` のすべてのフィクスチャを、文法*と*コンパイラの両方が拒否しなければならない。これがなければ、`.*` に退化した文法も検査 2 を難なく通る。ゲートはフィクスチャ数の下限も強制する。

<a id="what-the-gate-does-not-prove"></a>

## ゲートが証明しないこと

- **健全性ではない。** 文法が妥当な Almide *だけ*を受理するとは証明しない。設計上、上位集合である。検査 2 が失敗するのは受理不足の方向だけであり、検査 3 が固定するのは `negative-fixtures.txt` 内の明示された反例だけである。
- **コーパス外の網羅性ではない。** `spec/`、`examples/`、`stdlib/` のどのファイルも使わない構文機能は検査されない。spec フィクスチャ*なし*で新しい構文が入ってもここでは検出されない。新構文を常に `spec/` テストとともに導入する理由が、もう一つあるということだ。
- **意味論については何も証明しない。** `--emit-ast` は構文解析のみであり、型、effect、モジュール解決、checker 全体は対象外である。
- **エンジン間の移植性ではない。** ゲートは Python の `lark`（Earley + basic lexer）を使う。llguidance や XGrammar がこの厳密な方言をコンパイルできるとは証明しない。それらは独自の制約を持つ Lark *風*構文を受理する。

<a id="known-gaps--what-the-grammar-cannot-express"></a>

## 既知の差分：文法で表現できないこと

これらは率直に示す制限であり、バグではない。成果物がコンパイラより*緩い*箇所では、デコーダは単にそこを制約されない。より*厳しい*箇所では、コーパス検査が示すのは、検査したコンパイラ受理済みファイルを排除していないということだけであり、すべての合法プログラムの網羅性は証明しない。

| # | 差分 | 方向 |
|---|---|---|
| G1 | **入れ子のブロックコメント。** `/* … */` は非貪欲な正規表現であり、lexer は入れ子の深さを数える。`/* /* */ */` では余分な `*/` が残る。 | より厳しい |
| G2 | **heredoc の字下げ除去。** `"""…"""` は単一の不透明な終端記号である。`strip_heredoc_indent` は構文変換でなく*値*変換なので、構文上は何も失われない。ただし成果物は閉じ区切りの字下げ規則を表現できない。 | 該当なし |
| G3 | **補間の穴。** `${…}` は*字句的に*照合され、入れ子の `"…"`/`'…'` リテラルと最大三段の `{ }` の入れ子を扱う。コンパイラは穴を再字句解析し、サブパーサで再解析するため、内容は完全な式である。そのためデコーダは**穴の中では制約されず**、波括弧三段より深い穴は拒否される。単一のテキスト上 CFG がコンパイラの二段階字句解析を再現できない唯一の箇所である。 | 両方向 |
| G4 | **空白に敏感な単項マイナス。** `a⏎- b` は減算を継続し、`a⏎-b`（密着）は新しい文を開始する。トークンレベルの文法には間隔が見えないので、両方の読み方を受理する。 | より緩い |
| G5 | **診断だけの制約。** `??` の改行越え規則（E038/#1112）、末尾の `??`（E038）、名前付き引数の後の位置引数、「最初のデフォルト引数以降のすべての引数にもデフォルトが必要」という規則はパーサの*診断*であり、文法ではない。成果物はこれらを受理する。 | より緩い |
| G6 | **予約された文脈依存識別子。** `as`、`where`、型名 `Fn` はコンパイラでは綴りで照合するが、lexer には通常の識別子である。成果物はこれらを予約するため、合法な Almide である `let as = 1` を拒否する。コーパスにこの使い方はない。`self` は意図的に予約*しない*（すべての convention メソッド本体で値となる）ため、型のないレシーバ引数を「最初の引数は `: Type` を省略できる」と表している。このため成果物は、コンパイラが拒否する `fn f(x) -> Int = 1` を受理する。 | 両方向 |
| G6b | **`scoped` は文脈依存であり、予約されていない**（#1997、ALS-E31）。G6 の三つとは異なり、`scoped` は成果物中でも識別子の意味を維持する。`SCOPED` 終端記号はすべての通常の名前の位置（`_ident`）で受理されるため、`let scoped = 41` や `match scoped { … }` も引き続き解析できる。成果物がコンパイラより*緩い*のは先頭部分だけで、ブロックまたは `fn` が続けば `scoped` を修飾子と読む。一方コンパイラは、さらに `{` が同じ行にあり、`match`/`while`/`for` の先頭部分の外であることを要求する。 | より緩い |
| G7 | **`fan.<head>`。** head 名は限定しない（任意の識別子）。現在のブロック head には `bounded`/`timeout`/`min`/`settle` があり、`race` と `any` はコンパイラが診断する廃止済みの綴りである。 | より緩い |
| G8 | **文の区切りが必要**（改行または `;`）。コンパイラは、一行に区切りなしで二つの文が隣接することを許す。成果物が区切りを要求するのは意図的であり、大きな曖昧さを取り除き、整形済み Almide はこの許容に依存しない。 | より厳しい |
| G9 | **算術演算の優先順位を平坦化している。** `\|>`、`>>`、`+ -`、`* / %`、`^` は一つのレベルを共有する。優先順位が形づくるのは解析*木*であり、受理するトークン列の集合ではない。Earley は各列で深さのコストを払う。結合力の正本は引き続き `grammar/precedence.toml` と `Parser::infix_bp` にある。真偽値、比較、範囲のレベルは分離を維持する。それらの非結合性は言語の事実だからだ（`a < b < c` と `0..<1..<2` はエラー）。 | 同等 |
| G10 | **廃止・拒否された綴りを除外する。** `&&`、`\|\|`、`++`、範囲としての `..`/`..=` をコンパイラが解析するのは、移行のヒントを返すため*だけ*である。成果物はこれらを除外し、デコーダは決してサンプリングしてはならない。 | より厳しい |
| G11 | **深さ制限がない。** パーサは式の入れ子を 500（`MAX_DEPTH`）に制限するが、成果物にはこの制限がない。 | より緩い |
| G12 | **モジュール修飾されたレコードリテラル**（`mod.TypeName { … }`）を、パーサが要求する単独の識別子の後だけでなく、任意の後置式の後に受理する。 | より緩い |
| G13 | **非 ASCII 名**（#1456）。コンパイラは UAX #31 識別子（XID_Start の後に XID_Continue、NFC）を受け入れ、互換文字（`ａ`、`１`、`ﬁ`）を拒否し、大文字小文字のない名前の区分は宣言で決める。`住所` が型名になるのは、`type 住所` または case `| 住所` を宣言したモジュール内だけである。成果物の `UNAME` は非 ASCII の字母（letter）で始まる任意の名前で、値と型の両位置で受理し、続きの `\w` は互換文字も受理する。 | より緩い |

<a id="relationship-to-the-grammar-submodule"></a>

## `grammar/` サブモジュールとの関係

[`almide/almide-grammar`](https://github.com/almide/almide-grammar)（`grammar/` サブモジュール）は、tree-sitter と VS Code の生成器が利用する、キーワード・優先順位・TextMate の*記述的*データを保持する。利用可能な CFG はなく、CI も取得しない。そのためこの成果物はコンパイラリポジトリに置き、ゲートが成果物と、それが写し取る lexer の両方へアクセスできるようにしている。`almide.lark` の優先順位に関するコメントは `grammar/precedence.toml` を参照する。両者が同じ正本 `Parser::infix_bp` を参照することで整合を保つ。
