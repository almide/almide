# 内存安全——哪些已证明，哪些受信任

[![English](https://img.shields.io/badge/English-d0d7de?style=flat-square)](MEMORY-SAFETY.md) [![日本語](https://img.shields.io/badge/%E6%97%A5%E6%9C%AC%E8%AA%9E-d0d7de?style=flat-square)](MEMORY-SAFETY.ja.md) [![简体中文](https://img.shields.io/badge/%E7%AE%80%E4%BD%93%E4%B8%AD%E6%96%87-24292f?style=flat-square)](MEMORY-SAFETY.zh-CN.md)

> [正本](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/design/MEMORY-SAFETY.md)的非规范历史参考快照，固定提交：35297a612fb29e3f78f6587aba253aa91d51f466。不自动同步。未在此独立重新验证安全、证明、测量或实现主张，也未运行验证命令。以正本为准。正文中的证书检查指所述证书与检查器机制，不表示第三方安全认证。

测量页面（[docs/benchmarks/README.md](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/benchmarks/README.md)）提供本文的一段式说明；本页是完整版本。所引用的已审计定理数量由 `proofs/check.sh` 计算并核对（对照 `proofs/TRUSTED_BASE.md`、`proofs/receipt.sh` 和测量页面），因此在那里引用，不在此重复。

你无需编写所有权注解、生命周期或 `free`——内存管理由编译器中的 [Perceus](https://www.microsoft.com/en-us/research/publication/perceus-garbage-free-reference-counting-with-reuse/) 式所有权推断决定：无需垃圾收集器、无暂停。推断计算每个堆值在何处引入、复制和消耗；各目标只在这些决定的执行机制上不同。交付证明的编译器有责任告知边界，以下便是：

**“内存安全”的含义。** 一个定义，经内核检查：[`proofs/MemorySafe.v`](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/proofs/MemorySafe.v)（#4013）。在堆轨迹上（每次分配、store、load、引用递增与递减都指明所属块），`MemorySafe` 包含四个条款：每次 load/store 位于其存活块内（空间）；不触碰已释放块，分配不交出存活块（时间）；读取的每个字节都在分配后写入过（初始化）；每次访问采用该块分配时的表示（类型）。轨迹检查器被证明对此既可靠又完备。以下证明达到**时间**条款（`rc_check_gives_temporal`），而 structural wasm 路径每次构建为所有 `xs[i]` / `b[i]` 访问输出的边界证书（#3345 可能省略检查，证书会重新推导）达到**空间**条款（[`proofs/SpatialCert.v`](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/proofs/SpatialCert.v)、`accepts_spatial`；证书事件确实对应字节中的访问，这一点每次构建对照已发布字节检查，#4011 (d)）。在源码层面，Almide 的一个带类型核心被证明在四个条款上均以 MemorySafe 方式运行（[`proofs/CoreSafe.v`](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/proofs/CoreSafe.v)、`typed_core_memory_safe`、#4014——只是一个核心，尚未与 lowering 绑定）。两个逐构建证书在同一轨迹上组合，可给出空间、时间和类型条款；若明确假设构造器纪律，则给出全部四个条款（[`proofs/Certified.v`](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/proofs/Certified.v)、`certified_with_bounds_cert`、`certified_memory_safe`）。尚无构建输出轨迹，因此此定义所服务的定理——逐构建检查器接受制品意味着制品为 `MemorySafe`——仍未解决：#4005（MIR 上的空间性质）、#4006（native）、#1696（structural wasm 路径）。计划与每项剩余缺口：#4011。

- **内核证明的检查器——针对 witness 所描述的 MIR 已证明。** **内核证明的检查器重新验证**的所有权证书（Rocq/Coq 主干，无额外公理，并经 `coqchk` 独立复查）确立：witness 所描述的 MIR 具有 RC 平衡——在建模片段中无重复释放、无泄漏——名字全域且 capability 有界。现在这些 MIR witness 仅由 `proofs/gate.sh` 与 `proofs/corpus-wall.sh` 判定：自 #2761 起，MIR lowering 不再产生 wasm 字节，所以 `almide verify app.almd` 改为判定 structural 路径的证书（#4011，见下文）。WasmEncode/WasmExec/WasmRcDec 定理同样针对模型化运行时（已退役的原有运行时）成立。证明涉及 IR 层面的 Inc/Dec 平衡，而非编译器内部；经证书检查的函数仍可能计算错误值，单独的 [跨目标契约台账](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/contracts/README.md) 和差分关卡就是为捕获此类问题而设。哪些流水线阶段已证明、哪些受信任、每个关卡主张什么及不主张什么，其精确边界见 **[proven-vs-trusted.md](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/contracts/proven-vs-trusted.md)** 中的图。
- **WebAssembly，structural 路径——在证书检查语料上逐构建检查，记录受信任。** 唯一的 wasm renderer（自 #1599 起默认，自 #2752/#2761 起为唯一路径，参见 [docs/wasm/](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/wasm/README.md)）在输出时记录证书（#1696，已关闭）：每帧一个所有权 witness，针对已发布 stock-WASI 字节的调用模式、名字全域性与 capability，以及每次索引运算符访问的 `bounds` witness（#4005）。`proofs/structural-wall.sh` 通过产品路径构建 `crates/almide-wasm/tests/golden/witness-fixtures.txt` 中的每个 fixture（954/954 已通过证书检查），在 bundle 中固定已发布文件的 SHA-256，并让提取出的检查器、Rocq 内核和 almide-verify 对每个 witness 达成一致。对 bounds 和 init witness，每次构建都会检查记录事件是否确为字节中的指令：`almide-anchor-check` 解码已发布模块本身，将每个定位事件与其指明的指令核对（#4011 (d)）；所有权 witness 的对应关系仍受信任。若 `almide-verify` 安装在编译器旁，`almide build --target wasm` 本身会记录证书，并在写入前让 verifier 判定；证书被拒绝时不写制品（`scripts/check-build-certifies.sh`）。其他证据是差分的（在 `wasm_cross` 语料上与 native 逐字节一致）及动态的（checked allocator，每夜）；其运行时 RC 和 allocator 字节由 `proofs/check-structural-bytes.sh` 对照 Coq 解码器模型 `StructuralDecode.v` 检查。
- **Native（Rust）——对 verified renderer 的程序逐构建检查，其余受信任。** `proofs/native-wall.sh`（#4006）以提取出的检查器、内核和 almide-verify 判定 verified native renderer 渲染的每个程序（958 个 `wasm_cross` 程序中的 106 个）的所有权证书，并将其固定到渲染出的 Rust 源码；其余程序回退到标准 codegen，不携带证书。同样的决定由 Rust 自身的所有权机制实现：编译器输出符合 Rust 所有权惯用法的代码，每个堆值由 Rust 的作用域结束 drop 释放。目前没有证明覆盖此路径；其证据是差分的（在契约语料上与 wasm 路径的输出逐字节一致）。在两个 renderer 间共享同一份经证书检查的 Perceus MIR，是 [native trust-spine ladder](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/roadmap/active/native-trust-spine.md)（[#764](https://github.com/almide/almide/issues/764)）的目标；共享的标量与列表操作已能从同一 MIR 渲染到两个目标。

## 缺口表（2026-10-24，#4011）

`MemorySafe` 的每个条款占一行（[`proofs/MemorySafe.v:165`](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/proofs/MemorySafe.v)；各条款为 `spatial_ev` :126、`temporal_ev` :132、`init_ev` :141、`type_ev` :147）。每格说明哪些**已证明**（内核检查、无额外公理的定理）、哪些**逐构建检查**（判定每次构建制品或证书的关卡及其方式），以及哪些**受信任**（没有任何检查）。structural 路径的“逐构建”指证书检查语料的 CI 构建（`proofs/structural-wall.sh`，trust-spine workflow）；`almide build` 本身不运行检查器；`almide verify app.almd` 按同一路径构建程序，写入同一个 bundle（`crates/almide-wasm/src/witness_bundle.rs`），文件存在时以 SHA-256 绑定到构建出的 `app.wasm`，并让 `almide-verify` 判定（#4011）。

| **TYPE** | 对 bounds 证书覆盖的访问**已证明**：`certified_with_bounds_cert`（`proofs/Certified.v:149`）在分配遵循布局时给出 `WellTyped`；`sited_alloc_ok`（`proofs/InitCert.v`）为每个属于记录位置的分配消除该假设——位置携带块的 header、slot 宽度、count 与表示。**受信任**：bounds witness 的块与 init witness 的位置描述同一块（两个 witness 通过记录纪律连接）；记录位置以外的分配；bounds witness 以外所有访问的表示（emitter 从类型检查过的 IR 得到的 `SliceTy`）。 | **受信任**：rustc 针对生成源码的类型系统。 | 对核心**已证明**。 |

此定义所服务的定理，即已发布制品 `a` 的 `K(c, a) accepts ⟹ MemorySafe a`，还依次需要三件事：为每个分配位置记录构造位置，而非仅列表字面量（全轨迹的 INITIALIZATION 与 TYPE，#4013——检查器及其定理已存在）；为索引运算符以外的堆访问提供证书（#4005）；以及检查记录事件就是字节中指令的翻译检查——在 structural wasm 路径上，bounds 和 init witness 已具备这种检查，包括 bounds 比较的操作数（`almide-anchor-check`，#4011 (d)），但仍以表示为信任边界；wasm 所有权 witness 的记录纪律及 native 路径（#4006）仍受信任。

Rust 提供的是零成本抽象（代价是所有权注解），而 Almide 提供**零注解**抽象：你不写注解，由编译器决定释放，重新验证这些决定的检查器已获证明（structural 路径输出 bundle；`almide verify` 与证书检查语料关卡在上述覆盖范围和信任限制内，检查所支持的 core 制品，而非 component）。

这一工作的起点是 Lean 4 **Perceus belt**（[`crates/almide-perceus-belt/`](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/crates/almide-perceus-belt)，截至 2026-08-27 有 41 个定理、0 sorry、由 CI 把关）：一个针对小型 IR 片段的所有权 pass 模型，证明的内容包括变换会为每次看到的分配输出 release（`allHeapFreed`——在建模片段中，每个堆绑定至少一个 `Dec`；更强的精确平衡谓词则由逐构建证书在真实程序上检查）。这是关于设计的、经过机械检查的证明；上述逐构建证书是在原有路径仍发布期间覆盖已发布制品的机制（该路径由 #2761 退役）。[规范](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/specs/perceus.md)

冻结的语言表面、符合性条款和破坏性变更政策见 **[docs/STABILITY.md](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/STABILITY.md)**（2026-08-20 宣布）；可测量稳定性标准见 [proofs/stability-closure.toml](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/proofs/stability-closure.toml)，每次 push 均报告。
