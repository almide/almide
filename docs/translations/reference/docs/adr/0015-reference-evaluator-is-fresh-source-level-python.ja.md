- **状態**: 採択済み（2026-08-21 に航空品質条項付きの Python として批准。**同日に Rust へ改訂** — 改訂節を参照。ファイル名は当初の slug を保持し、ADR ID とパスは恒久的）
- **日付**: 2026-08-20
- **背景**: QUALIFICATION.md の制限 2 — cross レッグが判定するのは真実ではなく一致であり、両ターゲットが同じように間違っていても見えません。[#10](https://github.com/almide/als/issues/10) はそれを埋める道具を名指します。このリポジトリが所有する参照評価器と、判定を *legs == ref* とする runner の `ref` レッグです。現在存在するものの実測:
  - このレッグが判定すべきコーパス: `spec/wasm_cross` の 592 fixture、`spec/programs`、`spec/wasm_cross_pkg`。これらは **478 種の stdlib 関数**を呼びます（`module.fn`。主なモジュールは int/list/string/bytes/value/float/regex/map/json/fs/set/fan）。
  - 唯一の機械化された意味論は λ_almd カーネルです（C-280、edit-locality belt、Lean 4.29、1,583 行、Mathlib なし）。**12 の式形式**（int/string リテラル、var、let、1 引数 call、ok/err、Result の match、`!`、`??`、print、seq）、関係に対して健全性が証明された fuel-indexed 評価器、そして**トレースが評価器で固定された 48 プログラム**の生成コーパス（実装リポジトリの `proofs/kernel-conformance/`）と表面 fixture `spec/wasm_cross/kernel_conformance.almd` があります。
  - 実装の第三の oracle `crates/almide-interp` は、コンパイラと parser、checker、lowering を共有する IR インタープリタです（10.8k 行）。前半の欠陥は 3 レッグすべてを同じように動かします。
  - 判定者の toolchain は Python 3 + bash で、`gates` にはコンパイラも cargo も Lean もありません。`tree-sitter-almide` はコンパイラの parser を手で維持する鏡像です（1,050 行の grammar.js、Rust binding のみ。drift は実装側で週次ゲート検査）。
  - ADR-0014 は既に出力の形を決めています。固定された期待値は道具で導出し、`spec/wasm_cross` の Roc 形式トレースは参照評価器の出力としてのみ現れます。
- **決定**:
  1. **規範本文から新しく書く。** 評価器は ALS の各章（`docs/specs/als/`、110 節）、言語文法（実装が `docs/GRAMMAR.md` として公開する EBNF を、ここでは判定者の parser 仕様として保持）、stdlib 仕様から書きます。`almide-interp` の評価規則を移植してはなりません。移植は実装の意味論を写し、検出すべき共漂流を残します。新しく読み解くことが、doctest の消化で起きたのと同様、仕様の穴を見つけます。
  2. **ソースレベル、独自 front end、抽象値。** 独自の再帰下降 parser で `.almd` ソースを解析します（コンパイラ crate なし、tree-sitter ビルドなし。第三の文法は独自の drift と、Python を使うゲートのリポジトリに native ビルド手順を加えてしまいます）。値は抽象的です（ALS に従い無制限から wrap する Int、String、List、Map、Set、Tuple、Record、Variant、Option、Result、Fn）。バイトヒープは持たず、判定者がモデル化するのはプログラムが*何を*観測するかであって、実装が*どう*配置するかではありません。
  3. **Rust（stable、固定）、独立 crate、ブラックボックスプロトコルの背後。** 評価器はこのリポジトリの crate `ref/` です。stable Rust のみ（`rust-toolchain.toml` が channel を固定し、nightly feature なし。そのため適格化済み toolchain — Ferrocene、[#18](https://github.com/almide/als/issues/18) — でも変更なしで再ビルド可能）、`almide-*` crate への依存なし（ゲート検査）、依存関係はゼロまたは精査した少数に保ちます。runner は決してリンクせず、REF PROTOCOL を呼びます。`<ref> run <file.almd> --json` が `{"exit": n, "stdout": s, "stderr": s}` または `{"abstain": {"class": c, "reason": r}}` を出力します。そのため任意の言語の評価器（対象断片についてのコンパイル済み Lean 評価器、将来の移植）を差し込め、判定者との接点は実装ではなくプロトコルです。（改訂 — 最初の批准は Python でした。1 行も書く前に変更した理由は後述。）
  4. **λ_almd を種とし、初日から 100%。** 48 のカーネルプログラムと `kernel_conformance.almd` が最初の oracle です。他を判定する前に、評価器で固定されたそのトレースをバイト単位で再現しなければなりません。その一致は CI が永久に守る 1.0 の下限です（#10 の「λ_almd 一致率」。fragment gate を種とし、カーネルの成長とともに増えるだけです）。
  5. **辞退によって正直にする。** 評価器が未実装のものはすべて、class（`stdlib:<module.fn>`、`syntax:<form>`、`runtime:<capability>`）付きの ABSTAIN とし、`proofs/ref-abstain.toml` に fixture ごとに記録します。分類付きで縮小のみを許し、辞退は合格でも不合格でもありません。無言の fallback は禁止です。
  6. **レッグの判定は *legs == ref*。** 評価器が評価する fixture では、native と wasm はそれぞれ参照の観測値（exit、stdout、stderr、`cross` と同様に trim）と一致しなければなりません。両ターゲット間の一致だけでは不十分です。辞退した fixture は従来の一致判定を維持し、辞退を数えます。各契約に reference-backed 属性（全 fixture を評価済み）を付け、README generator が増加のみを許す比率として表示します。
- **根拠**: 参照の価値は独立性です。ここで独立性を得るのは、厳密に一度に 1 次元ずつです。独立した front end（文法からの第二の parser）、独立した意味論（ALS 本文の第二の読解）、独立した stdlib（stdlib 仕様からの第二の実装）。却下した選択肢はいずれも、便宜のためその 1 つを手放します。Python は小さなプログラムの tree-walker を置く最も安価なホストで、判定者を `python3` だけで導入可能に保ちます。プロトコルにより言語選択を覆すコストは再設計ではなく移植になります。カーネルコーパスから始めるので、評価器が最初に正しく扱うべき 49 プログラムは、期待トレースが一致によるものではなく*証明済み*のものです。これは今日、両リポジトリのいずれにおいても、一致ではなく真実を得られる唯一の場所です。
- **代替案**:
  (a) *Lean の λ_almd belt を表面全体に広げる* — 実行可能レッグとしては却下。表面全体の機械化は研究級（#10）です。belt は機械化された種として残し、一致 ratchet が両者を結びます。(b) *新しい parser の背後へ `almide-interp` の規則を移植する* — 検査対象の意味論を写すので却下。(c) *front end に tree-sitter-almide を使う* — 独自に drift する第三の手作業保守の文法、Python ゲートのリポジトリでの native ビルド、コンパイラが拒否するものを受理する parser となるため却下。(d) *まず Python* — 当初の批准でしたが、同日の下記改訂で置き換えました。切り替えコストがゼロなら、到達可能な上限の高い選択肢が勝ちます。(e) *手で選んだ部分集合だけを判定する* — 却下。abstain 台帳はすべてを判定し、何を省いたかを示します。
- **航空品質条項**（決定とともに批准。各項目は指針ではなくゲート — 改訂で Rust 向けに再記述）:
  1. *決定性。* 評価器はホストの順序に依存しません。Map/Set の反復は常に ALS が規定する順序に従い、ホストの順序には従いません。`HashMap`/`HashSet`（プロセスごとにランダムな反復順）は禁止型です（`clippy.toml` の `disallowed-types`）。順序付き構造だけを使います。ゲートはコーパスを 2 回実行し、トレースと判定のバイト一致を要求します。
  2. *全域性または辞退。* 構文的全域性は構成によって得ます。すべての AST node 種類は variant で、AST へのすべての `match` は網羅的です（形式を忘れるとコンパイラが拒否）。未実装の形式は class 付きの明示的な `Abstain` arm であり、wildcard にはしません。stdlib の全域性は測定します。判定するコーパスが呼ぶすべての `module.fn` は、実装済みか `proofs/ref-abstain.toml` 内にあるかのどちらかです。実行時の未処理呼び出しは評価器の失敗（プロトコルエラー）で、無言の合格ではありません。ゲートは両表を列挙し、穴があれば失敗します。
  3. *評価器自身の mutation testing。* crate に `cargo-mutants` を実行し、kernel + cross コーパスで判定します。kill rate は悪い方向への変化を許さない ratchet とし、生き残りを列挙します（edit-locality 調査では 12 の法則中 mutation を第一位に挙げています）。
  4. *固定した適格化可能な toolchain — Ferrocene を追跡。* `rust-toolchain.toml` は現在の Ferrocene リリースの基となる upstream stable 版を固定します（批准時: Ferrocene 26.05.0 == Rust 1.95.0。subscription 自体は #18 の資源項目）。そのため stock rustc から `criticalup` で導入した Ferrocene への変更は CI 手順の変更だけで、コードや版の変更は不要です。nightly feature は使いません。toolchain の版を candidate binary・platform とともに適合声明へ記録します。固定版を動かすのは Ferrocene リリースと同時だけです。
  5. *規定された意味論をホストへ委譲しない（ホスト多様性条項）。* native ターゲットは Rust `std` 上で動きます。参照側が `string.split` を `str::split` と書けば、実装とホストの意味論を共有し、一致は ALS 本文でなく共有ホストを測るものになります。したがって ALS が自ら挙動を規定する std 操作（文字列の分割・trim・case、float の整形と解析、整数解析、sort/ordering、collection の反復順、hashing）は**禁止メソッド**です（`clippy.toml` の `disallowed-methods`）。評価器は ALS 本文から char/byte primitive 上にそれらを書きます。wasm ターゲット（self-hosted Almide）は真に別のホストのままなので、三者の投票に 1 本の無関係なレッグを保てます。
  6. *実装からの独立性。* crate の `cargo tree` に `almide-*` crate は現れず、実装リポジトリへの path/git 依存もありません（ゲート検査）。
- **改訂（2026-08-21、評価器コードが存在する前）**: 最初の批准は Python を選びました。DO-330 は TQL-4/5 検証ツールのコンパイラの適格化を要求しない（実際に要求せず、主張はツール自身の検証、条項 1–4 に基づく）ことと、Python ホストが N-version の多様性を加えることが根拠でした。主張の段階表（[#9](https://github.com/almide/als/issues/9)、[#18](https://github.com/almide/als/issues/18)）に照らして再判定すると、信頼性の上限が違います。参照評価器が適格化済み toolchain で再ビルド可能な stable Rust crate である判定者は、CPython script より将来の reviewer に対して強い主張になります。Rust は構文的全域性を構成によって与え（Python では測定しかできなかった唯一の条項）、失うホスト多様性は規律でなく構造的ゲート（条項 5）で回復可能です。Python の利点は執筆速度と toolchain 不要でした。実在する利点ですが、変更は書き直しでしかできません。コードはゼロ行だったので切り替えコストもゼロであり、上限の高い選択肢を採りました。変更しなかったもの: 規範本文から新しく書くこと、独自 front end、抽象値、ブラックボックスプロトコル、1.0 の λ_almd seed、abstain 台帳、判定規則。`gates` に crate 用のキャッシュ付き cargo 手順が加わります（header は「コンパイラなし」とは言わなくなります）。
- **撤回条件**: (1) コーパスでの評価器の実時間が cross レッグ自身を上回る — 間違っているのは言語ではなく設計。(2) abstain 台帳が 2 リリースにわたり縮小しない — その場合、障害は評価器でなく stdlib 仕様の穴であり、章の負債として #10 に送る。(3) カーネル一致の退行 — 定義上、評価器が間違っている（カーネルは証明済み）のであり、逆ではない。
- **帰結**: `ref/`（独立 crate: lexer、parser、評価器、stdlib、プロトコル CLI `ref run <file> --json`）。`scripts/check-ref-*.sh` ゲート（kernel 一致 1.0、独立性、lint、全域性、abstain 台帳、mutation ratchet）。`--ref` コマンド付きの `scripts/conformance.py --legs ref`。ref の各判定 class に対する `selftest-conformance.py` シナリオ（ref pass、native ≠ ref、wasm ≠ ref、互いは一致するが両方 ≠ ref — 共漂流 class —、abstain の計上、不正なプロトコル出力は赤）。`proofs/gate-verification.toml` の 1 行。`proofs/ref-abstain.toml` は縮小のみ。カーネルコーパスを generator commit の記録付きで `proofs/kernel-
  conformance/` に保持します（再生成し、決して編集しない。ADR-0014）。`spec/wasm_cross` の Roc 形式 `.expected` トレースが可能になるのは、その fixture の abstain 集合が空になってからだけです。ADR-0014 の条件に、道具の名前が付いた形です。

## 原本に関する注意

当初のファイル名、Python を根拠とする説明、「コンパイラなし」の背景は歴史的記述として残る一方、同日改訂は Rust を選び、キャッシュ付き cargo 手順を加えています。黙って整合させず保持します。48 のカーネルプログラムと 1 つの表面 fixture、1.0 の一致下限、抽象値モデル、明示的な辞退が記載された範囲を定めており、レッグ間の一致もこの読者版も、言語全体の真実や成果物全体の安全性を立証しません。航空品質条項はこの採択設計で必須ゲートとして提案されたものであり、ツール適格化や認証の完了証拠ではありません。Ferrocene 版、コーパス規模、リポジトリ・toolchain の説明は当時の原本の主張です。「このリポジトリ」と判定者側のパスは、原本の判定者と実装の区別を保持し、この翻訳によって評価器やゲートを作成することはありません。固定原本に独立した付録はなく、全条項・改訂・撤回条件・帰結を収録しています。
