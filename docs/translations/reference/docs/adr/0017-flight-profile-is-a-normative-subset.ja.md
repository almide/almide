# ADR-0017: bounded プロファイル（旧称「flight プロファイル」）は言語の規範的な部分集合であり、チェッカーによる強制に先立ってここで規定する

> [英語の正本](https://github.com/almide/almide/blob/35297a612fb29e3f78f6587aba253aa91d51f466/docs/adr/0017-flight-profile-is-a-normative-subset.md)（固定コミット `35297a612fb29e3f78f6587aba253aa91d51f466`）の非規範的な読者用スナップショット。元の ADR が正本であり、変更しない。この写しは自動同期されず、チェッカーや生成器の入力ではない。以下の決定、日付、測定値、実装状態、主張は固定した当時の原文を伝えるもので、独立検証や現行リリースの保証ではない。コードブロックとそのコメントは原文のまま保持する。

> 原文の注意点：ここでの requirements-first の決定、拒否診断、ビルドごとの所属証明は当時の規範的意図であり、全チェッカーや cert seat の実装、または外部認証・適格性評価を示す証拠ではない。Float の除外を緩和できるのは記された両前提の成立時だけであり、明示された残存制限も維持する。

- **状態**: 採択 — 2026-08-21 に裁定（[#29](https://github.com/almide/als/issues/29)）。修正は一つだけ：**プロファイルは業界ではなく、与える保証で名付ける。** *bounded プロファイル* — 静的に上限のある時間とメモリ、閉じた呼出しグラフ、ケーパビリティで制限された effect — とし、マーカーは `@bounded`、章は `bounded.md`、接頭辞は `B`（`ALS-B<n>`）とする。`@flight` は言語に現れない。「flight」は QUALIFICATION.md と実装側ロードマップで動機となる文脈として残る。⚖ 3 と ⚖ 4 は原案どおり批准し、⚖ 5 は名称変更付きで批准した。ファイルの slug は元の語を維持する（ID とパスは恒久的。ADR-0015 の先例）。以下は修正後の決定であり、実装文書が旧名を使っている箇所では元の名称を引用する。
- **日付**: 2026-08-21（提案と採択は同日）
- **背景**: 航空用途のコードは言語の部分集合 — MISRA C、Ada Ravenscar、SPARK — で書かれ、認証プログラムが実際に適格性を評価するのもその部分集合である。実装側は Almide の部分集合を設計済みである（flight-subset-spec.md、flight ladder の G-F1）：回数が決まったループのみ、ループ内確保なし、上限のある静的確保、再帰なし（呼出しグラフの非巡回性）、クロージャー／高階／`any P` ディスパッチなし、ケーパビリティで制限された effect、`break`/`continue` は対象外、Float も暫定的に対象外。属性（その設計では `@flight`、ここでは `@bounded` — 状態欄参照）により関数単位で強制し、部分集合への所属はレビュー担当者が確認するのでなく、ビルドごとの証明書が証明する。現時点でこの設計は実装側だけにあり、`ALS-<id>` 節も contract も fixture もない。つまり、まだ言語の要件ではなく、言語の要件として引用できない。CONTRIBUTING.md の順序では振る舞いをまずここに置く。このプロファイルはロードマップ上で最大の該当項目であり、来歴が最も慎重に読まれるものでもある（QUALIFICATION.md の制限 7）。修正に影響した事実がもう一つある。部分集合の規則は航空機固有ではない。回数が決まったループ、上限のある確保、再帰禁止、閉じた呼出しグラフは、組込み、リアルタイム、サンドボックス、ゲームのコードにも等しく役立つ。属性に業界名を含む汎用言語は、顧客を文法に漏れ込ませてしまっている。
- **決定**: bounded プロファイルは、このリポジトリで規定する**規範的な部分集合**とする。接頭辞 `B` を持つ新しい ALS 章 `bounded.md` を STANDARD.md に登録し、仕様を先に、強制を後に行う。
  1. **方言ではなく部分集合。** すべての `@bounded` プログラムは有効な Almide プログラムであり、属性の有無によらず観測可能な振る舞いが同じである（SPARK ⊂ Ada）。fixture 群はまさにこれを表明する：`spec/wasm_cross` の各プロファイル内プログラムは、属性あり／なしでバイト単位で同一に実行される。
  2. **所属はチェッカーの判定であり、その判定が要件である。** 部分集合の各 OUT 規則と RESTRICTED 規則を `ALS-B<n>` 節とし、観測可能な事項を記す：X を行う `@bounded` 関数は、固定した診断コードで拒否される。`tests/diagnostics/<case>/` に対応する `broken.almd` / `fixed.almd` の組を置く（拒否の表面も言語の一部 — README の「tests/diagnostics」）。
  3. ⚖ **flight-subset-spec.md §2 の IN/OUT 表を初期の規範内容として採用する。** 解決済みの未決事項も含む：ループ内 `Dup` は IN、`break`/`continue` は OUT（正確な上限、MISRA の単一出口）、再帰は呼出しグラフの非巡回性によって OUT とし、未知の呼出し先は保守的に拒否する。入れ子の回数指定ループは積の上限付きで IN。各行を一つの節とする。未（強制が未実装）と記された行も今規定する。これこそ requirements-first の意味であり、実装側の pin を進めることで green にする。
  4. ⚖ **ADR-0016 の family が規範となり、かつ cert seat が float 演算セットを持つまで、Float は bounded プロファイルの対象外とする。**（現時点の MIR に `FloatOp` はない。）節には直説法でそう記す（「Float 演算を行う `@bounded` 関数は E… で拒否される」）。両方の前提が成立したとき、黙って緩和せず、節を改訂する。
  5. ⚖ **属性は関数単位で、保証に基づく名称とする。** `fn` / `effect fn` に `@bounded` を付け、モジュール単位の綴りは糖衣とする。`@bounded` 関数が呼べるのは `@bounded` 関数と純粋な stdlib モジュールの一階メンバーだけである（閉じた呼出しグラフ — 非巡回性とケーパビリティの証明の前提）。コンパイルフラグを仕組みとしては用いない（インポートした上限なしのコードまで判定に巻き込むため）。`flight` という語は言語のトークンではない。
  6. **flight-subset-spec.md §6 の率直な残課題**（有界再帰、固定小数点／決定的 Float、静的サイズ配列、バイト単位のメモリ上限、`≤ B` の早期脱出、読めるレイアウト、機能的正しさのトレーサビリティ）は、QUALIFICATION.md と同じ形式の明示的制限一覧として章に記録する。部分集合がまだ表現しないものを、主張と誤認させないためである。
- **根拠**: (1) DO-178C の credit はこの部分集合についてのみ主張する（flight-qualification.md §1：「DAL-A for the flight subset」）。要件でない部分集合は credit を担えない。(2) 所属を証明書で証明する設計はプロジェクトの差別化要因だが、証明には証明すべき命題が必要である。その命題が `ALS-B` 節である。(3) 拒否の壁より先に節を入れることだけが、プロファイルの来歴を `requirements-first` にする。後から入れれば、最も厳しく精査される要件が `retroactive` になる。(4) 診断コーパスによる強制は、チェッカーがまだなくても、初日から各 OUT 規則を実行可能な証拠にする。どの実装にもゲートがない段階でも、判定器は再帰する `@bounded` 関数を受理した実装を不合格にできる。(5) 名称について：プロファイルはコードについての約束であり、その約束は有界性である。特定の買い手にちなんで名付けると、ほかのすべての買い手にとって不適切で、汎用文法にも不似合いになる。
- **代替案**: (a) 部分集合を実装設計のままにし、チェッカーが強制してから規定する — 却下：評価者が最初に読む要件そのもので、2 PR の順序を逆転する。(b) 属性でなくコンパイルフラグ（`--flight` / `--bounded`） — flight-subset-spec.md §4 で却下（インポートした stdlib を巻き込む。強制の最小単位は関数）。(c) 独自文法を持つ別方言 — 却下：方言でなく部分集合にすることは SPARK/MISRA の教訓であり、双方で一つの判定器を維持する条件である。(d) 設計の綴り `@flight` を維持する — 裁定時に却下：業界は性質ではない。`@bounded` は証明する内容を名付ける。
- **帰結**: 新しい章 `bounded.md`、STANDARD.md の新接頭辞行 `B`、約 15–20 の `ALS-B` 節と各節一つの contract、各 OUT 規則の診断ケース、部分集合であって方言ではないという法則のクロスターゲット fixture 群。実装側の G-F1 は「設計して強制する」ではなく「判定器を green にする」作業となる。各節がレビュー行と一緒に入らなければ、`proofs/als-validation.toml` の `unvalidated` 上限は新しい節の数だけ上がる。PR ではどちらを選ぶかを見える形で示さなければならない。
- **反証条件**: 属性の有無で振る舞いが変わる `@bounded` プログラムがあれば規則 1 は反証され、間違っているのはプログラムではなく章である。認証評価者（#15）がモジュール全体またはプログラム全体を強制単位として望めば、規則 5 は覆る。ADR-0016 の family が規範になる前に cert seat に Float 演算セットが入ることは、規則 4 を緩和する理由ではなく、プロセス違反である。
