<a id="context"></a>

## 背景

Almide のランタイム側は、信頼できない入力でも文書化した範囲内で値、定義済みのエラー、または定義済みの中止に至ると約束している。コンパイラには同様の約束がないが、常に信頼できない入力を処理している。

- プルリクエストの CI。
- ファイルを開いた時点で動く LSP。
- 採点器やモデル評価ハーネス（Dojo）。
- プレイグラウンド。

2026-10-24 のレッドチームのラウンドで計測したもの：

| 形 | 上限があるか | 計測結果 |
|---|---|---|
| 式 / リストのネスト `((((…))))` | はい、「nesting too deep (max 500)」 | 深さ 50,000 で 0.06 s、48 MB |
| `let t(i) = (t(i-1), t(i-1))` | **いいえ** | 深さ 22：3.7 GB、深さ 39：5.4 GB で停止（#4114） |
| ジェネリックな `fn dup[T](x: T) -> (T, T)` を通した同じ倍増 | **いいえ** | 深さ 18：295 MB、1 行ごとに ×2 |
| 網羅性検査用の幅 24 のタプル `match` | はい、横ばい | 0.02 s、23 MB |

他のコンパイラは、こうした形に事後的・個別に上限を設ける。以下は背景情報にすぎず、この ADR はその数値に依存しない。

- Rust の `recursion_limit` と `type_length_limit`。**ソース**が `#![...]` で引き上げられる。
- TypeScript の「type instantiation is excessively deep」。
- Swift の時間に基づく「expression too complex」。
- GHC の `-freduction-depth`。

それらのいずれも同時には提供しない、と原文が挙げる三つの性質：

- すべてのフェーズに上限がある。
- ソースから上限を変更できない。
- 判定がマシンに依存しない。

<a id="decision"></a>

## 決定

**D1. 予算表を一つにする。** 入力に応じて増大するすべてのフェーズに名前付きの予算を設け、到達時の診断とともに一つのレジストリへ置く。このレジストリは `ALMIDE_*` スイッチレジストリ（#2205）と並ぶもので、`docs/specs/cli.md` にレンダリングする。初期の行は次の通り。

- 構文のネスト。
- 推論された型の大きさ（ノード数）。
- プログラムごとのジェネリック具体化数。
- 網羅性検査の作業量。
- マニフェストとロックの大きさ。
- 依存関係の数と深さ。

**D2. 時間ではなく数を測る。** 予算はノード、具体化、バイトまたはステップを数え、秒や空きメモリは使わない。同じ入力は同じ判定になる。

- どのマシンでも。
- ネイティブと wasm 上で動くコンパイラでも。
- CLI と LSP でも。

（「空きメモリに追従する判定」という教訓を参照。）

**D3. ソースから予算を引き上げられない。** 予算を変更する属性、マニフェストのキー、ロックの項目はない。コンパイラを実行する人は `--budget NAME=N` で変更できる。`--profile critical` はこのフラグを拒否する。環境変数でも予算を変更できない。これは #4129 に従う。

**D4. 予算超過は定義済みの診断になる。** ソース位置、測定値、予算、および修正を行うモデル向けのヒントを持つ E-code とする。例えば「type too large (N nodes, max M): name the intermediate type or use a record」。クラッシュ、メモリ不足による強制終了、ハングにはしない。

**D5. まず構造、最後に予算。** 表現方法で爆発的な増大を不可能にできるなら、その方法を使う。型を共有する（hash-cons または arena-intern）ことで `(t, t)` のコストを O(1) にする。診断中の型表示では繰り返す構造を省略する。予算は、構造で防げないものに対する最後の防御となる。

**D6. 予算は計測から決める。** 各値は `spec/`、`stdlib/`、演習コーパス、Dojo のタスク群で観測した最大値の約 10× とする。計測スクリプトと出力をコミットする。原文の設計上の主張は、モデルが書いたコードは予算に到達せず、敵対的入力だけが到達するというもの。

**D7. ゲート。** CI は既知の爆発的増大の形ごとに生成器を動かす（#4114 の倍増、そのジェネリック版、ネスト、幅広い match、長い補間の連鎖、多数の import）。そして二つを検査する。

- それぞれが予算の診断によって終了する。
- 各生成器の範囲内で、`almide check` が数える作業量の増大はソースサイズに対して最大でも線形となる。

負の対照：型共有と型サイズ予算を無効にすると #4114 の生成器が予算を超え、ゲートは失敗する。

<a id="consequences"></a>

## 帰結

- 行 9 のランタイム上限と組み合わせて、「Almide にどのような入力を与えても、文書化された範囲内で定義済みの結果に至る」という主張を、プログラムからツールチェーンに拡張する。
- 予算は互換性の対象となる。引き上げは追加的な変更だが、引き下げは以前コンパイルできたコードを拒否し得るため、`proofs/dialect-epochs.toml` の項目が必要になる。
- LSP や採点器は、資源枯渇対策のための OS レベルのサンドボックスなしで信頼できないソース上で動かせる、という帰結を掲げる。副作用からの隔離は別の問題（#4128）。

<a id="rulings-2026-10-27"></a>

## 裁定（2026-10-27）

1. D6 の値は計測する。`scripts/measure-compile-budgets.sh` が `proofs/compile-budgets.toml` を書き、各新規既定値はコーパス最大値の約十倍となる。この ADR より前からある二つの予算は以前の値を維持する。`nesting` は 500（コーパス最大値 33 の 15×）、`manifest_bytes` は 1 MiB のまま（#4194）。
2. 予算表は一つの仕様表（`almide budgets --md`、`docs/specs/cli.md` に埋め込み）とし、単一の契約 C-440「表中のすべての予算が守られる」を持つ。
3. `almide fmt` はこの表を共有する。パースだけを行うため、適用される予算は `nesting`。
4. 「関数ごとの出力コードサイズ」は D1 から外す。出力コードは IR に対して線形であり、その IR はすでに `nesting` と `type_size` が制限する。
5. D5 は予算の代わりではなく、予算とともに導入する。複合型は引数リスト（`almide_types::TyVec`）を共有する。clone はポインターのコピーとなり、各リストはノード数と推論変数を含むかをキャッシュする。解決処理は変数ごと、および共有リストごとにメモ化する。型サイズ予算の制限を外した状態では、#4114 の連鎖はその長さに対して線形の時間とメモリで検査できる（`tests/compile_budget_test.rs`）。負の対照である `ALMIDE_CONTROL_NO_TYPE_SHARING` は、clone のたびに再び木全体をコピーさせる。
