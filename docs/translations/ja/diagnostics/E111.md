# E111 — 型が大きすぎる

[English](../../../diagnostics/E111.md) | [日本語](../../ja/diagnostics/E111.md) | [简体中文](../../zh-CN/diagnostics/E111.md)

> 原文：[`docs/diagnostics/E111.md`](https://github.com/almide/almide/blob/9a95b28519b90ae535dc9918bfed04805dc4675c/docs/diagnostics/E111.md)、固定コミット `9a95b285`。読者向けの非規範的な翻訳であり、CLI の診断出力は英語のまま。

推論された型が `type_size` コンパイルコスト予算（ADR-0030）を超えた。コンパイラが1つの型に構築する上限より多くのノードを持っている。型は内部の型のコピーごとに大きくなるため、数行で指数的な大きさを要求できてしまう。

```almide
effect fn main() -> Unit = {
  let t0 = 1
  let t1 = (t0, t0)
  let t2 = (t1, t1)
  // ... each line doubles the type: t22's has 4 million leaves
  println("ok")
}
```

```
error[E111]: type too large (257+ nodes, max 256)
```

引数を2回返すジェネリック（`fn dup[T](x: T) -> (T, T)` に対して `dup(dup(dup(x)))`）でも同じことが起こる。チェッカーは推論中に構造を共有し、共有構造を展開して表す時点で予算がコピーを止める。

## 修正

中間の型に名前を付けるか、段階ごとに型が大きくならないレコードやリストにデータを保持する。

```almide
effect fn main() -> Unit = {
  let t0 = 1
  let t1 = [t0, t0]
  let t2 = t1 + t1   // List[Int], however long it gets
  println("ok")
}
```

## 理由

コンパイラは信頼できないソースを処理する。PR の CI、ファイルを開いたときの LSP、採点システム、playground などである。予算導入前は、この形の22行で `almide check` が 3.7 GB に達していた（#4114）。予算は秒数やメモリではなくノードを数えるため、どのマシンでも判定が同じになる。ソース側から引き上げることはできず、そのための属性、manifest キー、環境変数はない。コンパイラを実行する人は `--budget type_size=N` で引き上げられる（`almide budgets` が全予算を一覧表示する）が、`--profile critical` はそれを拒否する。

フィクスチャ：`tests/diagnostics/e111-type-doubling-chain`、`e111-type-doubling-through-a-generic`。ゲートは `tests/compile_budget_test.rs`。
