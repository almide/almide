# E085 — 標準ライブラリ外での `@intrinsic` または `prim.*`

[English](../../../diagnostics/E085.md) | [日本語](../../ja/diagnostics/E085.md) | [简体中文](../../zh-CN/diagnostics/E085.md)

> 原文：[`docs/diagnostics/E085.md`](https://github.com/almide/almide/blob/9a95b28519b90ae535dc9918bfed04805dc4675c/docs/diagnostics/E085.md)、固定コミット `9a95b285`。読者向けの非規範的な翻訳であり、CLI の診断出力は英語のまま。

`@intrinsic("almide_rt_…")` と `@wasm_intrinsic` は fn 名を直接 runtime シンボルに結び付け、`prim` モジュールは標準ライブラリがその上に書かれる基本層（生の load/store、allocator、`fd_write`、ホストファイル呼び出し）である。どちらも runtime 境界であり、標準ライブラリ自身のソース、つまりコンパイラ同梱の標準ライブラリ、または埋め込みソースのいずれかと同名の `stdlib/` 下のファイルだけで許される。他の場所ではチェッカーが宣言と、すべての `prim.<fn>` 参照（呼び出し、パイプの対象、fn 値）、`import prim` を拒否する。

```almide
@intrinsic("almide_rt_fs_write")
effect fn write(path: String, text: String) -> Result[Unit, String]   // E085
```

## 診断の形

```
error[E085]: @intrinsic on fn 'write' outside the stdlib
  --> app.almd:1:1
hint: intrinsics live in the stdlib; wrap in an effect fn: call the stdlib
      module that owns the operation (fs, http, process, ...) from an
      `effect fn` of your own, so `--profile critical` sees the capability
```

```almide
effect fn main() -> Unit = {
  let text = prim.read_text_file("in.txt")!   // E085
  println(text)
}
```

```
error[E085]: `prim.read_text_file` outside the stdlib
  --> app.almd:2:14
hint: `prim` is the standard library's primitive floor, not user surface;
      call `fs.read_text` instead
```

ヒントは基本層の操作を包む公開関数を示す。標準ライブラリソースから導出する（標準ライブラリ自身の呼び出しグラフ内で操作に最も近い公開関数を使い、単一操作専用の転送関数を優先する）ため、標準ライブラリの変更に追従する。専用転送関数がなく多数の公開関数で共有する基本層操作（`prim.handle`、`prim.load32`）は内部基盤であり、ヒントは標準ライブラリ内部のものだと示す。

## 修正

操作を所有する標準ライブラリモジュールを import して呼ぶ（エフェクトを持つ操作なら `effect fn` から）。

```almide
import fs

effect fn write(path: String, text: String) -> Unit = fs.write_text(path, text)!
```

`prim.*` についてはヒントが示す関数を呼ぶ（`prim.read_text_file(p)` なら `fs.read_text(p)!`、`prim.band(a, b)` なら `int.band(a, b)`）。

## Fix-it 判定

**not-fixable** — 代替は runtime シンボルまたは基本層操作を所有する標準ライブラリモジュールへの呼び出しであり、シンボル名だけではその呼び出しは決まらない（シグネチャ、エフェクト、エラーの形は runtime ではなく標準ライブラリラッパーのもの。`prim.read_text_file` と `fs.read_text` はエラーの形が異なる）。コンパイラは規則と修正の形を示すが、宣言を書き換えない。

## 理由

権限の説明（`almide check --profile critical --allow IO`、[cli.md](../../../specs/cli.md#--profile-critical)）は標準ライブラリモジュール単位で行い、プログラムには `fs` が許可されるかされないかである。runtime シンボルを直接名指しするユーザーファイルは `fs` を import しないため、単独の属性はどの profile からも見えずにディスクへ書く手段になっていた。`scripts/check-intrinsic-boundary.sh` が証明したのは intrinsic がリンクされることであり、許されることではない。`prim` は一段下の同じ穴である。常にアクセスできたため、ユーザーファイルの `prim.read_text_file(p)` が型検査を通り、`import fs` なしでホストへ到達した（#3025）。権限はソースの出自で決め、モジュール名では決めない。`list` というユーザーモジュールもユーザーモジュールであり、`spec/stdlib/x_test.almd` は標準ライブラリではない。チェッカーが出自を知れないソース（パスのない言語サーバーのメモリ内解析）は判定しない。
