# Fan cost model ledger (#3341) — the constants both legs' parallel-offer
# decision uses, and the measurements they come from.
# Pinned by tests/fan_cost_model_test.rs to the native runtime
# (runtime/rs/src/list.rs `almide_rt_fan_plan`) and the embedded wasm host
# (crates/almide-wasm-run/src/host_fan.rs `plan`): one formula, a pair of
# constants per leg (since 2026-10-16 — each leg's pair is the envelope over
# its own measured rows; a shared pair had to cover the slower wasm leg and
# kept native sequential where it would win). Change a constant here and in
# its leg's copy, with the measurement that justifies it.
#
# The model. Every parallel twin is a SITE (native: one per callback type;
# wasm: one per `__fan_site_K` export), and every offer at a site records
# the compute time its elements took: t ns per element. "Compute time" is
# the thread's CPU time inside the elements (CLOCK_THREAD_CPUTIME_ID on
# unix; a wall clock elsewhere), so spawn latency and the time a thread sat
# descheduled are not counted, and a worker's FIRST element of the offer —
# its warm-up, a fresh thread's (wasm: and instance's) first call — is kept
# out of t (it is the WORKER term's), unless no worker ran a second one.
# A site's FIRST offer goes parallel, as
# before #3341. A later offer of n elements on W workers costs
#   offer_ns + W * worker_ns   (waking the resident crew and waiting for
# it, the fan group's bookkeeping; on wasm, the request round trip and the
# worker calls) and
# saves   t * (n - ceil(n / W)).   The W in 2..=workers with the largest
# positive net saving wins; none = the offer runs on the calling thread
# (wasm: on one pooled instance), sequentially. Output is the same on every
# path (C-321). ALMIDE_FAN_COST_OFF restores the pre-#3341 behaviour
# (always parallel).
#
# Rejected: timing element 0 on the calling thread and deciding after it.
# It serialises one whole chunk before the parallel part — measured on
# fannkuchredux (10 chunks of ~18 ms): native 21 -> 35 ms, wasm 29 -> 45 ms.
#
# Rejected: wall time per element (the clock before 2026-10-05). On a loaded
# runner one preempted element of a trivial body reads a whole time slice
# and the site stays parallel: Linux container, 4 CPUs shared with 6 looping
# parallel fan programs, the 10-iteration probe (8 elements, W=4, break-even
# t > 11 us), 600 offers measured both ways — wall over break-even in 3
# (max 1.44 ms per element), CPU time in none (max 1.6 us; the same three
# offers read 263-277 ns). A wasm worker's warm-up call read 4-22 us (wall)
# against ~0.2 us warm on that machine.
#
# What it cannot see: a site's first offer (always parallel on every core,
# so one cheap offer pays the W=8 row once: 2.0-3.0 us native since the
# 2026-10-17 pool, 41-69 us wasm, plus the pool's spawn — and on wasm the
# workers' instantiation — when it is the run's first parallel offer), and a
# site whose work per element swings between offers (the estimate is the
# last offer's).

native_offer_ns  = 1_500
native_worker_ns = 700
wasm_offer_ns    = 30_000
wasm_worker_ns   = 5_000

# ── The native pool, 2026-10-17 ───────────────────────────────────────────
# The pool now publishes an offer to threads that poll between offers and
# steal blocks (docs/benchmarks/fan-floor.md, "The pool"), so the native

# The cost of an offer is its row less the elements' share,
# ceil(10 / W) * (W1 / 10). native: 1.5 + 0.7W us (2.9 at W=2 .. 7.1 at
# W=8) is the envelope over every row on both machines: the largest costs
# are 2.2 (W=2..4), 3.2 (W=5), 3.6 (W=6), 6.0 (W=7, AMD 100) and 5.3 us
# (W=8, AMD 100). The constants were 12 + 3W, the envelope over the crew's
# 7-35 us.
#
# What an offer reads as t changed too:
#   - the thread CPU clock read that ends a timed interval is subtracted
#     from it (measured once: the least of 16 back-to-back pairs). A worker
#     of a parallel offer often times one or two elements, and on the AMD VM
#     (a 1.1 us read) 0.4 us elements read 1.5-4 us, which kept the site
#     parallel where sequential was faster;
#   - a parallel offer is timed once in 8 (`ALMIDE_FAN_RESAMPLE_PAR`; each
#     helper's three clock reads were on the offer's critical path), and
#     every sequential site once in 16 (the 1-in-4 tier caught 0.4 us
#     elements once the crossover fell to ~0.6 us, at 12% of their offer on
#     the AMD VM);
#   - an estimate from a parallel offer within 2x of the crossover, or one
#     that timed only the workers' first elements, is checked by the next
#     offer running sequentially (`ALMIDE_FAN_PROBE`): the elements of a
#     parallel offer read slower than the same elements on one thread, and a
#     site's first offer is parallel and spawns the pool (0.4 us elements
#     read 4.1 us on the AMD VM, and the site ran parallel for 8 offers);
#   - a sequential site turns parallel only on two measurements in a row: one
#     interrupted offer read above the crossover sent 0.42 us elements (0.58
#     us crossover) parallel at ~9 us a time on the AMD VM.
