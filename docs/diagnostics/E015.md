# E015 — Possible stdlib reimplementation

A top-level `fn` has the same name and compatible signature as a pure
function in a computational stdlib module. This is an advisory warning:
only names and types are compared; the bodies may implement different
operations. E015 does not provide a replacement edit or delegation shim.

Host/environment modules, including `args`, are excluded even when their
functions have pure-looking signatures. A helper that turns an empty
string into `none` must not be replaced by a command-line option lookup.

## Common case

```almide
// ~30 lines of algorithm:
fn binary_search(xs: List[Int], target: Int) -> Option[Int] = {
    let lo = 0
    let hi = list.len(xs) - 1
    // ... loop implementation ...
}
// warning[E015]: has the same signature as stdlib `list.binary_search`
```

## Fix

After checking that the stdlib function has the intended semantics, you may delegate:

```almide
fn binary_search(xs: List[Int], target: Int) -> Option[Int] =
    list.binary_search(xs, target)
```

Or rename your fn if the algorithm is intentionally different:

```almide
fn my_search_descending(xs: List[Int], target: Int) -> Option[Int] = ...
```

## When E015 does NOT fire

- **Different name** — near names such as `optional` and `option` do not match.
- **Host/environment module or effect function** — excluded from candidates.
- **Different parameter types, return shape, or arity** — excluded from candidates.

The stdlib side may be generic (`binary_search[T: Ord]`) and the
user side monomorphic (`List[Int]`) — that still counts as a match;
asymmetric `TypeVar`-wildcard is deliberate.

## Why warning, not error?

There's no correctness issue — your fn works. The measurement
hypothesis (`docs/roadmap/done/reimpl-lint.md`) is that LLM retry
loops benefit from knowing that an identically named stdlib function exists.
Flipping to error would break legitimate specializations.
