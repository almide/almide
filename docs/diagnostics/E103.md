# E103 — `==` on a Secret that cannot compare in constant time

A `secret.Secret[A]` (#4107) compares with `==` / `!=` (and `assert_eq` /
`assert_ne`) only when `A` is `String` or `Bytes`: then the comparison runs in
constant time (`string.is_equal_constant_time` / `bytes.is_equal_constant_time`),
also when the Secret sits in a record, tuple, list, option or result being
compared. Every other comparison that would read a Secret is E103:

- a `Secret` of any other type (`Secret[Int]`, `Secret[MyRecord]`);
- a variant holding a Secret in any payload;
- a map or set holding a Secret.

```almide
import secret

fn main() -> Unit = {
  let a = secret.new(1234)
  println(if a == secret.new(1234) then "same" else "different")   // ← E103
}
```

```
error[E103]: operator '==' cannot compare 'Secret[Int]': a Secret compares only when it holds a String or Bytes (in constant time)
  hint: Compare what the secrets hold, explicitly: `secret.reveal(a) == secret.reveal(b)`. `==` on Secret[String] / Secret[Bytes] is constant time; a variant or map holding a Secret compares by `match` / per key.
```

## Fix

1. Compare the revealed values explicitly: `secret.reveal(a) == secret.reveal(b)`.
   The reveal is visible at the call site, which is the point.
2. For a variant holding a Secret, `match` the pair and compare the Secret
   payloads with `==` (constant time for String / Bytes).

## Why

A derived `==` stops at the first differing byte, so the time it takes says
how much of a guessed secret was right. String and Bytes Secrets compare in
constant time instead; for any other payload there is no constant-time
comparison to give, so the comparison is refused rather than silently timed.

## Fix-it verdict

**not-fixable**: whether a revealed comparison is acceptable depends on what
the secret is. The diagnostic names the type and the explicit spelling.
