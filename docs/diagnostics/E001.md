# E001 — Type mismatch

The type of an expression doesn't match what the surrounding context expects.

## Common cases

```almide
let x: Int = "hello"             // expected Int, got String
fn f() -> Int = "abc"            // body type doesn't match return type
list.map(xs, (x) => x + "!")     // closure return type conflicts with list element
```

## Specialized sub-patterns (with `try:` snippets)

### Unit leak: fn body ends with a `let` binding

```almide
fn sum_digits(n: Int) -> Int = {
    let abs_n = int.abs(n)           // ← `let` returns Unit, not Int
}
```

Diagnostic:

```
error[E001]: type mismatch in fn 'sum_digits': expected Int but got Unit
  try:
      // fn body ends with `let abs_n = ...` (a statement, returns Unit).
      // Add `abs_n` as the trailing expression so the fn returns Int:
      //
      //   let abs_n = <computation>
      //   abs_n                         // <-- add this line
```

The compiler extracts the real binding name from the AST and cites it in
the snippet. Fix: add the name as a trailing expression.

### Unit leak: if-arm is an assignment

```almide
fn clamp(x: Int, lo: Int) -> Int = {
    var val = x
    if val < lo then { val = lo } else val    // ← then-arm is Unit
}
```

Diagnostic:

```
error[E001]: type mismatch in if branches: expected Int but got Unit — Int is the declared return type, and the branch at line 3 produces it
  try:
      // the then-arm is `val = ...` (assignment, returns Unit).
      // Rewrite as a rebinding of `val`:
      //
      //   let new_val = if cond then <new-value-for-val> else val
```

The real variable name (`val`) is cited. Fix: use `let new_x = if cond ... else ...`.

### Effect call bound to an annotated `let` without `!`

```almide
effect fn count() -> Int = 3

effect fn main() -> Unit = {
  let n: Int = count()             // ← the call is Result[Int, String]
  println(int.to_string(n))
}
```

Diagnostic:

```
error[E001]: type mismatch in let n: expected Int but got Result[Int, String]
  hint: the value is a Result[Int, String] — unwrap it first: `!` propagates the error (effect fn body), `?? fallback` supplies a default, or `match` handles ok/err
  try: (machine-applicable — `almide fix` applies it)
      !
```

A user `effect fn f() -> T` is `T!` at the call site (ADR-0002 §D6), so the
annotation names the ok type and the missing piece is the `!` — the same
guidance E005 gives `g(count())` and E041 gives `let m = count()`. In an
effect fn body (outside any lambda) the repair `count()` → `count()!` is
**machine-applicable** when the callee is an `effect fn` declared with a
non-Result `-> T`: `!` is the one spelling of the type declared on both ends.
A callee declared `-> Result[T, E]` returned a Result on purpose, so the same
`!` is only a suggestion (`??` or `match` may be what the author meant). In a
pure fn, a lambda, or when the call spans several lines, the hint is given
without an edit.

### A wrong FIRST arm (#2927)

```almide
effect fn level() -> Level? = some({ label: "v", n: 1 })

effect fn apply(c: Cmd) -> Result[Level?, String] = match c {
  A => ok(level()),        // ← the mistake: level() without `!`
  B(_) => ok(none),
}
```

Diagnostic:

```
error[E001]: type mismatch in match arm: expected Result[Option[Level], String] but got Result[Result[Option[Level], String], String] — Result[Option[Level], String] is the declared return type, and the arm at line 5 produces it
  --> app.almd:4:8
  hint: add `!` to `level()`: without it the call's own Result is wrapped a second time. …
  try: (machine-applicable — `almide fix` applies it)
      !
```

A match / if in tail position is checked against the fn's declared return
type, so the arm (or branch) that disagrees with it is the one reported —
not the correct arms after it. Without a declared type to go by, the first
arm fixes the type and the message says so (`the first arm at line N fixed
the type to T`). An `ok(f())` / `some(f())` arm whose call yields a Result
the declared type does not nest names the missing `!`.

### `??` on an effect fn that returns an Option, without `!` (#3522)

```almide
import args

effect fn main() -> Unit = {
  let ledger = args.positional_at(0) ?? "ledger.toml"   // ← missing `!`
  println(ledger)
}
```

Diagnostic:

```
error[E001]: type mismatch in ?? fallback: expected Option[String] but got String
  --> app.almd:4:41
  hint: `args.positional_at` is an effect fn (its call is `Result[Option[String], String]`): propagate its error with `!` before `??` — `args.positional_at(0)! ?? "ledger.toml"`
  try: (machine-applicable — `almide fix` applies it)
      !
```

An effect fn declared `-> Option[T]` (`args.positional_at`, `args.option`, or
your own) is called as `Result[Option[T], String]`, so a bare `??` defaults
the `Err` and wants an `Option[T]` fallback. When the fallback is the `T`,
the fix is `!` then `??`: `!` propagates the error, `??` defaults the none.
The binding is typed `T`, so its later uses are not reported a second time.
A fallback that is neither `Option[T]` nor `T`, and `??` on a pure
`Option[T]` call, keep the plain mismatch.

## Fix (general)

- Adjust the literal/value to match the expected type.
- Change the explicit type annotation to match the actual expression.
- Convert with stdlib helpers: `int.to_string`, `int.parse(s)?`,
  `float.from_int`, `float.to_int` (truncating), etc.
- **If the "got Unit" half of a mismatch is suspicious**, inspect
  whether a trailing `let x = ...` or an `x = y` assignment is in a
  position expected to yield a value.

## Fix-it verdict

**mechanical** for one shape only (#2653): `let x: T = f()` where `f` is an `effect fn` declared `-> T` and the binding sits in an effect fn body — appending `!` to the call is exact (above); the same `!` for an `ok(f())` / `some(f())` match arm or if branch that nests the declared `Result` one layer too deep (#2927), with the same callee rule; and the `!` before `??` when the left side is a one-line call of an `effect fn` declared `-> Option[T]`, the fallback is its `T`, and the `??` sits in an effect fn body outside any lambda (#3522). Every other E001 is **not-fixable** — the error reports a semantic/design problem no automatic rewrite can decide. (`mechanical` = an unattended fixer may apply the
rewrite; `conditional` = a suggested fix needs review; `not-fixable` = no
automatic rewrite exists. #1486's applicability doctrine.)
