# E013 — Field access on a non-record / missing field

A `.field` access targeted a value whose type doesn't declare that
field (or isn't a record at all).

## Common cases

```almide
type Point = { x: Int, y: Int }

let p = Point { x: 1, y: 2 }
let z = p.z                      // E013: no field `z` on Point

let n: Int = 42
let bad = n.value                // E013: Int has no fields
```

## Diagnostic

```
error[E013]: no field `z` on type `Point`
  --> main.almd:4:9
  hint: Available fields on `Point`: x, y. Check spelling or verify the record type.
  in field access .z
```

When the type is a record, the diagnostic lists its fields. A bare member
access is not the same as a UFCS call: `s.to_upper()` may resolve a
function, while `s.to_upper` asks for a field.

### A user type named after a stdlib type

```almide
import json
type Value = { n: Int }
let v = json.parse("{}")!
let n = v.n                      // E013: no field `n` on Value — the type has no fields
```

`json.parse` returns the STDLIB's `Value`; the user's `type Value` is a
different type (`self.Value` in the entry program, `m.Value` in module
`m`) and never rebinds the stdlib's (#1828). The hint names both: "Here
`Value` is the `value` module's type, not your `type Value` (which is
`self.Value`)". Read the stdlib value through its module (`value.*`,
`json.*`), or rename your type. The same applies to every stdlib-owned
name: `HttpRequest`, `HttpResponse`, `FileStat`, `ProcessStatus`, `Url`,
`TcpStream`, `TcpListener`, `SafeHtml`, `IpAddr`, `Deque`, `Path`
— and to every shape of declaration: an OPAQUE alias (`mod type Value =
String`) is a newtype the program owns under the same `self.Value` /
`m.Value` identity (#1835), so the json value's field read is this E013
with the same hint, and aiming the newtype's pattern `Value(s)` at the
json value is E048.

## Fix

- Spelling: check the declared field name(s). Records are case-sensitive.
- Wrong record: you may be accessing a field that exists on a
  different type. Verify `p`'s declared type matches the fields you
  expect.
- Method-style mistake: `xs.head` / `s.length` aren't fields, they're
  cross-language idiom imports. Rewrite as `list.first(xs)` /
  `string.len(s)`. An exact, type-directed property-to-function
  rewrite can be machine-applicable; a fuzzy field-name suggestion still
  needs review.

## Why

Record fields and tuple indices (`.0`, `.1`, ...) are value accesses.
Method-style calls with parentheses use UFCS resolution; they are not
implicit property reads. Use `module.function(value)` when that makes the
intended operation clearer.
