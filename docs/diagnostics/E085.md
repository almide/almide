# E085 — `@intrinsic` or `prim.*` outside the stdlib

`@intrinsic("almide_rt_…")` and `@wasm_intrinsic` bind a fn name straight to
a runtime symbol, and the `prim` module is the primitive floor the stdlib is
written over (raw loads and stores, allocators, `fd_write`, the host file
calls). Both are the runtime boundary: legal only in the stdlib's own sources
— the bundled stdlib the compiler carries, or a file under `stdlib/` named
after one of its embedded sources. Anywhere else the checker rejects the
declaration, and any `prim.<fn>` reference (a call, a pipe target, a fn value)
or `import prim`.

```almide
@intrinsic("almide_rt_fs_write")
effect fn write(path: String, text: String) -> Result[Unit, String]   // E085
```

## Diagnostic shape

```
error[E085]: @intrinsic on fn 'write' outside the stdlib
  --> app.almd:1:1
hint: intrinsics live in the stdlib; wrap in an effect fn: call the stdlib
      module that owns the operation (fs, http, process, ...) from an
      `effect fn` of your own, so `--profile critical` sees the capability
```

```almide
effect fn main() -> Unit = {
  let text = prim.read_text_file("in.txt")!   // E085
  println(text)
}
```

```
error[E085]: `prim.read_text_file` outside the stdlib
  --> app.almd:2:14
hint: `prim` is the standard library's primitive floor, not user surface;
      call `fs.read_text` instead
```

The hint names the public function that wraps the floor op. It is derived
from the stdlib sources (the public functions nearest to the op in the
stdlib's own call graph, a dedicated one-op forwarder first), so it follows
the stdlib as it changes. A floor op with no dedicated forwarder that many
public functions share (`prim.handle`, `prim.load32`) is the floor's own
plumbing: the hint says it is internal to the standard library.

## Fix

Import the stdlib module that owns the operation and call it (from an
`effect fn` when the operation is effectful):

```almide
import fs

effect fn write(path: String, text: String) -> Unit = fs.write(path, text)!
```

For `prim.*`, call the function the hint names (`fs.read_text(p)!` for
`prim.read_text_file(p)`, `int.band(a, b)` for `prim.band(a, b)`).

## Fix-it verdict

**not-fixable** — the replacement is a call into whichever stdlib module owns
the runtime symbol or floor op, and the symbol's name does not determine that
call (its signature, effect and error shape are the stdlib wrapper's, not the
runtime's: `prim.read_text_file` and `fs.read_text` differ in error shape). The compiler names the rule and the shape of the fix; it does not
rewrite the declaration.

## Why

The capability story (`almide check --profile critical --allow IO`) is told
in terms of stdlib modules: a program is granted `fs` or it is not. A user
file that names the runtime symbol itself never imports `fs`, so a bare
attribute was a way to write to disk that no profile could see —
`scripts/check-intrinsic-boundary.sh` proved that intrinsics *link*, not that
they are *allowed*. `prim` is the same hole one level down: it was
always accessible, so `prim.read_text_file(p)` type-checked in a user file and
reached the host without an `import fs` (#3025). The authority is decided by
the source's origin, never by a module's name: a user module called `list` is
still a user module, and `spec/stdlib/x_test.almd` is not the stdlib. A source
whose origin the checker cannot know (the language server's in-memory
analysis, with no path) is not judged.
