# E085 — `@intrinsic` outside the stdlib

`@intrinsic("almide_rt_…")` and `@wasm_intrinsic` bind a fn name straight to
a runtime symbol. They are legal only in the runtime boundary — the
repository's `stdlib/` and `runtime/` trees and the bundled stdlib copy the
compiler carries. Anywhere else the checker rejects the declaration.

```almide
@intrinsic("almide_rt_fs_write")
effect fn write(path: String, text: String) -> Result[Unit, String]   // E085
```

## Diagnostic shape

```
error[E085]: @intrinsic on fn 'write' outside the stdlib
  --> app.almd:1:1
hint: intrinsics live in the stdlib; wrap in an effect fn: call the stdlib
      module that owns the operation (fs, http, process, ...) from an
      `effect fn` of your own, so `--profile critical` sees the capability
```

## Fix

Import the stdlib module that owns the operation and call it from an
`effect fn`:

```almide
import fs

effect fn write(path: String, text: String) -> Unit = fs.write(path, text)!
```

## Why

The capability story (`almide check --profile critical --allow IO`) is told
in terms of stdlib modules: a program is granted `fs` or it is not. A user
file that names the runtime symbol itself never imports `fs`, so a bare
attribute was a way to write to disk that no profile could see —
`scripts/check-intrinsic-boundary.sh` proved that intrinsics *link*, not that
they are *allowed*. The authority is decided by the source's origin, never by
a module's name: a user module called `list` is still a user module. A source
whose origin the checker cannot know (the language server's in-memory
analysis, with no path) is not judged.
