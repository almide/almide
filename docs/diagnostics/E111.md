# E111 — type too large

An inferred type passed the `type_size` compile-cost budget (ADR-0030): it
has more nodes than the compiler builds for one type. A type grows with every
copy of a type inside it, so a few lines can ask for an exponential one:

```almide
effect fn main() -> Unit = {
  let t0 = 1
  let t1 = (t0, t0)
  let t2 = (t1, t1)
  // ... each line doubles the type: t22's has 4 million leaves
  println("ok")
}
```

```
error[E111]: type too large (4097+ nodes, max 4096)
```

The same happens through a generic that returns its argument twice
(`fn dup[T](x: T) -> (T, T)`, then `dup(dup(dup(x)))`): the checker shares the
structure while it infers, and the budget stops the copy when the shared
structure would be spelled out.

## Fix

Name the intermediate type, or keep the data in a record or a list whose type
does not grow with each step:

```almide
effect fn main() -> Unit = {
  let t0 = 1
  let t1 = [t0, t0]
  let t2 = t1 + t1   // List[Int], however long it gets
  println("ok")
}
```

## Why

The compiler runs on untrusted source — CI on a pull request, the LSP when a
file is opened, graders, the playground — and before the budget, 22 lines of
this shape took `almide check` to 3.7 GB (#4114). The budget counts nodes, not
seconds or memory, so the verdict is the same on every machine. The source
cannot raise it: there is no attribute, manifest key or environment variable
for it. The person running the compiler can, with `--budget type_size=N`
(`almide budgets` lists every budget), and `--profile critical` refuses that.

Fixtures: `tests/diagnostics/e111-type-doubling-chain`,
`e111-type-doubling-through-a-generic`; the gate is
`tests/compile_budget_test.rs`.

## Fix-it verdict

**not-fixable**: how to restructure the data is a decision about the program.
(`mechanical` = an unattended fixer may apply the rewrite; `conditional` = a
suggested fix needs review; `not-fixable` = no automatic rewrite exists.
#1486's applicability doctrine.)
