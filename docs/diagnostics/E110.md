# E110 — untrusted input decodes only into an input type

A fn marked `@input_sink` (`http.decode_json`) decodes untrusted input into its
`Decode`-bounded type parameter. That parameter must be bound to an **input
type**: a record declared `: Decode` and not also `Encode` (row 22, C-436).
Every field of an input type is input, so the type is the allowlist of what
the client may set.

```almide
type User: Codec = { name: String, email: String, is_admin: Bool = false }

match http.decode_json[User](req) {   // ← E110
```

```
error[E110]: `http.decode_json` decodes untrusted input only into an input type, and `User` is also sent out (it is `Codec`)
  hint: Declare what the client may set as its own type, then build `User` in code:
          type UserInput: Decode = { name: String, email: String }
          match http.decode_json[UserInput](req) {
            ok(i) => … User { name: i.name, email: i.email, … } …
            err(bad) => bad,     // unknown key → 400
          }
        Every field of a `: Decode` type is input. A field the client must not set stays out of it.
```

The same code covers three more shapes:

- a record **nested** in the input type that is also sent out
  (`type SignupInput: Decode = { address: Address }` with `Address: Codec`):
  adding `verified: Bool = false` to the shared `Address` would make it
  settable from the request;
- a **variant** at the sink: the sink refuses any key outside a record's
  fields, and a variant has no field set;
- a **type parameter** of a fn that is not itself `@input_sink`
  (`fn body_as[T: Decode](req) = http.decode_json[T](req)`): mark the
  forwarding fn `@input_sink` so its callers' types are judged.

A type declared by a stdlib module (`Url`, `Uuid`) nested in an input type is
a leaf value and is not judged.

## Fix

```almide
type User: Codec = { name: String, email: String, is_admin: Bool = false }

type UserInput: Decode = { name: String, email: String }

match http.decode_json[UserInput](req) {
  ok(i) => http.response(201, "${User { name: i.name, email: i.email, is_admin: false }.name}"),
  err(bad) => bad,
}
```

## Why

Mass assignment needs an untrusted source **and** a target type whose field
set is wider than what that source may set. In every derive-based codec
measured (Go, serde, pydantic, zod, Swift, kotlinx, Jackson, aeson) a known
field such as `is_admin` is set from input unless something marks it, and
strict unknown-key handling does not help, because `is_admin` is a known key.
The ecosystems that close the hole do it with an allowlist type separate from
the domain type (FastAPI's `UserCreate`, zod's `pick`, Elm's decoder value,
Rails' strong parameters). A `@skip_decode` on the domain type is a denylist:
the next field added to `User` arrives unmarked.

A `: Decode`-only type is that allowlist, declared once, and edits to `User`
cannot widen it. The sink also decodes with `T.decode_strict`, so a key
outside the input type (`is_admin`, a typo, a probe) is
`400 Bad Request: unknown key '<k>'`. `T.decode` elsewhere stays lenient.

## Fix-it verdict

**not-fixable**: which fields the client may set is a decision about the
endpoint. (`mechanical` = an unattended fixer may apply the rewrite;
`conditional` = a suggested fix needs review; `not-fixable` = no automatic
rewrite exists. #1486's applicability doctrine.)
