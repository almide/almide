# E054 — fmt verification failed

`almide fmt` refused to write a file because formatting it would not have
conserved the program. This is the formatter's `--safe` verifier (the Black
model, #1309): before any write, the formatted output must (1) still parse,
(2) carry the identical AST, and (3) keep every comment. When any of the
three fails, the file is left untouched and this diagnostic reports why:

```
error[E054]: fmt verification failed — AST changed by formatting at $.decls[3].body
  hint: Formatting this file would not conserve the program (parse, AST, or
        comments), so it was left untouched. This is a FORMATTER bug, not a
        source problem — please report it ...
```

## What it means

Unlike every other E-code, **the defect is in the compiler, not in your
source**. The verifier exists precisely so a formatter bug becomes a loud
refusal instead of a silent corruption; the message carries the first
diverging AST path (or the parse error, or the comment count) so the report
is actionable for the compiler side.

## What to do

- Leave the named file unformatted (fmt already did — the refusal is the
  safety property working).
- Report the file at <https://github.com/almide/almide/issues> — each E054 is
  a formatter defect that a regression fixture can pin.
- Format the surrounding files normally; the refusal is per-file.

A known benign class: comments sitting inline mid-expression
(`f(1 /* x */, 2)`) are legal to parse but not yet attachable by fmt —
`#1326` tracks attachment. Such files stay unformatted rather than lose the
comment.

## Where it fires

There is no source fixture for E054 in `tests/diagnostics/` on purpose: the
trigger is an internal formatter defect, which no committed source file can
(or should) reproduce deliberately. The verifier logic itself is pinned by
`crates/almide-tools/tests/fmt_corpus_test.rs`, which feeds corrupted
"formatted" outputs straight into `verify_format` and asserts refusal.
