# E022 — `!` operator outside an error-propagating context

The postfix `!` unwraps an `Option[T]` or `Result[T, E]` and exits through
the innermost compatible failure channel when it fails. Such a channel can
belong to an effect fn, a pure fn returning Result/Option, or an inferred
fallible lambda. A test block instead uses test-unwrap semantics.

A plain, infallible fn has no failure channel:

```almide
fn parse_number(s: String) -> Int = int.parse(s)!   // E022
```

## Fix

Declare a fallible return when propagation is intended:

```almide
fn parse_number(s: String) -> Int! = int.parse(s)!
```

Or handle the failure locally:

```almide
fn parse_or_zero(s: String) -> Int = int.parse(s) ?? 0
```

A lambda's `!` belongs to the lambda's own channel, not the surrounding
fn. Its error type comes from a contextual type or the join of its `!`
operands (ADR-0021); the call that consumes a fallible callback may itself
return a Result. Adding `effect` is necessary for real effects, not merely
for a pure calculation that can fail.

## Error type mismatch (#2635)

Where `!` can propagate, the error it carries must already be the fn's
compatible error type; it does not invent a conversion to a user error type. In a fn whose error type is a user
type (`-> Result[T, Failure]`, `-> T!Failure`), three operands fail with
a `String` instead, and are E022:

- an effect call whose return is not `Result` (`-> Bool`, `-> Unit`,
  `-> Int`, a record, …) — its effect channel is `String`;
- a `Result[_, String]`;
- an `Option` (its `none` becomes a `String` error).

```almide
type Failure = | Slow | Broken(String)

effect fn ready() -> Bool = ...
effect fn tidy() -> Unit = ...

effect fn step() -> Result[Int, Failure] = {
  tidy()!                                   // E022: fails with String
  if ready()! then ok(1) else err(Slow)     // E022: fails with String
}
```

```
error[E022]: operator '!' cannot propagate this error: the fn's error type is `Failure`, but this effect call fails with `String`
```

Handle the error in place: `match` on the result and return `err(...)`
with a `Failure` case, use `?? default` (`ready() ?? false`), or discard
a Unit call's error with `let _ = tidy()`. A variant error `!`-ed inside
a fn whose error type is `String` is still accepted: it is converted to
its text.

## Why

Fallibility and effect are separate axes. E022 rejects a missing or
incompatible failure channel, not pure code as a class. Conversion from a
variant error to a String channel uses its repr text; the strict-conversion
design discrepancy is recorded in ADR-0021 D5.
