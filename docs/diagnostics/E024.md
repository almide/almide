# E024 — integer literal out of range

An integer literal that does not fit the type it is used as. Lowering and both
code generators parse the literal with `.unwrap_or(0)`, so an out-of-range
literal would otherwise **silently fold to 0** on both targets with no
diagnostic. The check is type-aware and runs after type inference, so the range
is the literal's *actual* type, not always `i64`.

A literal can miss its range three ways, and each gets its own hint:

| | cause | fix |
|---|---|---|
| **magnitude** | the value is too large for the width | a smaller literal, or a wider type |
| **sign** | a negative literal in an unsigned type | drop the `-`, or the signed type of the same width |
| **carrier** | inside `UInt64`'s declared range, above the `i64` the compiler carries integers in | stay at or below `i64::MAX`, or carry it as a string (#872) |

## Common cases

### Magnitude

```almide
fn main() -> Unit = println(int.to_string(9223372036854775808))  // E024: > i64::MAX in an Int context
```

`9223372036854775808` is `i64::MAX + 1`. In a default `Int` (i64) context it
cannot be represented, so it would fold to 0.

```
error[E024]: integer literal '9223372036854775808' is out of range for Int
  hint: Int would silently fold to 0 here; its range is -9223372036854775808..=9223372036854775807, so use a literal within it, or model larger magnitudes as Float (lossy) or a parsed string
```

### Sign

```almide
fn main() -> Unit = {
  let k: UInt64 = -5   // E024: UInt64 has no negative values at all
  println(uint64.to_string(k))
}
```

An unsigned type has no negative values, so this is not about how large `5` is
— `5` is perfectly in range, `-5` is not representable at any magnitude. Native
`rustc` rejects the emitted `-5u64` outright (`error[E0600]: cannot apply unary
operator '-' to type 'u64'`), so without E024 this is a check-passes /
build-fails gap rather than a silent fold.

```
error[E024]: integer literal '-5' is out of range for UInt64
  hint: UInt64 is unsigned — it has no negative values at all; drop the '-', or use the signed Int64 if the value can go below zero
```

`-0` is exempt: it is `0`, which every unsigned type represents.

### Carrier

```almide
fn main() -> Unit = {
  let big: UInt64 = 18446744073709551615   // E024: past the i64 carrier
  println(uint64.to_string(big / 2))
}
```

`UInt64` is *declared* to reach `18446744073709551615`, but the compiler carries
every integer — signed or not, at every width — in one `i64`, and MIR (the
default path for both targets) has no unsigned 64-bit lane. Above `i64::MAX`,
`/` would be a signed divide and `uint64.to_string` would print signed, so both
targets would agree on the same wrong answer. The literal is rejected rather
than silently carried; see #872 for the lane that lifts this.

```
error[E024]: integer literal '18446744073709551615' is out of range for UInt64
  hint: this magnitude is inside UInt64's declared range but above the i64 the compiler carries every integer in, so it would be signed past 9223372036854775807 on both targets (#872); keep it at or below 9223372036854775807, or carry it as a string / Float (lossy)
```

## Fix

- Use a wider / unsigned type when the magnitude is legitimate — but note the
  ceiling is the `i64` carrier, not the declared domain (#872):
  ```almide
  let big: UInt64 = 9223372036854775807   // the largest magnitude any type carries
  ```
- The negated `i64::MIN` magnitude is valid as a signed value (the `-` is what
  makes it representable):
  ```almide
  let lo: Int = -9223372036854775808      // i64::MIN — fine
  ```
- Model very large magnitudes as `Float` (lossy) or carry them as a string.
- For a sign error, move to the signed type of the same width — `UInt8` → `Int8`,
  `UInt16` → `Int16`, `UInt32` → `Int32`, `UInt64` → `Int64`:
  ```almide
  let delta: Int32 = -5                   // was UInt32
  ```

## Why type-aware

The range depends on the literal's context, decided post-solve:

- `Int` / `Int64` → i64 (`-9223372036854775808 .. 9223372036854775807`); a bare
  positive `9223372036854775808` overflows, but `-9223372036854775808` reaches
  `i64::MIN` and is valid.
- `UInt64` → `0 .. 9223372036854775807` for now (declared `0 .. u64::MAX`, capped
  at the carrier — #872); `Int8`/`UInt8`/… use their own widths, all of which
  fit the carrier. The lower bound is `0`, so *any* negated non-zero literal is
  out of range regardless of width.

A naive `i64`-only check would wrongly reject a valid `UInt64` literal or the
negated `i64::MIN`, so the check waits for the literal's resolved/annotated type.
