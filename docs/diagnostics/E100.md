# E100 — a `RawPtr` in a file that declares no `@extern` fn

`RawPtr` is the pointer scalar of the C ABI: the type an `@extern(c)` fn
takes or returns. On native it is a bare `*mut u8`; on wasm it is a
linear-memory offset. `bytes.from_raw_ptr(p, n)` and
`bytes.copy_to_ptr(b, p, cap)` move `n` or `cap` bytes through it, and
nothing can check that the memory behind `p` is that long. Rust keeps such
a call inside `unsafe`; in Almide it is legal only in a file that declares an
`@extern` fn, which is what marks the file as talking to foreign code.

A user file with no `@extern` declaration may not hold a `RawPtr`
value. That covers every way of reaching one: a call, a method call
(`b.as_ptr()`), a pipe, an alias import, the fn named as a value, and a
helper whose parameter is a `RawPtr`.

```almide
effect fn main() -> Unit = {
  let small = bytes.from_list([1, 2, 3, 4])
  let copy = bytes.from_raw_ptr(bytes.as_ptr(small), 4096)   // E100
  println("${bytes.len(copy)}")
}
```

## Diagnostic shape

```
error[E100]: a `RawPtr` in a file that declares no `@extern` fn
  --> app.almd:3:33
hint: `RawPtr` is the C-ABI pointer of `@extern`: `bytes.from_raw_ptr` and
      `bytes.copy_to_ptr` move as many bytes as they are told through it,
      with no bound. Copy within Almide with `bytes.slice` / `bytes.copy_from`,
      or declare the `@extern` fn the pointer is for in this file
```

There is one error per declaration (fn, top-level `let`, test), at the first
`RawPtr` expression in it.

## Fix

To copy bytes inside the program, use the checked operations, which stop at
the end of the buffer:

```almide
effect fn main() -> Unit = {
  let small = bytes.from_list([1, 2, 3, 4])
  let copy = bytes.slice(small, 0, 4096)
  println("${bytes.len(copy)}")
}
```

To hand a buffer to C, declare the foreign fn in the same file. The pointer
is then part of that file's FFI surface, which is outside every memory
guarantee (#4008):

```almide
@extern(c, "c", "write")
fn c_write(fd: Int, buf: RawPtr, n: Int) -> Int

effect fn main() -> Unit = {
  let msg = bytes.from_string("hi\n")
  let _ = c_write(1, bytes.as_ptr(msg), bytes.len(msg))
}
```

## Fix-it verdict

**not-fixable** — whether the pointer stays in the program (use
`bytes.slice` / `bytes.copy_from`) or goes to foreign code (declare the
`@extern`) is the author's decision, and the right length depends on what the
code meant.

## Why

With `bytes.as_ptr`, the two calls read and wrote past a 4-byte buffer from
ordinary code (#4043): the native leg corrupted its heap and died, and the
wasm leg overwrote the next block and exited 0. `prim.int_to_ptr` was already
closed by [E085](E085.md), but the public `bytes` API reached the same hole.
In a file with no `@extern`, a `RawPtr` can only point at the program's own
`Bytes`, so a use there has no foreign code to serve. Tying the type to the
declaration makes the unchecked surface the same as the FFI surface: a
program none of whose files declares `@extern` holds no `RawPtr`, and the
memory-safety statement (#4011) can be made about it.
