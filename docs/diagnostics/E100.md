# E100 — outside the memory-safety guarantee, under `--profile critical`

`almide check --profile critical` admits only code inside Almide's
memory-safety guarantee (#4008). Three things are outside it, and each is
E100:

- a call to any `ffi.*` function. `ffi.read` and `ffi.write` read and write
  memory at a raw address with a length nothing checks (R-L0-45);
  `ffi.address` and `ffi.to_int` exist only to feed them;
- a call to one of the deprecated `bytes` raw-pointer spellings `ffi`
  replaces: `bytes.as_ptr`, `bytes.as_mut_ptr`, `bytes.data_ptr`,
  `bytes.from_raw_ptr`, `bytes.copy_to_ptr`;
- the declaration of an `@extern` fn: its body is foreign code.

Unlike a capability (E076), no `--allow` grant admits these. Without the
profile the same program checks as before: critical is a subset of the
language, not a dialect.

```almide
fn main() -> Unit = {
  let b = bytes.from_string("abc")
  let c = bytes.from_raw_ptr(bytes.as_ptr(b), 1000000)   // ← E100 under --profile critical
  println(int.to_string(bytes.len(c)))
}
```

```
error[E100]: `bytes.from_raw_ptr` is outside the memory-safety guarantee and is not admissible under `--profile critical`
  hint: the critical profile admits only code inside the memory-safety guarantee — keep raw-address and foreign code in a module that is not checked with `--profile critical`
```

## Fix

1. Use the safe operation the raw address stood in for: `bytes.slice`,
   `bytes.copy_from`, `bytes.get` and the typed readers bound every access by
   the buffer's length.
2. When the program really talks to foreign code, keep that code in a module
   of its own and check the rest of the program with `--profile critical`.

## Why

A raw read or write with an unchecked length is the one way ordinary Almide
code can corrupt memory: `bytes.from_raw_ptr(bytes.as_ptr(b), 1000000)` on a
3-byte buffer copies a million bytes of whatever follows it. The critical
profile is the promise that a program cannot do that, so it refuses every
construct that can.

## Fix-it verdict

**not-fixable**: the replacement depends on what the raw access was for. The
diagnostic names the construct and the profile; it does not rewrite the code.

The stdlib functions refused are the ones declared `@memory_unsafe` in their
`.almd` source (stdlib/ffi.almd, stdlib/bytes.almd); the checker reads that
declaration, not a list of names.

Not an ALS §B (`@bounded`) rule: a `@bounded` fn calling `ffi` is E076, as for
any module outside its declared capability. Fixtures: `tests/diagnostics/e100-*`
(each `meta.toml` sets `check_profile = "critical"`). Matrix:
`tests/critical_profile_test.rs` (`memory_unsafe_surface_is_refused_under_critical`).
