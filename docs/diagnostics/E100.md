# E100 — outside the memory-safety guarantee

A construct that can read or write memory outside Almide's values is refused
in two places.

## Without `import ffi` (#4043)

Raw memory is an explicit opt-in, as in Rust's `unsafe`. The stdlib functions
that reach memory foreign code can also reach are declared `@memory_unsafe` in
their `.almd` source: every `ffi.*` function (`ffi.region`, `ffi.alloc`,
`ffi.len`, `ffi.is_writable`, `ffi.read`, `ffi.write`, `ffi.to_bytes`).
Outside the stdlib, reaching one needs the calling FILE to write
`import ffi`. The opt-in is per file: a module that touches raw memory says so
itself, whatever the files importing it say. So a program whose files have no
`import ffi` and no `@extern` cannot reach memory outside its values, on any
target. Since `ffi` is the only module with `@memory_unsafe` functions and is
never auto-imported, a file without the import cannot even name it: the call
is E003 (`undefined variable 'ffi'`), whose hint is the import. E100 is the
refusal for a `@memory_unsafe` function reached any other way.

Every `ffi` access is bounds-checked against the `Region`'s length
([ADR-0031](../adr/0031-raw-pointers-carry-provenance.md)): an out-of-bounds
`ffi.read` or `ffi.write` answers `err`. The import is still required, because
a `Region` can view memory that foreign code also reaches (a buffer handed to
an `@extern(c)` fn, or one an `@extern` returned with `@region(len = …)`).

```almide
effect fn main() -> Unit = {
  let small = bytes.from_list([1, 2, 3, 4])
  let copied = ffi.read(ffi.region(small), 0, 4)!   // ← E003: no `import ffi`
  println(int.to_string(bytes.len(copied)))
}
```

```
error[E003]: undefined variable 'ffi'
  hint: Add `import ffi` (stdlib: bounds-checked memory regions shared with foreign functions)
```

The fix is the one line at the top of the file:

```almide check
import ffi

effect fn main() -> Unit = {
  let small = bytes.from_list([1, 2, 3, 4])
  let copied = ffi.read(ffi.region(small), 0, 4)!
  println(int.to_string(bytes.len(copied)))
}
```

The address-as-pointer spellings this rule used to name (`ffi.address`,
`ffi.to_int`, `bytes.as_ptr`, `bytes.as_mut_ptr`, `bytes.data_ptr`,
`bytes.from_raw_ptr`, `bytes.copy_to_ptr`) are gone (ADR-0031 D4, dialect
epoch 15): a read-only view of a `Bytes` is `ffi.region(b)`, a writable buffer
is `ffi.alloc(n)!`, and a read or write names an offset into the region
(`ffi.read(r, off, n)`, `ffi.write(r, off, b)`), never an address.

## Under `--profile critical` (#4008)

`almide check --profile critical` admits only code inside Almide's
memory-safety guarantee. Two things are outside it, and each is E100 even
with `import ffi`:

- a call to any `ffi.*` function. A `Region` can view memory foreign code
  also reaches, and a foreign region's length is the binding's word
  (`@region(len = …)`), so even a bounds-checked `ffi.read` is refused;
- the declaration of an `@extern` fn: its body is foreign code.

Unlike a capability (E076), no `--allow` grant admits these. Without the
profile the same program (with its `import ffi`) checks as before: critical
is a subset of the language, not a dialect.

```almide
import ffi

effect fn main() -> Unit = {
  let b = bytes.from_string("abc")
  let c = ffi.read(ffi.region(b), 0, 3)!   // ← E100 under --profile critical
  println(int.to_string(bytes.len(c)))
}
```

```
error[E100]: `ffi.region` is outside the memory-safety guarantee and is not admissible under `--profile critical`
  hint: the critical profile admits only code inside the memory-safety guarantee — keep raw-address and foreign code in a module that is not checked with `--profile critical`
```

## Fix

1. Use the safe operation the region stood in for: `bytes.slice`,
   `bytes.copy_from`, `bytes.get` and the typed readers bound every access by
   the buffer's length and need no import.
2. When the program really talks to foreign code, write `import ffi` in the
   file that does it, keep that file a module of its own, and check the rest
   of the program with `--profile critical`.

## Why

Before ADR-0031, a raw read with an unchecked length was the one way ordinary
Almide code could corrupt memory: reading a million bytes from the address of
a 3-byte buffer copied whatever followed it. `Region` now carries its length,
so `ffi` itself answers `err` instead; what remains outside the guarantee is
the memory a `Region` shares with foreign code. The `import ffi` line puts the
files that touch it where a reader, a reviewer or a model looks first; the
critical profile is the promise that a program does not touch it at all, so
it refuses every construct that can.

## Fix-it verdict

**not-fixable**: the replacement depends on what the raw access was for. The
diagnostic names the construct and the missing import or the profile; it does
not rewrite the code.

The stdlib functions refused are the ones declared `@memory_unsafe` in their
`.almd` source (stdlib/ffi.almd); the checker reads that declaration, not a
list of names. The stdlib's own sources are exempt from the import rule, as
they are from E085.

Not an ALS §B (`@bounded`) rule: a `@bounded` fn calling `ffi` is E076, as for
any module outside its declared capability. Fixtures: `tests/diagnostics/e100-critical-*`
(each `meta.toml` sets `check_profile = "critical"`) and
`tests/diagnostics/e003-no-import-ffi-region-*` (the #4043 probes). Matrices:
`tests/critical_profile_test.rs` (`memory_unsafe_surface_is_refused_under_critical`),
`tests/memory_unsafe_import_gate_test.rs`, `tests/raw_ptr_surface_test.rs`.
