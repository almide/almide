# E100 — outside the memory-safety guarantee

A construct that can read or write memory outside Almide's values is refused
in two places.

## Without `import ffi` (#4043)

Raw memory is an explicit opt-in, as in Rust's `unsafe`. The stdlib functions
that read or write at a raw address, or hand out the address that does, are
declared `@memory_unsafe` in their `.almd` source: every `ffi.*` function and
the deprecated `bytes` raw-pointer spellings `bytes.as_ptr`,
`bytes.as_mut_ptr`, `bytes.data_ptr`, `bytes.from_raw_ptr`,
`bytes.copy_to_ptr`. Outside the stdlib, a call to one — direct, a pipe
stage, a method call, a function value or a selectively imported name — is
E100 unless the calling FILE writes `import ffi`. The opt-in is per file: a
module that touches raw memory says so itself, whatever the files importing
it say. So a program whose files have no `import ffi` and no `@extern` cannot
read or write memory outside its values, on any target.

```almide
fn main() -> Unit = {
  let small = bytes.from_list([1, 2, 3, 4])
  let leaked = bytes.from_raw_ptr(bytes.as_ptr(small), 4096)   // ← E100: no `import ffi`
  println(int.to_string(bytes.len(leaked)))
}
```

```
error[E100]: `bytes.from_raw_ptr` is outside the memory-safety guarantee and needs `import ffi` in this file
  hint: `bytes.from_raw_ptr` reads or writes memory at a raw address with a length nothing checks; `import ffi` is the opt-in that marks a file as leaving the memory-safety guarantee — add `import ffi` and write `ffi.read` in place of the deprecated `bytes.from_raw_ptr` (ffi.read is an effect fn). Without raw memory, use the bounded `bytes` functions (`bytes.slice`, `bytes.get`, `bytes.copy_from`)
```

The rewrite, with `import ffi` at the top of the file:
`bytes.as_ptr(b)` / `bytes.as_mut_ptr(b)` → `ffi.address(b)`;
`bytes.data_ptr(b)` → `ffi.to_int(ffi.address(b))`;
`bytes.from_raw_ptr(p, n)` → `ffi.read(p, n)` from an effect fn;
`bytes.copy_to_ptr(b, p, c)` → `ffi.write(p, b, c)` from an effect fn.
With `import ffi` the deprecated spellings still check, with their E052
warning, until the epoch that removes them.

## Under `--profile critical` (#4008)

`almide check --profile critical` admits only code inside Almide's
memory-safety guarantee. Three things are outside it, and each is E100 even
with `import ffi`:

- a call to any `ffi.*` function. `ffi.read` and `ffi.write` read and write
  memory at a raw address with a length nothing checks (R-L0-45);
  `ffi.address` and `ffi.to_int` exist only to feed them;
- a call to one of the deprecated `bytes` raw-pointer spellings `ffi`
  replaces: `bytes.as_ptr`, `bytes.as_mut_ptr`, `bytes.data_ptr`,
  `bytes.from_raw_ptr`, `bytes.copy_to_ptr`;
- the declaration of an `@extern` fn: its body is foreign code.

Unlike a capability (E076), no `--allow` grant admits these. Without the
profile the same program (with its `import ffi`) checks as before: critical
is a subset of the language, not a dialect.

```almide
import ffi

fn main() -> Unit = {
  let b = bytes.from_string("abc")
  let c = bytes.from_raw_ptr(bytes.as_ptr(b), 1000000)   // ← E100 under --profile critical
  println(int.to_string(bytes.len(c)))
}
```

```
error[E100]: `bytes.from_raw_ptr` is outside the memory-safety guarantee and is not admissible under `--profile critical`
  hint: the critical profile admits only code inside the memory-safety guarantee — keep raw-address and foreign code in a module that is not checked with `--profile critical`
```

## Fix

1. Use the safe operation the raw address stood in for: `bytes.slice`,
   `bytes.copy_from`, `bytes.get` and the typed readers bound every access by
   the buffer's length.
2. When the program really talks to foreign code, write `import ffi` in the
   file that does it (and move to the `ffi.*` spellings), keep that file a
   module of its own, and check the rest of the program with
   `--profile critical`.

## Why

A raw read or write with an unchecked length is the one way ordinary Almide
code can corrupt memory: `bytes.from_raw_ptr(bytes.as_ptr(b), 1000000)` on a
3-byte buffer copies a million bytes of whatever follows it. The `import ffi`
line puts the files that can do that where a reader, a reviewer or a model
looks first; the critical profile is the promise that a program cannot do it
at all, so it refuses every construct that can.

## Fix-it verdict

**not-fixable**: the replacement depends on what the raw access was for. The
diagnostic names the construct and the missing import or the profile, and the
hint names the `ffi` rewrite; it does not rewrite the code.

The stdlib functions refused are the ones declared `@memory_unsafe` in their
`.almd` source (stdlib/ffi.almd, stdlib/bytes.almd); the checker reads that
declaration, not a list of names. The stdlib's own sources are exempt from the
import rule, as they are from E085.

Not an ALS §B (`@bounded`) rule: a `@bounded` fn calling `ffi` is E076, as for
any module outside its declared capability. Fixtures: `tests/diagnostics/e100-critical-*`
(each `meta.toml` sets `check_profile = "critical"`) and
`tests/diagnostics/e100-no-import-ffi-*` (the #4043 probes). Matrices:
`tests/critical_profile_test.rs` (`memory_unsafe_surface_is_refused_under_critical`),
`tests/memory_unsafe_import_gate_test.rs`.
