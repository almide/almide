# law ブロック実験 — C-ASSERTED を測ってみた記録 (2026-09-27)

> **これは何か**: [behavioral-contract](../active/behavioral-contract.md) の **C-ASSERTED**
> (機械が短い性質を提案し、人間は文面だけを批准し、性質は決定可能/自動化可能な断片に閉じる)
> を、設計ではなく **実測** で一度叩いた記録。出発点は「Lean の保証をプログラマの書き味で」
> という発想で、そこから数学語彙を剥いだ `law` ブロックを作り、二つの問いを測った。
>
> 1. law を見せると LLM の改変は正しくなるか(MSR 実験)
> 2. その law を機械だけで証明できるか(Lean 実験)
>
> **状態**: 実験は完了、次の一手は未着手(§7)。成果物は develop の `research/` 配下(PR #2775)、
> 生の実行データはリポジトリ外 `almide-docs-archive/law-spec-runs-2026-09-27/`。
> **兄弟文書**: [behavioral-contract](../active/behavioral-contract.md)(上位の設計)、
> [compile-time-contracts](compile-time-contracts.md)(`where` 事前条件、決定不能なら実行時検査へ落とす)。

## 1. 設計スケッチ(実験の前提)

```
law "reverse twice is identity" for (xs: List[Int]) {
  list.reverse(list.reverse(xs)) == xs
}
```

- `law` は **全入力に対するテスト** の形をした性質。命題は Bool 式で書く。
- LLM が書くのは **law(文)だけ**。証明本体・補題名・タクティクは書かせない。
- 判定は **宣言でなく算出**: 反例が見つかれば **エラー** / 証明が見つかれば `proved` /
  どちらでもなければ `tested`。`trusted` はソース外の台帳のみ(LLM が逃げ込む注釈を作らない)。
- **反例を先に出す**: 失敗時の表示は `unsolved goals` ではなく、縮小済みの最小反例。
- 原則: **誤りの証拠があるときだけ落とす。示せないだけなら落とさずレベルを下げる。**

MSR 観点の予測(実験前): 手書き証明は補題名のハルシネーションと改変脆弱性で強いマイナス、
law + 反例 + 自動判定だけならプラス寄り。この文書はその予測を測った結果。

## 2. 実験 1 — MSR(Grammar Lab `law-spec`)

**構成**: 6 課題(rle / paginate / rotate / chunk / merge / top_k)。各課題は「改変指示 +
見えるテスト + 見えない hidden テスト」。変種は `tests`(テストのみ)と `laws`(テスト + law を
読み物として提示、採点側が固定して付加)。一発目が gate(見えるテスト、laws 変種は + law)に
落ちたら出力を一度返して修正させる。hidden は採点専用 ―― **gate 通過 ∧ hidden 失敗 =
「生き残ったが実は誤り」**。モデル Haiku 4.5、各升 3 試行。

| | tests | laws |
|---|---|---|
| gate 通過(一発目) = 現行 MSR 相当 | **18/18 (100%)** | 11/18 (61%) |
| hidden 正答(最終) | 14/18 (78%) | 15/18 (83%) |
| **生き残ったが実は誤り(最終)** | **4** | **0** |

**読み方**:

- 最大の発見は law ではなく **MSR の測り方**: 弱いテストで「生存」を判定すると、tests 変種は
  100% に見えて実際は 78%。生存数の約 2 割が誤りだった。law は MSR を上げる機構というより、
  **MSR が正しいものを測るようにする機構**。
- law が効いた典型(merge): tests 変種は見えるテストが示す「リスト間の重複」だけ処理して
  hidden で全滅、laws 変種は「結果は狭義単調増加」を読んでリスト内重複・空入力まで処理した。
  ―― 効いたのは **読み物としての law**。反例を返して直す効果は、反例が返った 1 件が構文ミスで
  失敗しており **まだ一度も観測していない**。
- laws 変種の一発目の失敗 7 件のうち、law の反例で捕まったのは 1 件。残りはプロンプトの曖昧さ
  (型宣言を落とした 2 件)、既知のコンパイラバグ #2600(2 件)、構文ミス(2 件)。
  tests 変種の構文失敗は 0 件で、**law を見せると完全な解を書こうとして失敗機会が増える**
  代償があるかもしれない(n=3 では切り分け不能)。

**割り引くべき理由**: n が小さい(1 モデル × 3 試行)。law と hidden を同じ人間(実験者)が書いた
ので同じ端のケースを突いており、laws 変種が hidden と揃うのは半分は設計上当然。

## 3. 実験 2 — Lean(law を機械だけで閉じられるか)

**構成**: 6 課題の参照解を Lean 4.29.1 に **手で** 写し(hidden テストの全入力で同値を
`#eval` 確認)、law 16 本を定理として書き、人間が証明を書かずに試す。
T0 = 自動タクティク(`omega` / `decide` / `simp_all [defs]` / `grind [defs]`)、
T1 = T0 + 機械が総当たりできる帰納法(リスト引数の `induction`、定義展開後の `fun_induction`)。

| 課題 | 機械だけで閉じた | 閉じなかった |
|---|---|---|
| paginate | 1 未満のページは空 | 全ページをつなぐと元に戻る |
| rotate | 長さを保つ / 一周で恒等 | 逆回転で元に戻る |
| top_k | k 個以下 | 件数・名前順 / 上位を取りこぼさない |
| rle / chunk / merge | ― | 全部(8 本) |

**16 本中 4 本(25%)**。閉じたのは全部、定義展開で終わる浅い性質。帰納法が要るものは T1 でも
0 本。**「証明は機械が引き受ける」は素のままでは成り立たない。**

**詰まり所は証明ではなく「補題の形」**: law は包み関数(`chunk`, `merge`)について述べるが、
帰納法が掛かるのは内側の再帰補助関数(`restChunks`, `mergeAll`)で、その引数を一般化した補題が
要る(帰納法の強化)。補題を **文だけ** 人間が 3 本書くと、補題 3 本も law 2 本(chunk の再構成・
非空)も同じ機械手順で閉じた。人間の仕事は証明ではなく「どの関数について何が成り立つか」の
文で、それは形の上で law そのもの。

**定義時点の発見**: chunk の元コード(Almide)は `n ≤ 0` で無限ループする。Lean は停止しない
定義を拒否し、しかも停止性証明自体が自動では通らなかった(`List.length_drop` のヒントが要った)。
どの law もテストもこの穴を捕まえていなかった。

## 4. 発見の要約

1. **MSR は弱いテストで水増しされる**(今回 2 割)。law の採否とは独立に、Dojo の MSR が
   何割水増しされているかを測る価値がある。
2. **law の価値は修正ループ込みで出る**。一発勝負の計測では law はほぼ損。
3. **law の粒度は再帰関数単位に揃える**と自動証明に乗る。包み関数にだけ書くと閉じない。
   補題の形を機械に推測させる(lemma speculation)のは研究級。
4. **全域性は言語の問題**。停止しない関数を受け付ける限り「全入力で成り立つ」は言えない。
5. 副産物: #2771(未定義の型で E013 の誤誘導が先、根本原因 E029 が最後・位置なし ――
   LLM の修正ループには先頭の誤誘導しか届かない)。

## 5. Lean 相当に足りないもの(重い順)

今回の実験で **手でごまかした部分** がそのまま残課題:

1. **Almide → 論理 の信頼できる翻訳**(最大の穴)。今回の証明は手で写した Lean 関数についての
   証明で、Almide のコードについての証明ではない。写す段階で 3 箇所意味を変えている
   (String をリストに / chunk の `n ≤ 0` / Int の剰余)。既存の `proofs/*.v` は所有権断片の
   意味論で、ユーザー関数の値の意味論はまだ無い。先行例は Rust → Lean の Aeneas(研究一本分)。
2. **全域性**(停止性検査)。
3. **数の意味の一致**(Lean の `Int` は無限精度、Almide は 64 bit)。
4. **閉じないときの逃げ道**。LLM に証明を書かせない方針なので、閉じない law は `tested` に落ちる
   ―― 「Lean 相当の言語」ではなく「関数ごとに Lean 級の保証が付いたり付かなかったりし、
   その割合が見える言語」が現実的な到達点。
5. **小さなカーネル**。Lean を裏で使えば借りられる(比較的安い)。

### 検証としての信頼の鎖(今回どこまでが Lean 級か)

```
Almide のソース
   │ ① 手で Lean に写す          確認は hidden テストの約 25 入力の #eval だけ(= テスト級)
Lean の定義
   │ ② law を手で定理に写す      未確認
Lean の定理
   │ ③ 証明                     カーネル検査済み(Lean 級)
```

Lean 級なのは ③ だけで、鎖は最弱の輪で決まる。今回示したのは「Almide の関数が正しい」ではなく
「**写した Lean の関数について** 4 本(補題支援込みで 6 本)の性質が成り立つ」。
[`proofs/ALS.v`](../../../proofs/ALS.v) が所有権断片について立てている問い
(*you proved a MODEL — does the REAL emitted artifact correspond?*)に、関数の値の意味では
まだ答えていない状態。

- ① の弱さ: 意図した意味の変更が 3 箇所あり、意図しないずれは 25 入力では捕まらない。
- ② の弱さ: 例えば「狭義単調増加」は `getD i 0`(範囲外は 0)で書いた。範囲条件を書き損じると
  既定値のせいで **偽の性質が自明に真** になりうる。
- ③ の数字(16 本中 4 本)は「人手ゼロで閉じる率」であって検証の難しさではない。Lean に慣れた人なら
  16 本とも普通に証明できる規模。LLM に証明を書かせない設計の成立範囲の指標としてだけ読む。
