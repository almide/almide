# All Axes — 総合格闘技の勝ち筋

> 「ニッチのベルトも、総合のベルトも獲る」ための軸別戦略。
>
> [ROAD_TO_1_0.md](ROAD_TO_1_0.md) が**時間軸**（0.41→0.99 のバージョンラダー）なら、この文書は**評価軸**。
> 同じ作業を別の断面で見たもので、台帳と競合しない — 台帳の行はここでは「その軸の証拠」として引用される。
> 新しい軸の作業を始めるときは、**この文書で勝利条件を定義してから台帳の decade に割り付ける**。

## 前提: 2026 年に単一の「最強」は存在しない

外部調査（2026-08-13、4 方面・約 120 ソース）の結論は明確だった。コンパイル速度の王（Zig / tsgo）、
実行性能の王（LLVM）、証明の王（CompCert）は**全部別の実装**で、全軸同時制覇を達成した処理系は存在しない。
Carbon は世界最高クラスの人員と Google の支援を得て、announce から 0.1 まで約 6 年かかっている。

だから「最強」は**軸ごとに定義し、軸ごとに勝ち方を変える**。殴り合ってよい軸と、土俵をずらさないと
死ぬ軸がある。以下がその区別である。

## 軸 A: 編集ループ速度 — 正面から殴ってよい

**現在値**（README 自動生成、2026-08）: `almide check` 22.7ms / warm build 266.1ms / cold build 643.9ms /
cold wasm 299.1ms。ただし**測定対象が小さい** — これは規模非依存性の証明になっていない。

**勝利条件**:
1. 10k 行 dogfood（0.46/0.57）で `check` p95 < 100ms、`run` p95 < 500ms
2. debug パスから **rustc とリンカが消滅**（0.66–0.67）
3. 数字が README で公開され、ラチェット管理下（0.69）

**根拠と勝ち筋**: 2026 年の高速コンパイル事例は全て「開発ループから LLVM を外す」話である
（Zig: self-build 75s→20s、インクリメンタル 228–288ms / Roc: 3.4s→35ms / tsgo: **インクリメンタルなしで 10 倍**、
その内訳は半分がネイティブ化・半分が共有メモリ並列）。Almide は既に純 Rust なので前半は済んでおり、
残りは **Cranelift debug tier（0.6x）+ モジュール並列 + flat index-based レイアウト（#1316）**。
すべて既知の工学で、発明を必要としない。

**台帳の行**: 0.47–0.49（クエリ/キャッシュ、ただし[粗粒度で足りる](#査読-047048-はクエリエンジンではない)）、
0.61–0.69（cranelift → DWARF → default 切替 → JIT → 関数単位インクリメンタル）、#1311（行/秒ラチェット）

**足りない行**: [#1334](https://github.com/almide/almide/issues/1334) **スケール非依存ゲート** —
10k 行 dogfood 上の p50/p95 を CI ラチェットに載せる。現状の 22.7ms は「小さいから速い」を排除できていない。
0.47/0.49 の着工判断もこの数字待ちである。

## 軸 B: 実行時性能 — 土俵をずらして勝つ

**現在値**（`docs/project/BENCHMARKS.md`、CI ラチェット下）: n-body 1.135s / spectral-norm 0.685s で
**対 handwritten Rust 1.00×**、FFT のみ 1.18×（2026-08-13 に入力生成の形を修正、#1338）。
wasm レッグは native の約 1.13–1.16×。

**2026-08-13 の実測が、この軸の見立てを一つ更新した。** FFT 2^22 を段階分解したところ
（起動 / 入力生成 / カーネル、インターリーブ中央値 11 回、出力は 17 桁まで一致）:

| 生成の形 | 生成 | **カーネル** | 総 wall | カーネル対 Rust |
|---|---:|---:|---:|---:|
| 事前確保（`list.repeat` + 添字代入） | 66.4ms | **82ms** | 154.3ms | **0.872×** |
| `list.range \|> flat_map` | 116.0ms | 92ms | 213.9ms | 0.979× |
| Rust 参照（handwritten） | 39.3ms | 94ms | 138.9ms | 1.000× |
| 現行ベンチ（append ループ） | 69.1ms | 101ms | 175.9ms | 1.074× |

この表の 2 行は解消済み（2026-08-13、同日中）。`list.range |> flat_map` の生成が突出していたのは
**flat_map のラムダが中間リストを要素ごとにヒープ確保していた**ためで、末尾が固定長リテラルなら
Rust の配列を返すよう下ろすことで append ループと同着になった（[#1337](https://github.com/almide/almide/issues/1337)、
`listbuild` 3 行として perf suite に常設 + ratchet 化）。ベンチ自身の生成も事前確保に変更し、
FFT 行は 1.27× → 1.18×（[#1338](https://github.com/almide/almide/issues/1338)）。**残るのは materialize そのもの**。

**カーネルは既に handwritten Rust を 13% 上回っている**（プロセス起動は 5.9ms 対 5.6ms で差なし
＝ hello-world で個別実測済み）。つまり「スカラー codegen が天井」という当初の見立ては**測定で覆った** —
実際の律速は codegen ではなく**リスト materialize（最良の形でも対 Vec 1.69×）**である。
LLVM に命令選択で挑まないという方針は維持するが、B の敗因は一点に集約された: [#1004](https://github.com/almide/almide/issues/1004)。

### B1（守り）: ratchet 維持 + materialize コストの返済 — **この軸の最優先**

既存の `scripts/check-perf-ratio.sh` 文化を維持し、RcCow（0.55–0.56 / [#1004](https://github.com/almide/almide/issues/1004)）で
materialize ギャップを畳む。上の実測が示す通り、これは「負けないため」ではなく**勝つための前提**になった —
カーネルが 0.872× でも総 wall が 1.111× に留まる原因が全てここにあるため。関連:
[#1337](https://github.com/almide/almide/issues/1337)（推奨イディオムが最遅という矛盾）、
[#1338](https://github.com/almide/almide/issues/1338)（公開ベンチ自身が最遅の形を使っている）。

### B2（攻め）: 意味論が許す最適化で handwritten Rust を抜く ← [#1330](https://github.com/almide/almide/issues/1330)

Almide には Rust にない情報がある: **値意味論・effect による純粋性の証明・決定的データ並列（fan）・
HKT stream fusion（Phase 1–3 出荷済）**。手書き Rust が `for` ループで書くものを、Almide は
「合法だと証明できるから」融合・並列化・ベクトル化できる。これは Fortran が C に勝ち、Futhark が
手書き CUDA に勝つのと同じ勝ち方であり、**LLVM と競合しない**（LLVM の上で意味論を渡す側に回る）。

**勝利条件（勝利宣言の形）**: 名前付きワークロードで **1.0× を割る**（= Almide の方が速い）を
最低 2 本、CI ラチェット付きで README に載せる。候補は map/filter/fold チェーン（fusion が効く）と
`fan` による決定的データ並列。手書き Rust 側は「同じ最適化を人間が手で書いていない、普通に書かれた Rust」
であることを明記する（`unsafe` チューニング済み Rust に勝つ主張はしない）。

### B3（別階級）: fan → GPU で桁を変える ← [#1331](https://github.com/almide/almide/issues/1331)

`--target wgsl` は既に存在する。`fan` が決定的データ並列の構文である以上、同じソースが GPU に落ちる
デモは「別階級への出場」であって、CPU の王者と殴り合う必要がない。

**勝利条件**: 1 本の実ワークロードで、同一 `.almd` ソースが CPU レッグと GPU レッグの両方で
**同一出力**（3-way オラクルの拡張）を出し、シングルスレッド C 比で桁の差を示す。

**やらないと決めること**: 汎用スカラーコードで LLVM の命令選択に挑む最適化パスの自作。
投資対効果が最悪で、Cranelift ですら数値ホットコードで LLVM 比 15–50% 落ちる。

## 軸 C: 正しさ・信頼 — 現路線が既に最強圏、ただし穴が一つ判明した

**現在値**: 契約台帳 260 / native・wasm・interp の 3-way オラクル / Perceus の Lean ベルト /
PCC checker 1,400 行（信頼ベースを 10 万行から圧縮）/ fuzz nightly / wasm_cross 394 fixture・frontier 0。

外部調査の結論: **この組み合わせ（差分オラクル + 実行可能証拠に紐づく契約台帳 + 定理 + PCC）を
持つ言語プロジェクトは他に見つからなかった**。CompCert が 2026-03 に ATR 42/72 で DO-178C/DO-333 の
コンパイラ利用クレジットを史上初取得しており、「証明済みコンパイラで認証クレジット」の商業先例も
できた。0.7x–0.8x の資格化アークは、市場が実在する。

### 2026-08-13 に判明した構造的な穴 — fixture では塞げない

#1322 の根治で分かったこと: **native-v1 と wasm は同じ almide-mir を共有するため、MIR 層のバグは
両レッグを同一に誤らせ、394 本の parity fixture を全て緑のまま通過する**。実際に v0.57.0 から
潜伏していたスカラー let-エイリアスの miscompile が、この経路で全ゲートをすり抜けていた。
発見できたのは v0（`--no-verified`）レッグとの突き合わせだけだった。

**帰結（この軸の最重要行）**:
1. **v0 レッグと almide-interp を「反対尋問役」として維持する** — 系譜の違う実装を持たない検証は、
   共有層のバグに対して原理的に盲目。v0 の退役を検討するときは、この役割の引受先を先に決める。
   ただし interp は棄権が多く（cross-target corpus の投票率 281/402 = 69.9%）、棄権は評決ではない。
   **スカラー Int の制御フローに限れば、引受先はもう決まった**: 下の「構成によるオラクル」は
   第二実装を一切必要としないので、v0 が退役してもこの範囲の反対尋問は残る。それ以外
   （文字列・浮動小数・コレクション・effect）は未決で、v0 と interp が唯一の反対尋問役のまま
2. **生成型差分ファジング（Rustlantis 型）を linked IR 上に**（[#1332](https://github.com/almide/almide/issues/1332)）
   — fixture は回帰を捉え、ジェネレータは未知の乖離を捉える。Rustlantis は 22 バグ（LLVM 12 / Cranelift 1）を出している。
   **第一弾着地（2026-08-13）**: `tools/xtarget-fuzz` に **identity family** —
   「答えから逆算して」プログラムを構成し、期待出力をソース中のリテラルとして持たせる。
   差分ではなく**単独のレッグ**を裁けるので、両レッグが一致していても有罪にできる（＝上の構造的な穴に効く唯一の判定）。
   健全性は構成的: 各ブロックが自身の逆演算を持つか、生成時に算出した補正定数を持つか、
   分岐の両腕で釣り合っている。加えて `|acc|` の保守的上界で、唯一の切り捨て演算（`*m` / `/m` の閉じ側）が厳密になる。
   カバー範囲はスカラー Int の制御フローのみ（文字列・浮動小数・コレクションは意図的に対象外 — 安価な逆演算が無い）
3. 0.73 の translation-validation 証明書は、まさにこの層に効く（Alive2 / Crocus の実績パターン）

**台帳の行**: 0.71–0.79（証明カバレッジ → Critical プロファイル）、0.81–0.89（資格化キット製品化）、
プログラムトラック #577/#579（法人・当局リレーション）

## 軸 D: LLM writability — ホームグラウンド、階級の定義者になる

**現在値**: MSR 100%（30/30、Sonnet 4.6、almide-dojo 計測）。MiniGit Bench（同一モデル `claude-sonnet-5`、
20 試行、同一プロンプト・同一ハーネス、2026-07-15）で **20/20 通過・233 LOC で 5 言語中最小・
エージェント完了時間も最短**（[比較表](../../research/benchmark/lang-bench/README.md#same-model-snapshot-2026-07)）。

**外部の状況**: agentlanguages.dev に約 40 の AI 指向言語がカタログ化されたが、設計思想は収束
（一意綴り・明示型・JSON 診断・契約）している一方で、**end-to-end の「編集が生き残るか」指標を
持つのは Almide だけ**。"modification survival rate" の学術的採用例はゼロ。

**勝利条件（0.59）**: MSR が**土俵になる** — 公開ハーネスで第三者が再現でき、他言語も同条件で測れる。
指標を自分だけが測っている限り、それは主張であって順位ではない。

**効く投資（実証付き）**:
- **ループがコーパスに勝つ**: Idris で zero-shot 22/56 → コンパイラエラーループで 54/56。
  Qwen3-4B はコンパイラアクセスで 18.0% → 97.4%。訓練データ不足は pass@1 では消えないが MSR では消せる
- **フィードバック品質の序列**: 複合 63.6% > テスト失敗 57.9% > 最小 53.1% > **生コンパイラエラー 49.2%**
  → #1312（applicability 付き fix-it）と #1313（test 失敗の構造化）が MSR に直結する
- **構文制約デコード**: 低リソース言語では精度/コスト比が最良（CangjieBench）→ #1310（Lark/EBNF 出版）
- **effect の効果は誰も測っていない** → dojo#2（A/B）が文献初の数字になる

**正直な反証**: mame/ai-coding-lang-bench ではプロトタイプ規模で動的言語（Ruby/Python/JS）が最速最安、
後付け型検査は時間 1.6–3.2 倍。**初回実装速度では勝てない**。だから主張は「初回の速さ」ではなく
「編集の生存」でなければならず、その主張には 0.59 の数字が要る。

## 軸 E: ツールチェーン DX — ほぼ手中

**現在値**: 単一バイナリに `run/build/test/check/fmt/compile/add/deps/dep-path/clean/install/self-update/
explain/docs-gen/fix/ide/repl` と **LSP 内蔵**（hover / completion / documentSymbol / formatting /
definition / signatureHelp / codeAction）。playground、VS Code 拡張、tree-sitter 文法、grammar 単一ソース。

2026 年の table-stakes（Gleam / Astral / Zig / Deno モデル = 1 バイナリに fmt・test・LSP・pkg）は
**既に満たしている**。

> **訂正記録**: 2026-08-13 の外部リサーチ成果物は「LSP が 2026 年 table-stakes に対する最大のギャップ」
> と書いたが、これは外部調査側が `src/cli/lsp.rs` を知らなかったための誤りである。LSP は内蔵済み。

**残っている行（agent 向け surface）**:
- #1312 applicability タグ付き fix-it → `almide fix` の診断駆動化
- #1313 `almide test` 失敗出力の構造化（expected/found diff + `--json`）
- [#1333](https://github.com/almide/almide/issues/1333) **MCP サーバ / Claude Code plugin 定義** —
  2026 年のエージェント流通経路であり、LSP がある以上コストは数日
- #1314 snapshot テスト内蔵（主流言語に内蔵例がない差別化空白）

## 軸 F: エコシステム — 唯一、工学では勝てない軸

**現在値**: MVS + git 依存 + lockfile（2026 年の形式分析が MVS の多項式性を追認）、
install-time コード実行を持たない設計（npm Shai-Hulud ワームの伝播経路が構造的に不在）。
レジストリなし。stdlib は 41 モジュール 959 関数を**自己ホスト**。

**なぜ工学で勝てないか**: ライブラリの量は歴史の関数であり、コンパイラの品質では買えない。
Almide が 1 万パッケージを持つ日は、正攻法では来ない。

**では何で戦うか — テーゼの複利**: Almide のテーゼが正しいなら、**エージェントがライブラリを
量産できる**。その予行演習は既に済んでいる（stdlib 41 モジュール自己ホスト化）。次の段は
「外部パッケージがエージェントに書かれ、MSR ゲートを通って公開される」パイプラインで、
これは他言語には作れない類の非対称性である（他言語のエージェントは訓練データに依存し、
訓練データが多い言語ほど既存ライブラリも多い＝新規参入の必要がない）。

**勝利条件（1.0 以降）**: レジストリ + 「エージェントが書き、ゲートが通し、人間が承認する」
公開パイプラインが動き、そこを通った外部パッケージが 10 本存在する。

**それまでの戦い方**: ニッチのベルト（軸 C・D）が客を連れてくるまで耐える。
資格化市場（軸 C）は**エコシステムの大きさで選ばれない市場**であり、そこが最初の収益源になる。

## 依存順序 — なぜこの順か

```
軸D (MSR土俵化) ──┐
軸E (agent面)  ──┼→ 0.5x: 指標と道具を先に固める（測れないものは改善できない）
軸C (ファザー) ──┘

軸A (cranelift) ──→ 0.6x: 編集ループ。flat IR規律(#1316)が前提
軸B2 (意味論最適化) ─┘     RcCow(0.55-56)で表現を確定してから

軸C (証明・資格化) ──→ 0.7x-0.8x: codegen が安定してから積む

軸F (エコシステム) ──→ 1.0以降: 1.0 の信用が前提
軸B3 (GPU別階級)  ──┘
```

原則は台帳と同じ **「計測器が手術より先」**。加えてこの文書の原則がひとつ:
**勝利条件を数字で書けない軸には着手しない**。「速くする」ではなく「10k 行で p95 < 100ms」、
「性能で勝つ」ではなく「名前付きワークロードで 1.0× を割る」。

## 明示的に降りる軸

| 降りるもの | 理由 |
|---|---|
| zero-shot / pass@1 での勝利 | 訓練データ量が支配する。プロトタイプ規模では動的言語が最速最安（mame ベンチ実測）。土俵は MSR |
| 汎用スカラー codegen で LLVM 超え | 誰も達成していない。Cranelift ですら数値ホットで 15–50% 落ち。意味論最適化に回す |
| MLIR 採用 | 純 Rust の `cargo build` を C++ モノレポ依存と不安定 API に交換する取引。ヘテロ計算が中核価値の言語だけが選んでいる |
| 細粒度クエリエンジン（salsa 級） | matklad 2026-02 / Pyrefly / rust-analyzer の移行税。明示 import 言語は粗粒度で足りる |
| stack switching 前提の並行モデル | 未標準化。WASI 0.3 の async が答え |
| 巨大 stdlib | 凍結コストが重い（GRAND_PLAN の判断を維持） |
