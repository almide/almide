# Beyond-Rust Lab

**問い**: Almide は rustc と LLVM を通して機械語になる。その経路を保ったまま、生成する Rust をどう変えれば、
同じ rustc・同じフラグでビルドした手書きの Rust より速くなるか。

機械語を作る力（LLVM）は双方で同じなので、勝ち筋は次の 2 つしかない、というのが出発点の仮説。

- **A. 情報**: Almide の型検査・effect・値の意味論が知っていて、手書きの Rust には書かれていない事実を、LLVM が使える形で渡す。
- **B. 自動化**: Rust でも可能だが、手順が面倒で普通の Rust 利用者がやらない調整を、コンパイラが毎回自動でやる。

保留中の [performance-research.md](../../docs/roadmap/on-hold/performance-research.md) Phase 2 は
「rustc を外して LLVM IR を直接出す」案。この研究室は逆に「rustc を外さずにどこまで行けるか」を測る。
ここで届かない差が残ったときに初めて、Phase 2 を再開する根拠になる。

## 計測の単位: (カーネル, レバー) の 4 列

1 つの実験は、1 つのカーネル（計測対象のプログラム）に 1 つのレバー（生成する Rust への変換）を当てたもの。各実験で次の 4 列を測る。

| 列 | 中身 |
|---|---|
| **R0** | 普通に書いた手書きの Rust（`research/benchmark/perf/rust-ref/`）。`unsafe` なし |
| **A0** | Almide が今生成する Rust（`almide build --release` が書く `almide_gen_main.rs`） |
| **A1** | A0 にレバーを当てたもの。最初は**手で**当てる（プローブ） |
| **R\*** | 同じアルゴリズムを専門家が書いた Rust。`unsafe`・intrinsics・`assert_unchecked` を使ってよい。到達可能な上限 |

読み方:
- **Rust を超えた** ⇔ A1 < R0（同じフラグ、両方のアーキテクチャで、ばらつきを超えて）
- **レバーの価値** = A0 ÷ A1
- **残りの伸びしろ** = A1 ÷ R\*。1 に近ければ、そのカーネルは rustc 経由で上限に届いている

## 手順: 実装する前に、手で当てて測る

1. カーネルの A0 を出力させる（`/tmp/almide-run/almide_gen_main.rs`、ランタイムも含む 1 ファイル）。
2. レバーを手で当てて A1 を作る。出力が A0 とバイト単位で一致することを確かめる。
3. 4 列を同じ条件で測る（下の統制条件）。
4. 速くなった、または遅くなった行は、機械語の差分（`objdump` / `perf annotate`）で**命令レベルの理由**を書く。理由を書けない差は採用しない。
5. 卒業条件を満たしたレバーだけを、コンパイラの実装として issue にする。

手で当てて効かないレバーは、実装しても効かない。実装の費用を払う前に、安く反証する。

## 統制条件

- **同じ rustc、同じフラグ、同じ target CPU** を 4 列すべてに使う。target CPU はコンパイラの既定から取り、手で書き写さない（#3883: Almide 側だけが `x86-64-v3` で、比べ方が不公平になっていた）。
- 4 列の出力はバイト単位で一致すること。浮動小数点の演算順の入れ替え（fast-math）は使わない（native と wasm の出力一致の約束を壊すため）。
- 2 つのアーキテクチャで測る: GCE c4-standard-8（x86、Xeon 8581C）と c4a-standard-8（arm、Neoverse-V2）。
- 列を交互に実行し、7 回以上の中央値を取る。PMU（性能カウンタ）がある VM では命令数（`instructions:u`）も記録する。
- 引数は実行時に渡す。リテラルにすると、LLVM がループごと式に畳んでしまう。

## 卒業条件

レバーは、次の 3 つをすべて満たしたときにコンパイラの仕事になる。

- 2 つ以上のカーネルで A0 ÷ A1 ≥ 1.05
- 両方のアーキテクチャで成り立つ
- どのカーネルも 2% を超えて遅くならない

卒業したレバーは、性能チェック（`scripts/check-perf-ratio.sh`）の行と一緒に入れる。

## レバー一覧

| ID | 種類 | レバー | 仮説（LLVM が何をできるようになるか） |
|---|---|---|---|
| L1 | A | 証明済みの事実を `assert_unchecked` / 範囲検査なしの添字 / 符号なし演算として出す | 範囲検査の分岐が消える。`/2` が符号なしのシフトになる。ベクトル化の判断が正しくなる（#3604 の enumerate の添字） |
| L2 | A | 値の意味論による別名なしを、`noalias` が付く引数の形（`&mut [T]` と `&[T]` の分離）で出す | ロードの削除とベクトル化ができるようになる |
| L3 | A | effect のない関数を、LLVM が読み取り専用と推論できる形で出す（インライン化の境界、`#[inline]` の付け方） | 共通部分式の削除と、ループ不変式の外出しが効く |
| L4 | B | 熱い関数を、関数ごとに CPU 設定を変えた複数の版でビルドし、速い版を選ぶ（`#[target_feature]` と実行時の切り替え） | nbody は portable、spectralnorm は v3 のように、両方の得を取る（#3883） |
| L5 | B | PGO（実際に動かして集めた統計で最適化し直す）を `--release` の延長として自動でやる | 分岐の配置とインライン化の判断が、実際の実行に合う |
| L6 | A | コールバックを `Rc<dyn Fn>` から、具体的な関数への直接呼び出しにする | 呼び出しのたびの呼び先調べが消え、インライン化される（R0 と同じ土俵に立つ） |

L6 は「超える」ではなく「追いつく」ためのレバーだが、これが残っていると他のレバーの得が見えないので一覧に入れる。
メモリ確保の意味論（region window、Perceus の再利用）はすでに勝っている系統で、
[BENCHMARKS.md](../../docs/project/BENCHMARKS.md) の VICTORY 行で別に追う。

## カーネル

`research/benchmark/perf/` の既存の行（nbody、spectralnorm と慣用形 2 種、fasta、fft、fannkuchredux、mandelbrot）に加えて、
レバーごとに効き目を切り出す小さなカーネルを足す。

- enumerate の添字
- コールバック付きの map / fold

## E1 の結果（L1、2026-10-20）

生データ: [results/2026-10-20-E1-c4-standard-8.json](results/2026-10-20-E1-c4-standard-8.json)、[results/2026-10-20-E1-c4a-standard-8.json](results/2026-10-20-E1-c4a-standard-8.json)。

**条件**: rustc 1.99.1（LLVM 23.1.1）を 4 列すべてに。フラグは全列共通で `-C opt-level=3 -C codegen-units=1 -C lto=fat -C panic=abort -C llvm-args=-force-ordered-reductions=false`、
加えて target CPU。主の組は Almide の `--release` と同じ（x86_64 は `x86-64-v3`、aarch64 は指定なし）。副の組は x86 が target CPU 指定なし、arm は `native`（arm では指定なしが主の組と同じになるため）。
A0 は v0.68.0-rc2 のリリースバイナリが書いた `almide_gen_main.rs` と、同じく書き出したランタイム crate（`almide_rt.rs`）を、上のフラグで組み直したもの（Almide 自身と同じ 2 crate の形）。
9 回の中央値、列は毎回順番を回して交互に実行。出力の SHA-256 は全カーネル・全列で一致。引数は実行時に渡す（spectralnorm 5500、nbody 50000000、idxloop `100000 5000`）。

**A1 で当てた事実**（すべて Almide のソースから局所的に証明できるものだけ）:

| ID | 事実 | 検査器が知れる理由 | 当てた場所 |
|---|---|---|---|
| F1 | 行の添字 `i` は `0 <= i < n` | `for i in 0..<n` のカウンタ、または `list.map(0..<n, …)` の要素 | spectralnorm 3 種 |
| F2 | 列の添字 `j` は `0 <= j < n` | `for j in 0..<n` のカウンタ、`list.fold(0..<n, …)` の要素 | spectralnorm、indexed |
| F3 | `pair.0` は `0 <= pair.0 < len(v)` | `list.enumerate(v)` の添字 | enumerate |
| F4 | `1 <= i < n - 1`、`n = list.len(xs)` | 範囲のカウンタと、不変の List の長さ | idxloop |
| F5 | `i - 1`、`i`、`i + 1`、`i / 2` は `[0, len(xs))` に入る → `get_unchecked` | F4 から | idxloop |
| F6 | `i >= 0` → `i / 2` を符号なしの除算に | F4 から | idxloop |

当てなかったもの: spectralnorm の `v[j]` の範囲検査（`len(v) == n` は呼び出し側をまたいだ長さの追跡が要る）、`eval_a` の `ij * (ij + 1) / 2` を符号なしにすること（Int は wrapping なので、`n` に上限がない限り積が負になり得る）。nbody の熱いループには添字も整数演算もなく（カウンタは未使用）、当てる場所がないので A1 = A0（patch は空）。

A0 の確認: 組み直した A0 と、`almide build --release` が書いたバイナリの差は 1% 以内。例外は x86 の indexed（A0 が 2.3% 速い）と arm の nbody（A0 が 2.5% 遅い）。違いは `panic=abort` とランタイム crate のフラグ（Almide は `codegen-units=4`）だけ。

**機械語で見た理由**（差が 2% 以上の行すべて）

- **A0 は事実をもう持っている。** 範囲のカウンタと enumerate の添字について、LLVM は A0 で同じ事実を自分で導いている。spectralnorm 3 種の F1–F3 は、x86 でも arm でも熱いループの命令が A0 と同じだった（`perf annotate`）。A0 では `v[j]` の範囲検査もループの外に出ている。ループの出口を `min(n, len)` にして、抜けた後で中断するかどうかを見る形になる。idxloop の A0 も、範囲検査はひとつも残っていない。arm では `i / 2` は `lsr`、`r as f64` は `ucvtf`。x86 では 4 本並べてベクトル化されている。L1 が足せる情報は、もう入っていた。
- **spectralnorm_indexed の遅れ（x86 −21%、arm −2%／`native` −12%）は F2 が原因。** fold のクロージャの中の `assert_unchecked(0 <= j && j < n)` を入れると、`v[j]` の範囲検査がループの中に残る（x86 `cmpq %rbp,%rdx` + `je`、arm `cmp x10,x14` + 分岐、毎回）。A0 は出口に畳めていた。x86 ではさらに、A0 の 2 倍展開と 2 本の割り算の対（`vdivpd %xmm`）が消え、1 回ずつの `vdivsd` になる。命令数は x86 17.55G → 22.39G（+28%）、arm 15.13G → 18.15G（+20%）。F2 を外して F1 だけにした探りの列は A0 と同じ命令列になる（x86 の主の組で −2.3% は残るが、熱いループの命令は A0 と同じで、理由は特定できていない）。
- **idxloop の arm での遅れ（主の組 −20%）。** A1 では読み込みが無条件の `get_unchecked` になる。そのため LLVM は `xs[i-1]` と `xs[i]` を次の周回へレジスタで持ち越すように書き換える（1 周あたり読み込み 3 → 2、`fmov` 2 本を追加。命令数 7.50G → 8.00G、+6.7%）。命令の差はこれで全部。ただ、それが Neoverse-V2 でなぜ 20% にもなるのかは、機械語からは説明できていない。
- **idxloop の arm `native` での速さ（+4.5%）は説明できていない。** 命令数は同じ（5.50G）で、どちらも 2 倍展開。違うのは命令の並びとレジスタの割り当てだけ。
- x86 の idxloop（主の組）では A1 の命令数が 3.50G → 3.13G に減ったが、時間の差は 1% 未満。

**R\* の伸びしろ**（A1 ÷ R\*）
- spectralnorm、x86: 1.57–1.97。R\* は同じ演算順のまま 4 行をまとめて SIMD のレーンで割り算する。分母は f64 で計算し、`n <= 2^20` なら正確。命令数は 17.5G → 4.7G。これは L1 ではなく、行の並列化という別のレバーの候補。
- spectralnorm、arm: ≈ 1.0。R\* は `fdiv v.2d` を使い、命令数は半分（15.1G → 7.3G）なのに時間は同じ。Neoverse-V2 では f64 の割り算のスループットが律速で、2 レーンにしても得がない。`native` では R\* のほうが遅い（0.86–0.92）。
- nbody: x86 1.04–1.14、arm 1.08–1.18。R\* は位置が変わらない間の 10 本の `sqrt`／割り算を、4 レーン 3 組で計算する。
- idxloop: ≈ 1.0（arm の主の組の 1.25 は A1 自身の遅れ。A0 ÷ R\* = 1.00）。

**ついでに見えたこと**
- x86 `x86-64-v3` の idxloop では A0 が R0 より 1.66 倍速い（0.273 対 0.454）。R0 は `xs[i / 2]` などの範囲検査が 1 周に 2 本残り、スカラーのまま。A0 は検査なしで 4 本並べてベクトル化される。L1 とは関係なく、すでに「Rust を超えている」行。
- nbody は x86 で `x86-64-v3` にすると、指定なしより A0 が 11% 遅い（2.01 対 1.81）。R0 は変わらない。#3883 と同じ現象。arm では A0 が R0 より 18% 速い（2.86 対 3.48）。
- 1 crate の形（`ALMIDE_NO_RTLIB=1`、ランタイムを `src/main.rs` に含む）は、arm で enumerate 1.31 秒、indexed 1.34 秒。Almide のバイナリ（1.12 秒、1.22 秒）より遅いので、A0 には使わなかった。理由は調べていない。

**結論**: L1 を「証明済みの事実を、出せる場所すべてに機械的に出す」形で実装すると、得はなく、損が出る。このカーネル群では、L1 が出せる局所的な事実を LLVM はすでに導いている。冗長な `assert_unchecked` は、LLVM がしていた変形（範囲検査を出口に畳む、展開してベクトル化する、読み込みの配置）を壊す。L1 を続けるなら、対象は LLVM が自分では導けない事実に限る。例として、呼び出しをまたいだ長さ（`len(v) == n`）や、範囲つきの整数（`n` の上限から、積が負にならないことが言える）がある。その事実を出す前に、A0 の機械語に、それで消える命令が実際に残っていることを確かめる。
