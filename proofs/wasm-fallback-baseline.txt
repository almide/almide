# COMPILER_FRONTIER (4) — the debt, in leverage order:
spec/lang/closure_capture_map_test.almd :: COMPILER_FRONTIER :: defunc closure frontier — measured: 1 of 23 fns walls, `__almd_test_2` ("closure folds records through a captured map via match"), "computed closure call outside the liftable subset". The captured cell is a Map[String, Record] and the closure body MATCHES on map.get before writing back, so the callee is not statically resolvable at the call site — the two SCALAR-cell tests in the same file already render. Needs the closure-env brick (lift a computed callee whose capture set includes a heap cell), not another typed twin.
spec/lang/result_zip_test.almd :: COMPILER_FRONTIER :: result.zip_x unlinked — the walling instantiation is `zip(Result[Float, String], Result[String, String]) -> Result[(Float, String), String]`. Not the mechanical twin recipe: the two SIDES carry different tag layouts (scalar Ok is len-as-tag, heap Ok is cap-as-tag @16), so the twin must read each side's tag by its own rule, and the Ok payload is a MIXED tuple whose String element must be co-owned and freed by a recursive drop route that does not exist for `Result[(Float, String), String]`. The all-scalar `result.zip` twin already renders.
spec/stdlib/fs_streaming_test.almd :: COMPILER_FRONTIER :: blocked on `for_each_line` over a CAPTURED var, not on the accumulator twins. 2 of the 6 tests (`var seen` + list.push, `var calls` + increment) need a closure whose capture set is mutated inside the callback — the same closure-env brick as closure_capture_map_test. The fold_lines String/Int/List[String] accumulator twins are mechanical (the `_ls` chunked twin landed the same way) but landing all three still leaves those 2 tests walled, so this row does not move until the closure brick does.
